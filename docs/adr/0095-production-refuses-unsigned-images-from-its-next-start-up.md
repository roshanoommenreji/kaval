# ADR-0095: Production refuses unsigned images from its next start-up

**Status:** Accepted on 2026-11-13 (Roshan: `start KAV-143`, then `go` on the plan; the sixth and last story of the supply-chain line). **Built 2026-11-13 (#411) and proved live on production the same evening** (his `go production start-up`, then `apply production`; [Lab 97](../labs/lab-97-production-refuses-unsigned-images.md) Part 4): a signed image accepted, an unsigned one refused, both alerts loaded, memory measured. Two things are not yet seen live and are listed under Consequences.
**Deciders:** Roshan

## Context

Since 2026-11-13 staging has refused any Kaval image that is not signed by `release.yml` on `main` and is not on the frozen list of 19 older releases, and fails closed when the checker is down ([ADR-0094](0094-the-cluster-refuses-unsigned-images-on-staging-and-fails-closed.md); proven live the same day). Production still only had the promotion gate ([ADR-0092](0092-promotion-refuses-an-image-whose-signature-does-not-verify.md)): nothing stopped an unsigned image from being started on it by someone with cluster access, or by a pin changed some way other than `promote.yml`.

[ADR-0094](0094-the-cluster-refuses-unsigned-images-on-staging-and-fails-closed.md) said production would get the same "only after it has run a signed release and the memory on its real node is measured". Two questions follow from that sentence:

1. **Watch first, or refuse from the start?**
2. **Does production have to run a signed release before it gets the checker?**

## Options considered (what real companies do)

| | How it goes | Cost |
|---|---|---|
| **Watch, then refuse** (two production start-ups) | production gets the checker in report-only mode, a later change flips it | the safest on paper, but production would run for a while with the weaker guarantee, and the flip is a second change and a second session |
| **The same policy as staging, from the first start-up** | what was proved on staging goes to production unchanged; production's first session proves it | one change, one session; relies on the staging proof being faithful, so production must match staging file for file |
| **Wait for a signed release to be promoted first** | production runs a signed image, then gets the checker | needs a release round (an image change) only to satisfy an ordering rule; the first signed release is a side effect of an unrelated change |

## Decision

**Production gets the very same checker as staging, refusing and failing closed, from its next start-up. Production's first session proves the signed path with a throwaway pod, so no signed release has to be promoted first.**

1. **Same files, not a variant.** [ADR-0004](0004-environment-strategy-and-promotion.md): environments differ only by values and pins. The policy file `deploy/image-policy/image-validating-policy.yaml` is shared and unchanged. Production adds copies of staging's three Flux files in `deploy/gitops/prod/` (the checker's source, the pinned Kyverno release and the policy's own Flux object). Kustomize cannot share one file across folders (found at `KAV-51`), so they are copies, and a test fails the build if the staging and production copies differ in anything but the namespace.
2. **Scope: the production Kaval namespace only** (`kaval-prod`, filled in by Flux). The checker's own pods, Flux and the system pods are never waiting on it. That scope is what makes `Fail` safe, exactly as on staging.
3. **The registry login** is switched on in production's Terraform (`image_checker_enabled = true`): the server's start-up script copies `ecr-cred` into the `kyverno` namespace and refreshes it with the 6-hourly timer, which already refreshes the Kaval namespace's own login (the ECR token lasts 12 hours). A test pins that the checker's copy sits inside the part that timer re-runs. Staging's sessions have never lasted six hours, so the refresh of the checker's copy is not yet proven live by time; it is the same code path as the one that has kept production's own login fresh since `KAV-51`.
4. **Prometheus watches it** (`imageChecker.enabled: true` in production's values and in the hand-kept inline copy in `deploy/gitops/prod/helmrelease.yaml`): a scrape job and the two alert rules (`ImageCheckerDown`, `UnsignedImageSeen`), which reach Slack through the route that carried the four real cards on 2026-11-13.
5. **Production runs `sha-d1058eb` today**, which is on the frozen list, so every production pod starts. The signed path is proved by one throwaway pod, not by a promotion: `sha-152b59e` (built and signed by `release.yml`, never promoted, not on the list) is started in `kaval-prod`, expected to be accepted, and then deleted. The pod only sleeps, holds no secret and has a memory ceiling. This tests what a promotion would first test (Sigstore reachable from production's server, the registry login valid, the signature found) without needing an image change to carry it.
6. **The negative case is planted, not assumed.** The proof gives one old image a second name in the registry (`unsigned-trial`: same image, no signature, not on the list), starts a pod from it in `kaval-prod`, expects a refusal with the reason in the answer, and removes the name afterwards. A name that does not exist would also be refused, but for the wrong reason.
7. **Memory is measured on the real server, with the model loaded.** The checker used 44-51 MiB on staging; production's server also runs the language model, and the last production figure (2026-10-16) was 872 MB free at the worst moment. The proof reads the server's free memory and the checker's own use before and after. **Stop rule:** if the server has less than about 300 MB free with the model loaded, or the checker restarts for lack of memory, go back to watch-only by pull request (point 9) and decide again.
8. **What is not repeated on production.** The hard-kill of the checker and the emergency off-switch were proved on staging with identical files and the same Kyverno release; production does not get a deliberate outage for the sake of repeating them. The runbook carries both.
9. **The off-switch is the one from [ADR-0094](0094-the-cluster-refuses-unsigned-images-on-staging-and-fails-closed.md):** normal = a reviewed pull request to `[Audit]` + `Ignore`; emergency = delete Kyverno's two hooks.
10. **The proof is a script, not a scratchpad:** `scripts/ops/checker_proof.py <prod|staging> <step>` (steps `state`, `alerts`, `plant`, `signed`, `unsigned`, `frozen`, `clean`, `unplant`). The steps that create or delete refuse to run without `--yes`, which the owner's typed go covers.

## Consequences

- **Cost:** $0 a month on AWS. The proof session is about 5-10 cents on top of a production start-up the owner is doing anyway (production costs about $0.044 an hour while up); it rides on the next such start-up, there is no special trip.
- **Production's next start-up is the first time the checker runs there.** If it misbehaves, the rest of production still starts: Kyverno and its policy are separate Flux objects that nothing else waits on, and the namespace scope keeps the system pods clear.
- **What `terraform plan` shows for production** (read-only, run 2026-11-13): two in-place changes, the launch template (the start-up script) and the node group that points at it. The same plan also carries a newer base machine image (AMI) that was already waiting (`KAV-96` follow-up); both take effect when the server next starts, and the node group is parked at 0, so applying either changes nothing running. The AMI change is a separate risk from this story's, and the first start-up after it is the first time that image runs.
- **The frozen list ends 2026-12-31** (a test fails the build after that). Before then production should be on a signed release, or a rollback to a listed release will be refused. The next real release round plus `go promote` does that, and it is also the pass case `KAV-139` is waiting for.
- **Known limits, carried over and now true on production too:** a refusal right after a checker restart can leave `UnsignedImageSeen` silent; if the checker is down for good, the monitoring pods in the same namespace cannot be recreated either (Prometheus keeps running, but would not come back from a restart until the checker is repaired). Both are in the runbook; neither is fixed here. Sigstore being unreachable refuses even signed images ([ADR-0094](0094-the-cluster-refuses-unsigned-images-on-staging-and-fails-closed.md) point 4, accepted).
- **Not covered:** the same as [ADR-0094](0094-the-cluster-refuses-unsigned-images-on-staging-and-fails-closed.md): a pod's image changing without a pod being created or updated; pods outside the Kaval namespace; the checker's own supply chain.
- **Tests:** the existing 27 policy tests plus parity tests (copies identical, wrong namespace, switch, timer, listing, Prometheus), each shown to go red by a deliberate breakage; 17 tests for the proof script.

## What the live session found (2026-11-13, 18:43-19:00 IST)

- **Start-up:** the apply made exactly the two changes the plan showed (0 added, 2 changed, 0 destroyed). The checker was ready 4 minutes after the apply; `make prod-smoke` passed 9 of 9 on the first boot on the newer base image (the first time that image ran on production).
- **Signed accepted, unsigned refused:** a pod from the signed `sha-152b59e` was accepted (`pass`). A pod from a planted unsigned name was refused: the API server's answer names the policy and says "failed to verify cosign signatures", the pod does not exist, `fail` counted 1, a `PolicyViolation` Event was written, and `UnsignedImageSeen` fired. Both alert rules were loaded and healthy (`ImageCheckerDown` quiet).
- **My first negative test was wrong, and the checker was right.** The first planted name was copied from `sha-d1058eb`, and the planted pod was **accepted**. The pods' image digests were identical: `sha-d1058eb` and `sha-152b59e` are the **same gateway image** (the gateway code did not change between the two builds, and the signature belongs to the image, not to the tag). The checker correctly let a signed image in. The script was at fault: it now reads both digests and refuses to plant when they match, and the test was redone from `sha-791c44d` (a different image), which was refused. Only the gateway is shared: the agent, collector and executor images of `sha-d1058eb` differ from the signed release, so production's other three programs still depend on the frozen list.
- **Memory (the stop rule's measurement):** idle, about 1,400 MB available; with the language model loaded (1.1 GB, CPU), **414 MB available** on the 3,829 MB server; the checker used 51-56 MiB; 0 out-of-memory kills; no pod restarted. The stop rule (under about 300 MB) was not reached, but the margin is thinner than October's 872 MB free: the checker is about 56 MiB of a gap that is mostly Prometheus, the cost reader and the diagnoser, added since. A real diagnosis may use more than the one tiny question asked here; the existing alarm for memory pressure stays the watch. `make prod-smoke`'s "about 800 MB is normal while the model is loaded" is out of date (it was never gated).
- **Not seen live on production, accepted for now:**
  - *The frozen-list pass.* Production's own pods started before the checker was ready (Flux applied both together), so they were not counted. The same rule was proved on staging (a real gateway pod recreated through the live checker) and on the laptop; a new `frozen` step in `scripts/ops/checker_proof.py` covers it at the next start-up.
  - *The six-hour refresh of the checker's login.* The session lasted 17 minutes. A test pins that the checker's copy sits inside the part the timer re-runs.
- **Not repeated, as planned:** the hard kill of the checker and the emergency off-switch (proved on staging with the same files and Kyverno release).
- **Cost:** about 1 cent (up 17 minutes). Production was parked again at 19:01 after a fresh dump (396K, uploaded); registry planted name removed, real tags untouched.
