# ADR-0035: Versions are computed from commits, tagged after the images exist, and the change record rides in the promotion pull request

**Status:** Accepted
**Date:** 2026-10-10
**Related:** [ADR-0013](0013-component-versions-and-release-naming.md) (what a version is and how a release
is named), [ADR-0011](0011-commit-convention-and-jira-link.md) (the commit convention it reads),
[ADR-0030](0030-ci-publishes-images-by-oidc-and-staging-is-pinned-by-pull-request.md) (`release.yml`),
[ADR-0032](0032-promote-workflow-and-the-promotion-guard.md) (`promote.yml`),
[ADR-0034](0034-rollback-workflow-and-what-a-rollback-may-go-back-to.md) (the measured restore time),
`KAV-67`, Lab 36

## Context

ADR-0013 decided *what* a version is: each component has its own, a release is named `Kaval X.Y.Z` with its
components listed, tags are `<svc>-vX.Y.Z` and `vX.Y.Z`. It left the machinery to "release-please or a small
stdlib script, decided then", and said versions stay at `0.1.0` until a release exists. By 2026-10-10 a
release exists (`sha-2459417` is pinned in prod's files), nothing computes a version, no tag exists, and
`docs/releases/` holds only a format description. The change record the README promises (digests, changes,
issues, risk, staging evidence, rollback plan, verification) was also never written by anything.

## Decision

**1. A small stdlib script, not release-please.** `scripts/release/versions.py` reads the conventional
commits that touched each component since its last tag and says what the next version is. Release-please would
add a dependency, a manifest, its own changelog files and its own pull-request flow, and still would not know
which paths ship in which image. The script is about 350 lines, has tests, and sits next to the other release
scripts.

**2. Which files belong to which component is checked against the Dockerfiles.** `SHIPS` in `versions.py`
maps a path to the components whose image carries it: a service's own folder, `services/shared/` and
dependency files to the four deployed services, `migrations/` to the gateway, `policy/` to the agent and
executor, the backup scripts to `backup`. A test reads every Dockerfile's `COPY` lines and fails if the map
disagrees with what an image really contains, so the map cannot drift quietly.

**3. The bump is its own pull request, because the version must be in the code before the image is built.**
The image carries its version as a label stamped from `__version__` (ADR-0013). So bumping after the build
would put an old number on the new image. `release-prepare.yml` (run by hand from `main`) computes the plan,
writes `__version__` in each component that changed, `pyproject.toml` and `uv.lock`, and opens
`chore(release): Kaval X.Y.Z`. Merging it starts `release.yml`. (`uv.lock` records the project's own version
and CI's `uv sync --locked` fails if it disagrees with `pyproject.toml`, so all three move together; this was
checked with `uv lock --check` against a real bump.)

**4. Tags are made by `release.yml`, after the images are pushed, and only for versions with no tag yet.**
`versions.py tag --commit $GITHUB_SHA --push` makes `<svc>-vX.Y.Z` for each component and `vX.Y.Z` for the
product at the commit that built the images. Each tag is annotated with the bill of materials. A merge that
bumped nothing tags nothing, and running it twice is harmless. The first tags (`*-v0.1.0`, `v0.1.0`) are the
baseline, made once at `sha-2459417`, the version prod is pinned to; they are what the next bump counts from.

**5. While a version is 0.x, a breaking change moves the minor number** (amends ADR-0013, which said
major). `1.0.0` should be a decision about the project, not the side effect of a `!` in a commit. From 1.0.0
on, ADR-0013's rule stands. The product version follows the largest move among the components, after this rule.

**6. The change record is generated by `promote.yml` and travels in the promotion pull request.**
`scripts/release/change_record.py` runs in the `propose` job (no AWS, no Jira, by design), reads Git, the
passed-staging record and the gate's own output, and writes `docs/releases/YYYY-MM-DD-vX.Y.Z.md` into the
same pull request as the prod pin. Merging the go/no-go therefore also records what was decided. Its fields:

| Field | Source |
|---|---|
| Components, previous versions, digests | the versions in code at the new and the previous commit; the record's digests; `(unchanged)` when a digest equals the previous release's |
| Changes | non-merge commits since the version prod ran before, grouped by the component they touched |
| Issues | `KAV-n` keys in those commits' subjects |
| Risk | derived from the files touched (see below) |
| UAT | the gate's own line, copied from its output |
| Staging evidence | the record's checks and its `not_covered` list |
| Rollback plan | the version prod runs now, the exact command, whether going back crosses a migration, the last measured restore time (ADR-0034) |
| Verification | honestly "not recorded yet": the file is written before anything has run |
| Lead time | from the oldest commit in the release to when the record was written |

Risk rules: **high** if it adds a database migration, contains a breaking change, changes the executor, or
changes `policy/`; **medium** for infrastructure or the chart, shared code, or dependencies; **low** otherwise.
Each reason is listed in the record.

**7. The record says when the version number is not the whole truth.** A line "Unreleased changes in this
build" runs the same plan against the released commit: if it finds commits that would still bump a version, the
numbers shown are the last tagged ones and the images carry more. That is the honest answer to "is this
exactly 0.2.0?", and the reason to run `release-prepare.yml` just before promoting.

**8. The baseline record is backfilled once.** `docs/releases/2026-10-09-v0.1.0.md` was generated with
`--previous sha-ffb436b --note ...` for the promotion merged as pull request #83. It has no gate output to
quote and says so. Prod is parked, so it also says nothing has run it.

**9. Found and fixed on the way.** Pull request #83's text said "Prod runs `sha-2459417` now": `promote.yml`
rewrites prod's files with `pin` and only then wrote the text, which read the rewritten files. `promote.py`
now reads prod's committed state (`committed_prod_tag`), with a test.

## Alternatives considered

| Option | Why not |
|---|---|
| **release-please in manifest mode** | A dependency and a second flow for a job a short script does, and it does not know the Dockerfiles. Easy to adopt later if the script outgrows itself: the tag names are the same |
| **Bump inside `release.yml` after the build** | The image label would carry the old number |
| **Bump with a commit pushed straight to `main`** | Branch protection exists so nothing reaches `main` without checks. Every other bot in this repo opens a pull request; so does this |
| **Tag at promotion time instead of publish time** | A tag should name the commit that built the images. Promotion happens later and may be of a later commit; it would also let `promote.yml` write to tags, a new power it does not need |
| **Write the record when prod is verified healthy** | There is no automatic prod verification yet (prod is parked and CI has no cluster access). Writing it with the pin, with "verification: not recorded yet", is true and available today |
| **Have the record call Jira for story titles and UAT** | `propose` has no Jira access on purpose (ADR-0032). The keys and the gate's own UAT line are enough; titles are one click away |
| **Fold shared-code changes into every version (image-content versioning)** | Every image contains the gateway, collector and agent code, so every change would bump everything and the per-component idea (ADR-0013) would be empty |

## Consequences

**Easier.** "Which gateway is in prod?" has an answer: the record, the tag and the image label. A release has
a generated, reviewable change record at the moment it is approved. A person never types a version.

**Harder / limits.**

- **Two of the three new workflow changes have not run live yet.** `release-prepare.yml` has (dispatched
  on `main` on 2026-10-10 after the baseline tags were pushed: it checked out the history and tags, ran the plan
  and correctly reported "nothing has changed that moves a version"). `release.yml`'s tag step and
  `promote.yml`'s record step have not; unit tests, a real run of the generator against this repository's
  history, and a bump rehearsed in a clone (including `uv lock --check`) are what prove them. The first real promotion after this one exercises them; a failure there blocks the pull
  request, loudly, rather than writing a wrong record.
- **A component's version is about its own folder, not the whole image.** The gateway image also contains the
  collector's and agent's code (the Dockerfiles copy them), so a collector-only change changes the gateway
  image's bytes without bumping the gateway. That is ADR-0013's rule as written; the image digest is what
  identifies bytes, the version is the human label.
- **"Approved by" is who started the promotion**, because the merger is not known when the file is written.
  The approval itself is merging the pull request.
- **"Rolled back" says `no` until a rollback happens, then `rollback.yml` edits it** (KAV-71, amendment below).
  "Time to restore" stays `—`: the restore happens after the merge, so the file written before it cannot
  know it. It is measured by hand per the runbook.
- **The Jira Release (fix version) is a manual step, not CI's** (ADR-0013, 6). It needs write access to Jira,
  which CI deliberately lacks. Done 2026-10-10: `jira-sync.py release X.Y.Z` (Lab 42).
- **The measured restore time in a record is a constant** (`MEASURED` in `change_record.py`, from staging).
  Update it and ADR-0034 when prod's own time is measured.
- Every bot pull request's first CI run still waits for a person to approve it.

**Revisit when** the script needs per-package changelogs (then release-please), a second maintainer joins and
"Approved by" must be the merger.

## Amendment 2026-10-10 (KAV-71): a rollback marks the record it undoes

The follow-up this ADR listed. `rollback.py pin` now finds the newest `docs/releases/` file whose `Image tag`
is the tag prod runs *before* the pin, and rewrites its `Rolled back` line to
`yes, to <tag> on <date>. Why: <reason>`. `rollback.yml` commits that file in the same pull request as the
pin, exactly as `promote.yml` does for a new record, so merging the go/no-go also records it, and a rollback
pull request closed unmerged leaves the record alone.

- **Why in the same pull request, not a later job:** a record changed outside the reviewed change is a record
  nobody approved. This keeps "the merge is the decision" true in both directions.
- **A missing record never blocks a rollback.** A rollback is an emergency and the record is bookkeeping, so
  `pin` prints "nothing to mark" and carries on.
- **Already marked is left alone**, so a second rollback of the same release does not overwrite the first
  one's account.
- **Rejected:** a separate bookkeeping job after the merge (needs write access on `main`, which CI
  deliberately lacks); making "Time to restore" a typed field in the workflow (a number someone types is the
  thing the records exist to avoid).
- The dashboard already counted `Rolled back: yes...`, so change-failure rate now moves (`test_rollback.py`
  reads a marked record through `dashboard.read_releases`).
