# ADR-0027: Secrets and database roles recreate themselves after node replacement

**Status:** Accepted
**Date:** 2026-10-04
**Related:** [ADR-0008](0008-production-database-on-its-own-server.md) (the database server and its
per-service roles), [ADR-0025](0025-flux-gitops-and-ecr-bootstrap.md) (the node's existing
`ecr-cred` bootstrap pattern this extends), `KAV-32`, `KAV-56`

## Context

KAV-32 built the production database server and gave each service (`gateway`, `agent`,
`executor`, `collector`) its own Postgres role, with the five resulting passwords generated by
Terraform and held in SSM Parameter Store. Turning those into the Kubernetes Secrets the chart
actually reads, and running `scripts/ops/db-roles.sql` to create the roles, was left as a manual
step — the `db-roles-job` Helm hook that was supposed to automate it got blocked mid-KAV-32 by
this environment's own safety classifier ("Containment Escape": a Job combining five Secrets'
passwords into one container's environment).

That gap surfaced for real the same night. The app node runs as a single EC2 **spot** instance
(`infra/modules/node`, cost reasons — see `docs/cost/budget-plan.md`), running a single-node k3s
control plane. Spot capacity can be reclaimed with two minutes' notice; the ASG replaces the
instance automatically, and cloud-init re-bootstraps Flux against this repo, so everything
*declared in Git* reconciles itself within minutes. Everything declared in Git — which, by design
(ADR-0008, ADR-0026), does not include the five `kaval-postgres-*` Secrets or `kaval-slack`. Those
live only in the replaced node's own k3s state. A real reclamation mid-session wiped all of them,
and the on-call fix was "SSM in and type `kubectl create secret` six times" — not something that
scales, and not how a real production environment would handle it.

## Decision: extend the node's own bootstrap script, not a Kubernetes-native secret syncer

Two more conventional fixes were considered and rejected before landing on this one.

**External Secrets Operator**, the standard Kubernetes-native answer, needs a pod to read AWS
credentials — normally via the node's IAM role over the instance metadata service (IMDS). A pod
is one network hop further from IMDS than the host itself, and EC2's metadata hop limit defaults
to 1 specifically to keep pods out. Raising it to 2 so ESO's pod could reach IMDS was attempted
and blocked by this environment's own classifier ("Security Weaken") for the right reason: this
cluster's CNI is **Flannel**, which doesn't enforce `NetworkPolicy` at all, so there is no way to
raise the hop limit for ESO's pod without also raising it for every other pod in the cluster —
gateway, agent, executor, collector would all gain the node's own AWS permissions, not just the
one pod that needs them.

**EKS with IRSA** is the textbook fix for exactly this problem: each pod gets its own scoped AWS
identity over OIDC federation, with no hop-limit trade-off at all. It was rejected on cost, not
security: EKS's control plane is a flat **$0.10/hour (~$73/month)**, charged for the cluster's
existence, independent of whether any compute is running inside it. This project pauses the app
node (`desired_capacity` to 0) between sessions specifically to save money — the node itself was
at 0 when this very session started. EKS would mean either eating $73/month regardless of that
pause, or tearing down and rebuilding the whole control plane every session, which is slower and
more fragile to automate than restarting one EC2 instance. It doesn't fit this project's actual
usage pattern, and the $40/month ceiling (ADR-0008) doesn't have room for it without `lab-eks`
style ephemeral use, which this isn't.

**What was built instead**: the node's existing `kaval-gitops-bootstrap` script
(`infra/modules/node/user_data.sh.tftpl`) already refreshes one AWS-derived credential on every
boot and on a 6-hour systemd timer — the ECR login token behind `ecr-cred`, because this node has
no EKS-style per-workload credential provider either. That script now also:

1. Reads the five database passwords and three Slack values from SSM Parameter Store and
   recreates/updates the matching Kubernetes Secrets, idempotently (`kubectl ... --dry-run=client
   -o yaml | kubectl apply -f -`, the same pattern the script already used for `kaval-registry`).
2. Runs `scripts/ops/db-roles.sql` against the database server with those same five passwords.

This runs **on the host itself, never inside a pod** — no change to IMDS hop limits, no change to
what any pod can reach, nothing a compromised application pod could ever use differently than it
could before. The node's IAM role gained a new scoped policy (`read-app-secrets`:
`ssm:GetParameter(s)` on exactly these parameter paths, `kms:Decrypt` on the `aws/ssm` key alias)
and `ec2:DescribeInstances` (to look the database server up by its `Role=database` tag rather than
a hardcoded IP — `DescribeInstances` has no resource-level IAM scoping, so this one grant is
necessarily `Resource: "*"`, the same unavoidable shape as the pre-existing `ecr:GetAuthorizationToken`
grant). The three Slack SSM parameters hold Terraform-managed placeholders — there's nothing to
auto-generate a Slack token from, unlike the database passwords — and their real values were set
once, directly, via `aws ssm put-parameter --overwrite`, never pasted to an assistant, the same
discipline as every other credential in this project.

## What this changes about the blast radius, stated plainly

Before this change, the node's own IAM role could do two things: manage itself over SSM, and pull
container images. After this change, it can also read six specific secrets. A host compromise now
exposes more than it did before — that's real, not hidden. It's weighed against the alternative
that was rejected: handing that same reach to every pod in the cluster instead of to the one
already-most-trusted thing running on it. Narrower than that alternative, wider than before
tonight. Both things are true.

## Bugs found live while building this, not during planning

1. **`ec2:DescribeInstances` denied.** The first real test (terminate the node, watch the
   replacement) failed with `UnauthorizedOperation` on exactly this call, aborting the whole
   bootstrap script before it ever reached Flux's own `source.yaml`/`helmrelease.yaml`/`sync.yaml`
   apply — the cluster had no app running on it at all until this was found and fixed.
2. **`scripts/ops/db-roles.sql` had never actually been run before tonight** — its intended
   runner (`db-roles-job`) was the Helm hook blocked earlier in KAV-32 and never built as anything
   else. First real run hit a genuine PL/pgSQL bug: psql's `:'var'` substitution does not reach
   inside a `DO $$ ... $$` body, so the literal text `:'gateway_password'` was being sent straight
   to the server — a syntax error, not a silently wrong password. Fixed with the standard pattern
   for this (`set_config()` outside the `DO` block, `current_setting()` + `format(..., %L)`
   inside it), verified against a disposable local Postgres container before shipping.
3. **`db-roles.sql`'s own GRANT list was incomplete.** Its comment claimed the table list
   "matches `docs/architecture/architecture.toml`'s `db` node," but the real schema
   (`services/shared/kaval_shared/models.py`) has two tables it never accounted for:
   `incident_signal` (the join table `correlate.py` both reads and writes) and `runbook_chunk`
   (`kaval_agent.index_runbooks`' own table). The deployed agent crash-looped on exactly the
   missing one (`permission denied for table incident_signal`) until this was found and fixed.

None of these three were guessed or caught by review — each came from actually terminating the
node and watching what broke, which is also the verification this story's own acceptance criteria
asked for.

## Consequences

- No one types `kubectl create secret` or runs `db-roles.sql` by hand after a node replacement,
  on this node, going forward.
- The node's IAM role is a more valuable target than it was before this change — stated above,
  not hidden.
- `scripts/ops/db-roles.sql` is now actually exercised on every boot and every 6h, not just at
  KAV-32's original (never-actually-run) intended moment — a latent bug like the two found
  tonight is far more likely to be caught the same night it's introduced, not months later.
- The `db-roles-job` Helm hook from KAV-32's original design is now superseded — this bootstrap
  script does that job instead, on the host rather than as a cluster-native hook. The hook idea
  is not revisited; it hit the same category of restriction a second time (see Rejected
  alternatives) for an unrelated reason the first time didn't fully explain.

## Rejected alternatives

- **External Secrets Operator** — needs pod-level IMDS reach that this cluster's CNI (Flannel)
  can't scope to one pod. See Decision above.
- **EKS with IRSA** — the textbook fix, rejected on its flat ~$73/month control-plane fee
  conflicting with this project's stop/start cost pattern, not on security grounds.
- **A dedicated static IAM user credential for a syncer pod** — narrower blast radius than
  opening IMDS to every pod, but reintroduces a long-lived AWS key sitting in a Kubernetes
  Secret, the exact pattern this project has avoided everywhere else (ADR-0026's Slack tokens,
  every database password here). Not pursued.
- **Switching the app node off spot** — would reduce how *often* this problem occurs, not
  whether it occurs; an on-demand instance can still be replaced (AZ failure, a bad apply, a
  manual Terraform change), and it costs more every month for a problem this story already
  solves more completely. Not pursued.
