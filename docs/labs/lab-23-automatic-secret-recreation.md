# Lab 23 — Secrets and database roles that survive a node replacement

**Phase:** 4 · **Time:** ~20 min for the Terraform/script changes, plus three live
node-termination tests
**Cost:** $0 (reuses the node's existing IAM role and its existing boot script; no new AWS
resource)

KAV-32 gave every service its own Postgres role and password, generated by Terraform and held in
SSM Parameter Store — but turning those into Kubernetes Secrets, and creating the roles in
Postgres, was left manual. The app node is a spot instance; it got reclaimed mid-session the same
night, wiping every manually-created Secret along with it. This lab closes that gap. The design
reasoning, the two alternatives rejected (External Secrets Operator, EKS with IRSA), and the
blast-radius trade-off stated plainly are in
[ADR-0027](../adr/0027-automatic-secret-and-role-recreation.md).

This lab is three real bugs found live, in order, each one only visible once the previous one was
fixed and a fresh node actually booted. None were guessed.

---

## What's built (reproducible from zero)

### Step 1 — the node's IAM role can read the new secrets

`infra/modules/iam`: a new `read-app-secrets` policy on the node's role —
`ssm:GetParameter`/`GetParameters` scoped to exactly the DB password and Slack parameter ARNs
(`var.secret_parameter_arns`, built from `module.database.ssm_parameter_arns` plus the three
Slack parameters' own ARNs — never a wildcard path), `kms:Decrypt` on the `alias/aws/ssm` key, and
`ec2:DescribeInstances` (necessarily `Resource: "*"` — this action has no resource-level IAM
scoping; see the bug it caused, below).

### Step 2 — three placeholder SSM parameters for Slack

`infra/envs/prod/main.tf`: `aws_ssm_parameter` resources for
`/kaval/kaval-prod/slack/{bot-token,app-token,channel-id}`, `SecureString`/`String`, value
`"REPLACE_ME"`, `lifecycle { ignore_changes = [value] }` so Terraform never fights the real value
once it's set. There's nothing to auto-generate a Slack token from (unlike the database
passwords), so this is as far as Terraform can go on its own:

```bash
aws ssm put-parameter --profile kaval --region ap-south-1 --overwrite \
  --name "/kaval/kaval-prod/slack/bot-token" --value "<real value>"
# ...same for app-token and channel-id
```

### Step 3 — the bootstrap script itself

`infra/modules/node/user_data.sh.tftpl`, inside the existing `kaval-gitops-bootstrap` script
(the same one that already refreshes `ecr-cred` every 6h), right after the `ecr-cred` Secret is
built:

```bash
declare -A DB_ROLE_USERS=( [admin]=kaval [gateway]=kaval_gateway [agent]=kaval_agent [executor]=kaval_executor [collector]=kaval_collector )
DB_HOST=$(aws ec2 describe-instances --region "$REGION" \
  --filters "Name=tag:Role,Values=database" "Name=instance-state-name,Values=running" \
  --query "Reservations[0].Instances[0].PrivateIpAddress" --output text)

for role in "${!DB_ROLE_USERS[@]}"; do
  DB_PASSWORD=$(aws ssm get-parameter --region "$REGION" \
    --name "/kaval/kaval-prod/db/${role}-password" --with-decryption \
    --query Parameter.Value --output text)
  kubectl create secret generic "kaval-postgres-${role}" -n kaval-prod \
    --from-literal=POSTGRES_HOST="$DB_HOST" --from-literal=POSTGRES_PORT=5432 \
    --from-literal=POSTGRES_DB=kaval --from-literal=POSTGRES_USER="${DB_ROLE_USERS[$role]}" \
    --from-literal=POSTGRES_PASSWORD="$DB_PASSWORD" --from-literal=POSTGRES_SSLMODE=require \
    --dry-run=client -o yaml | kubectl apply -f -
  unset DB_PASSWORD
done
# ...same --dry-run=client | apply pattern for kaval-slack from the three Slack parameters
```

Then `scripts/ops/db-roles.sql` is fetched from this repo's raw GitHub URL and run with the five
passwords as `psql -v` variables. `postgresql15` (the `psql` client) is installed once, at first
boot, outside this repeating function. Both the Secret recreation and the `db-roles.sql` run are
idempotent — safe to repeat on every boot and every 6h run of the existing systemd timer, not
just the first one.

Every `${...}` that's meant for the real shell (not Terraform's own template substitution) is
escaped to `$${...}` — `terraform validate` catches the ones that aren't; it does not catch bash
syntax errors, so a `bash -n` check on the rendered template is a second, separate step worth
doing before pushing (`terraform console` with `jsonencode(templatefile(...))`, decoded, piped to
`bash -n`).

## The three bugs, in the order they were actually found

### Bug 1 — `ec2:DescribeInstances` denied

First live test: terminate the node, watch the replacement. The new bootstrap script aborted
immediately after creating `ecr-cred`, with:

```
aws: [ERROR]: An error occurred (UnauthorizedOperation) when calling the DescribeInstances
operation: ... is not authorized to perform: ec2:DescribeInstances
```

`set -euo pipefail` meant the whole script stopped there — Flux's own `source.yaml` /
`helmrelease.yaml` / `sync.yaml` never got applied either, so the cluster had **no app deployed
at all**, not just missing Secrets. Fixed by adding the grant from Step 1. Verified by re-running
the (now-fixed) script by hand via `aws ssm send-command` against the already-broken node — it
completed end to end, including the Flux apply, and all 5 pods came up `Running`.

### Bug 2 — `db-roles.sql`'s own syntax error

`scripts/ops/db-roles.sql` had never actually run before this story — KAV-32's intended runner
(a `db-roles-job` Helm hook) was blocked before it was ever built. First real run:

```
psql:/tmp/db-roles.sql:22: ERROR:  syntax error at or near ":"
LINE 4:     CREATE ROLE kaval_gateway LOGIN PASSWORD :'gateway_passw...
```

psql's `:'var'` substitution does not reach inside a `DO $$ ... $$` body — the dollar-quoting
hides it from psql's own pre-scan of the input, so the literal text `:'gateway_password'` was
sent straight to the server. Fixed with the standard pattern for this exact situation:

```sql
SELECT set_config('kaval.gateway_password', :'gateway_password', false);  -- plain top-level SQL; substitution works here
DO $$
BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'kaval_gateway') THEN
    EXECUTE format('CREATE ROLE kaval_gateway LOGIN PASSWORD %L', current_setting('kaval.gateway_password'));
  ELSE
    EXECUTE format('ALTER ROLE kaval_gateway PASSWORD %L', current_setting('kaval.gateway_password'));
  END IF;
END $$;
```

Verified against a disposable local Postgres container (`docker run --rm -d postgres:16`, fake
passwords): all four roles created, a real login with the generated password succeeds, re-running
the script a second time is a clean no-op on the `CREATE` path.

### Bug 3 — `db-roles.sql`'s GRANT list was incomplete

With bugs 1 and 2 fixed, a fully fresh node boot got further than ever — Secrets recreated,
roles created — but the deployed `agent` pod still crash-looped:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.InsufficientPrivilege) permission denied for table incident_signal
```

`db-roles.sql`'s own comment claimed its table list "matches
`docs/architecture/architecture.toml`'s `db` node," but the real schema
(`services/shared/kaval_shared/models.py`) has **nine** tables; the GRANT list only covered
seven. Missing: `incident_signal` (the many-to-many join table `correlate.py` reads and writes
while grouping signals into an incident) and `runbook_chunk`
(`kaval_agent.index_runbooks`' own table, per its model docstring). Fixed by adding both GRANTs.
Verified the same way as Bug 2 — disposable container, full 9-table schema, the exact failing
query and the exact write (`INSERT INTO incident_signal`) both reproduced and confirmed fixed as
`kaval_agent` before shipping.

## Verification (the actual end state, after all three fixes)

Terminate the app node (`aws autoscaling terminate-instance-in-auto-scaling-group --instance-id
<id> --no-should-decrement-desired-capacity`), wait for the ASG's replacement to reach
`InService` and SSM `Online` (a few minutes), then from the node:

```bash
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get pods -n kaval-prod
```

Expected, and what the third and final test actually showed: all 5 pods `Running`, **0
restarts** — including `agent`, which had been crash-looping before Bug 3's fix. No
`kubectl create secret`, no manual `psql` invocation, nothing typed by a human anywhere in this
run.

```bash
kubectl logs -n kaval-prod -l app.kubernetes.io/component=agent --tail=15
```

`"nothing new"` twice — the correlate loop's normal healthy output when there's nothing new to
correlate, not an error.

## Known gap, named not hidden

The node's IAM role can now read six secrets instead of one — a real, larger blast radius than
before this story, if that one host were ever compromised. Weighed against the alternative
(handing the same reach to every pod in the cluster instead), this is narrower, not absent. See
ADR-0027's "What this changes about the blast radius" section for the full reasoning. Secret
*rotation* is still manual and infrequent (Terraform generates each password once; nothing
expires or rotates them on a schedule) — unchanged by this story, not newly introduced by it.
