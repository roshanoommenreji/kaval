# Releases

Change records, one per production deploy, **generated by `promote.yml`** — never typed.

That distinction is the point. A change record written by hand is written to satisfy a process,
so nobody reads it and it is often wrong. One generated from commits, Jira and the pipeline's own
outputs is accurate, costs nothing per release, and is therefore worth reading when something has
gone wrong at 2am.

Empty until Phase 4, when the pipeline exists. The dashboard's Releases panel reads this directory
and says "no releases yet" until then.

## Format

The filename is `YYYY-MM-DD-vX.Y.Z.md`. `scripts/tracking/dashboard.py` parses the heading and the bullet
fields, so those must keep their shape — everything below them is free text.

```markdown
# Release v0.4.1 — 2027-01-14

- **Environment:** prod
- **Approved by:** Roshan
- **Digest:** sha256:a3f9c2...
- **Lead time:** 3.1 days
- **Rolled back:** no
- **Time to restore:** —

## Changes
Generated from conventional commits since v0.4.0.

## Issues
From Jira smart commits.

## Risk
Derived: does this touch infrastructure, policy, or the executor?

## Staging evidence
Which tests passed, on which digest, at what time.

## Rollback plan
`helm rollback kaval <n>` — previous revision, and the last *measured* time-to-restore.

## Verification
Post-deploy check result, recorded after the fact.
```

## Why each field is there

| Field | Because |
|---|---|
| **Digest** | "v0.4.1" is a label someone can move. A digest is not. |
| **Approved by** | The human oversight claim needs a name against it |
| **Lead time** | Commit → production, one of the four DORA measures |
| **Rolled back** | Feeds change failure rate |
| **Time to restore** | Measured, not estimated. "We would roll back" is not a plan. |
| **Risk** | Derived from what the diff touches, not from someone's mood |
| **Staging evidence** | *What* passed, not merely that something was tested |
