### What we learned, and what changes

1. **Measuring first paid off.** The plan had a possible new measuring agent (15 to 20 MiB). The
   read-only look on staging showed the existing numbers already see the disk, so nothing was added to
   the 4 GB node and the whole disk feature is two kept metrics and one query.
2. **The staging line had to be lower than prod's, and that is a recorded, tested difference.** A
   bounded fill cannot reach 85 % of 20 GB, so staging's own settings use 0.38 and the chart keeps 0.85
   for prod (a test checks both). The code path is identical; only the number differs. The honest limit
   is that the 85 % line itself has not been crossed live.
3. **The four-layer refusal held, two layers seen live.** The policy said `never` for a restart filed
   against a disk incident, and the gateway refused the approval. The agent and the executor layers are
   proven by unit tests (nothing live reaches them, because the gateway stops first).
4. **Disk problems and the "unhealthy" noise do not mix any more.** This run, unlike the slow-service
   run, was on the build with the correlator lane, and the incident opened under its own name straight
   away.
5. **Still not seen:** a real Slack post (staging has none; prod, `KAV-83`), the disk check in prod
   (Prometheus is not there yet, `KAV-83`), a slow fill over hours (no trend is built: ADR-0047), and the
   database server's own disk (another machine, `KAV-82`).
