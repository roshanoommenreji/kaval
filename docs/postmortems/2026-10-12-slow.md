### What we learned, and what changes

1. **Staging's live settings are a second copy that a change can miss (run 1).** What Flux deploys is
   the inline `values:` of `deploy/gitops/staging/helmrelease.yaml`. The probe target and the disk
   line were added only to `deploy/environments/staging/values.yaml`, which every render and test
   reads. The deployed poller had an empty target. A known gap ("hand-kept copy") had been written down
   in the file's own header, but nothing checked it. **Fixed** by adding both settings, and by a test
   (`scripts/dev/test_gitops_values_in_sync.py`) that fails whenever an environment's two copies
   differ. It also found nothing else out of step, in staging or prod.
2. **One incident per program let a harmless event hide a slow service (run 2), and that is a safety
   hole, not a cosmetic one.** The rule "no fix for a slow service" reads the incident's *name*. Under
   the name `unhealthy` the rule did not apply, so the agent would have been free to propose a restart.
   **Fixed:** causes that are for a person now have their own lane in the correlator and always form
   their own incident under their own name, and ordinary signals never join one. Five tests reproduce
   the live case (three fail on the old code). Kaval's own health incidents gain the same protection.
3. **A commit of mine failed silently and a pull request merged without the fix it described.** The
   commit subject was six characters over the limit and I had filtered the output that said so; the
   cluster showed the truth (the setting still empty) and it was redone. Lesson for the tooling: after a
   commit, check that the commit exists.
4. **Chart ahead of image.** When the poller's new arguments reached the cluster (the chart is read
   from git at once) before the new image did (the staging pin is a separate pull request), the old
   image crashed for about five minutes on the new arguments. It healed by itself, and Kaval's own
   "service is down" alert fired for it, which is the alert working on a real fault. Noted; no change.
5. **Staging cannot show the Slack hop.** Staging has no Slack connection, so a real post is seen only
   in prod once Prometheus reaches it (`KAV-83`). The check runs the real alert code as a dry run and
   prints the exact message, which proves the text and the choice of signal, not the delivery.
6. **A hand-filed proposal against a people-only incident cannot be approved at all.** The gateway
   refuses (409) before the executor is ever involved, so the executor's own refusal is proven by unit
   tests, not live. Four layers, two of them live.
