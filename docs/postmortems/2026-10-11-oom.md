### What we learned, and what changes

1. **Kaval called it a crash loop, not a memory problem.** The incident's cause is `crashloop`; the
   container's `OOMKilled` reason is available but does not change the label. The by-hand proposal
   supplied the memory diagnosis. Whether an OOM kill should be its own cause is decided with the
   crashloop experiment: noted on `KAV-80`.
2. **The memory-pressure warning never fired**, and should not have: the victim is killed the moment
   it allocates, so it never *sits* near its limit. That warning catches slow growth; this experiment
   is the sudden case. A gradual-growth variant would exercise it: noted for `KAV-83`.
3. **The kill switch works.** By accident: a second start (my mistake) was refused by the runner, and
   its exit then switched the shared switch off, which aborted the first run after 190 s and removed
   its victim. Fixed (PR #131): a start is refused *before* the switch is touched.
4. **Twelve minutes was too short for a person.** The first full attempt reached the proposal and ran
   out of time before anyone approved. The window is now 20 minutes, the hard limit 25 (PR #131).
5. **Three defects in my own tooling were found by running it**, all in `chaos.sh` and fixed: a quoting
   bug in the check for a running Job, an input stream the proposal pod never received, and the
   restart of the switch described above. None was visible in tests that stub the cluster.
6. **A proposal left over from the aborted attempt** (`a04bbf92`, for a victim that no longer exists)
   is still waiting for a decision in staging. If approved it would fail with "not found", which is
   harmless. Real systems need this tidied by an expiry: that is `KAV-82` (approval expiry).
