## Pre-stop snapshot, and the discovery that `make down` never actually paused the database (`KAV-32`, ADR-0008 amended, Lab 24)

Picked up the next `ROADMAP.md` Phase 4 line: the pre-stop snapshot ADR-0008's stopping table
already names. Re-reading that table while designing it surfaced a real gap: it says `make down`
pauses "the app node and the database... together" — but `make down` has only ever run
`terraform destroy -target=module.node`. The database has been running unpaused, billing its full
~$14.40/mo, since the 2026-10-04 apply, through every session since, including last night.
Corrected the chat guidance given last night, which had said the opposite.

**Built:**

- `scripts/ops/pause-database.sh` / `resume-database.sh` — stop/start the database instance
  (never terminate), idempotent, wired into `make down`/`make up`. The pause script snapshots
  the data volume first, tagged so it's findable by the exact query
  `docs/runbooks/restore-from-backup.md` already used before this story existed.
- The hard-stop Lambda (`infra/modules/budget/lambda/hard_stop.py`) does the same
  snapshot-then-stop for every `Project=kaval` instance it stops at the `$38` threshold, not just
  ones paused by the scripts above. New IAM: `ec2:DescribeVolumes` (no resource-level scoping
  exists for it, same shape as `ec2:DescribeInstances` in ADR-0027), `ec2:CreateSnapshot` scoped
  to `Project=kaval`-tagged volumes, `ec2:CreateTags` scoped to `ec2:CreateAction=CreateSnapshot`
  since the snapshot doesn't exist to tag-scope against until the same call creates it.

**Found live, not guessed, from a `terraform plan` run to review the above:** the database's DLM
daily-snapshot policy has been sitting in AWS's `ERROR` state since KAV-32's very first apply —
a month ago, functionally — because `copy_tags = true` already copies the source volume's `Name`
tag onto every snapshot, and the schedule's own `tags_to_add` also set a `Name` tag. DLM rejects
the resulting duplicate key and never retries on its own; nothing surfaces this loudly, it just
sits silent until someone looks at the policy's actual AWS state rather than its Terraform
config. **No daily snapshot had ever been taken.** Fixed by dropping `tags_to_add` (`copy_tags`
alone already carries `Name`/`Role`/`Project` from the volume); `terraform plan` confirmed
`ERROR → ENABLED` as the only change to that resource. Full writeup in Lab 24.

Applied with explicit go-ahead (the plan review surfaced the app-node ASG drift from last
night's manual pause too, and Roshan chose to resume it in the same apply rather than keep it
paused). Three of four planned resources applied cleanly; the ASG's instance launch hit a real,
transient AWS spot-capacity shortage for `t4g.medium` in `ap-south-1` — confirmed via
`describe-scaling-activities`, not a config problem — and kept auto-retrying on its own after.

Jira board was also stale in a way unrelated to today's work: `KAV-32` showed 0 of 12 acceptance
criteria ticked, despite 6 of them having been genuinely finished in the 2026-10-04 apply. Ticked
those 6 plus today's 7th (pre-stop snapshot — covers 2 of its 3 named stop paths; the third,
the nightly auto-stop schedule, doesn't exist yet to wire into, and is its own unticked AC item).
Left `Backups` unticked: the DLM half is fixed and live now, but the nightly `pg_dump`-to-S3
half is still disabled, same blocked `aws-creds` script named in Lab 22.

## Nightly auto-stop, the third stop path (`KAV-32`, ADR-0008 amended, Lab 25)

Picked up the next `ROADMAP.md` Phase 4 line: ADR-0008's stopping table has said since
2026-09-26 that a 02:00 IST EventBridge Scheduler rule covers a forgotten `make down`; it just
didn't exist yet.

Built it to reuse, not duplicate: the new `aws_scheduler_schedule` (`infra/modules/budget`)
targets the *same* `hard_stop` Lambda the $38 threshold already calls, instead of writing a
second copy of "scale the ASG to zero, snapshot-then-stop every `Project=kaval` server outside

this off once Phase 7 makes the system always-on.

`terraform plan` showed exactly 4 resources to add, 0 to change — confirmed before applying.
Applied with explicit go-ahead; `aws scheduler get-schedule` confirms `ENABLED`,
`cron(0 2 * * ? *)`, timezone `Asia/Kolkata`, target the hard-stop function. Ticked the matching
`KAV-32` acceptance criterion directly via the Jira API rather than `jira-sync.py tick` — that
command marks every remaining AC item done in one call, and KAV-32 still has four genuinely open
(staging DB, nightly `pg_dump`-to-S3, start-up health check, SSM Patch Manager/connection
logging), so a blanket tick would have lied about those. Status stays `In Progress`.

## The Watchtower dashboard artifact and the repo's own generator had quietly diverged

Went to republish the Claude.ai dashboard artifact ("Kaval Watchtower") after a routine
`make docs-sync`, and caught a real gap before publishing over it: the two new plain-language
pages added to that artifact directly in an earlier session — "AWS, plain and simple" and
"Inside the cluster", each with its own clickable flow diagram — only ever existed in the
published artifact's HTML. `scripts/tracking/dashboard.py`, the actual generator that's supposed
to be the single source of truth `docs/dashboard.html` is built from, never knew about them.
Publishing the freshly generated file over the live artifact would have silently deleted both
sections.

Ported them into the generator properly instead of re-patching the artifact by hand again:

- New `[[aws-tour.node]]`/`.edge` and `[[pods-postgres.node]]`/`.edge` tables in
  `docs/architecture/architecture.toml` — the same data-driven shape `system`/`journey`/
  `delivery` already use, so `render_diagram()` generates both the SVG and the click-to-inspect
  detail data automatically, rather than hand-maintaining raw SVG markup a second place.
- The prose itself moved into two new source files, `docs/architecture/aws-tour.md` and
  `docs/architecture/pods-postgres.md`, split by a `<!-- diagram -->` marker that
  `dashboard.py` splices the generated diagram into.
- Two new entries in `dashboard.py`'s `arch_cards` list put both pages on the board as clickable
  cards, same as the three existing architecture views.
- One side effect, accepted rather than fought: the generator derives each node's built/active/
  planned status from its owning `ROADMAP.md` phase, not from a hand-set label. Phase 4 is still
  `[~]`, so most AWS-tour/pods-postgres nodes render "active" (dashed, with a `P4` badge) rather
  than the uniformly-solid "all built" look the hand-drawn version had. That's more consistent
  with how the rest of the dashboard already depicts in-progress Phase 4 work than a special
  case would have been, even though it's a small downgrade from the original's visual polish.

No Jira story for this — it's closing a gap in how the existing dashboard tooling stays in sync
with itself, not new product scope, so it went on its own `chore/` branch rather than piggy-backing
on an unrelated story. Verified by regenerating and checking the output directly: both views
render with the correct node/edge counts, their tables and diagrams, and the `DETAIL` JS object
carries both — then republished the artifact from the regenerated file.
