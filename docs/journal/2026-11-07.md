## Should Kaval build OPA itself? A laptop trial (`KAV-131`)

`KAV-131` is the decision [ADR-0033](../adr/0033-dated-trivy-exception-for-the-bundled-opa-binary.md) promised before the fifth exception ends on 2026-11-21: keep downloading OPA's release file and excusing each scanner finding, or build OPA from its published source. Roshan chose it as the first job after the morning's merges. It was done in a separate worktree, on a laptop, with no AWS and no cost, and nothing was merged. [ADR-0079](../adr/0079-where-the-opa-binary-comes-from.md) holds the comparison and a recommendation; [Lab 79](../labs/lab-79-building-opa-ourselves-and-proving-it.md) is the trial, step by step.

**What was built.** OPA v1.21.4 (the version in use) from the commit its tag points at (`05c8451`, checked three ways), inside the Go image OPA's own recipe names (`golang:1.27.3-trixie`, pinned by digest), with that recipe's flags and one change: `golang.org/x/net` raised to 0.62.0 (the fix for CVE-2026-78661), which `go get` raises together with five sibling libraries from the same Google repository.

**What it showed.**
- *The unmodified rebuild is the official program:* the same 94 libraries, the same build settings, 60.30 MB against 60.32 MB.
- *The scanner (the same Trivy and flags CI uses, an empty exception list):* the official file fails with CVE-2026-78661 alone; the rebuild with the fix passes, and so does a rebuild with a second fix.
- *Same answers:* identical on 1,000 policy questions on amd64 and on 308 on arm64 (emulated), with the real data and again with a promotion added so that `auto` can happen; a control that has to differ did, on exactly the questions where a promotion makes the answer `auto`. Both files pass all 29 policy tests.
- *OPA's own tests:* its whole unit-test suite on the fixed tree passes in 129 packages; one timing-sensitive test (`TestActivateV1Bundles`, "context deadline exceeded") failed once on a busy laptop, and it also fails once in ten on the untouched tag, so it is not caused by the library change.
- *Repeatable:* two builds from empty caches gave byte-identical files, and building through a Dockerfile stage with `docker buildx`, the way CI would, gave the same bytes again (`72f34858...`); the lab's own script, run as printed in a fresh container, gave them a third time.
- *Cost:* about two minutes a build on 4 CPUs (3 min 3 s when the libraries are downloaded too, 2 min 46 s through buildx); the binary is the same size, so the images do not grow.

**Two surprises.** First, the flawed code is not in OPA at all: zero functions of the HTML package `x/net/html` are in the official file. The scanner matches library *versions*, not functions. OPA's own weekly release check is `govulncheck`, which reports only flaws OPA can reach, so upstream sees nothing to fix and has no reason to hurry; waiting for them is not a plan. Second, a rebuild with no git tag is stamped with a made-up version (`v0.0.0-<date>-<commit>`), which made Trivy report three old OPA findings and `govulncheck` one, none real; tagging the checkout `v1.21.4` removed all four. And `govulncheck` already flags a different library in the official file (`klauspost/compress` 1.20.0, fixed in 1.20.2) that Trivy does not yet: probably the sixth finding. A second override in the same recipe cleared it, and `govulncheck` then reported no vulnerabilities.

**Recommendation, not a decision.** Build it ourselves, as a small checked stage in both Dockerfiles (option C in the ADR). It ends the pattern instead of managing it: every one of the five findings had a fix available on the day it appeared. It costs nothing in AWS and about two minutes of build only when a pin changes. The decision is Roshan's and is due before 2026-11-21; the ADR stays `Proposed` until then, and if he chooses to keep the download instead, the ADR says what limit replaces it. The implementation would change both images, so its merge is held until after tomorrow morning's teardown (tonight's staging reads `main`).

**Working notes.** The worktree tool puts the new branch's folder inside the repository's `.claude/worktrees/` (already excluded from git), so the main folder stayed on `main` and clean. Extracting OPA's source on Windows fails on its 260-character path limit, so the source is checked out inside Docker, which is also how the Dockerfile stage does it. The hostname stamp copied from OPA's own recipe turned out to do nothing in this version (both files print an empty hostname); the lab keeps it only so its checksums can be reproduced, and the implementation drops it.

**Decided.** At about 17:10 IST Roshan chose to build (`decide build`, option C). [ADR-0079](../adr/0079-where-the-opa-binary-comes-from.md) now reads Accepted, and the build is its own story, `KAV-132`, under the same Phase 8 epic as `KAV-130` and `KAV-131`. Its pull request is opened so that CI runs the real build on the arm64 runner, but it is not merged until after tomorrow morning's teardown, because it changes the images and tonight's staging reads `main`; this ADR change is documentation only and may merge at any time.

## CodeQL switched on, and made to prove it can find something (`KAV-110`)

Scorecard's code-analysis check scored 0 on 2026-11-01 and the threat model listed "no static code analysis" (T-SUPPLY-5). `KAV-110` turns on CodeQL, GitHub's code scanner, which is free on a public repository. [ADR-0080](../adr/0080-codeql-scans-every-pull-request-and-starts-as-advice.md) holds the decision; [Lab 81](../labs/lab-81-turning-on-codeql-and-reading-what-it-says.md) is the step-by-step. It changes only CI (pull request #333), so it may merge at any time, including before tomorrow morning's teardown: `release.yml` starts only on changes to the services, migrations, policy and a few scripts, so a new workflow cannot build an image or open a release pull request.

**What was built.** `.github/workflows/codeql.yml` scans the Python and the workflow files on every pull request, after each merge, every Monday 04:41 UTC and by hand. The token starts empty; the job gets `contents: read` and `security-events: write`; every action is pinned to a commit; nothing is built. It is **not a required check yet**: it becomes one after a clean week (ADR-0080). Nine tests were written first and seen failing (`scripts/dev/test_codeql_workflow.py`); breaking the workflow thirteen different ways was caught every time by the test meant to catch it.

**What it showed.**
- *The pull request's scan found nothing, which said less than it seemed to:* 0 alerts, with the log showing that 268 Python files were read by 45 queries and the 8 workflow files by 18. But on a pull request CodeQL reports only the alerts in the lines the pull request changes (GitHub's diff-informed analysis), and this one changed a single Python file. Both jobs took about a minute, next to the existing checks, so a pull request waits no longer than before.
- *The first full scan, of `main` after the merge, raised one alert:* `py/bind-socket-all-network-interfaces` (medium) in `services/shared/tests/test_metrics.py`, a test that opens a port on purpose so that the metrics server's "port already taken" path is exercised. It was dismissed as `used in tests` with a written reason; fixing it would mean editing `services/`, which starts a release build, so it was not worth doing for a test.
- *A scan that finds nothing proves little,* so a throwaway pull request (#334, a draft, closed and never merged) planted four mistakes on purpose: a database query and a shell command built from a web request, the Flask debugger left on, and a workflow pasting an issue title into a shell command. CodeQL caught all four (two critical, two high) and GitHub's own `CodeQL` check went red, "4 new alerts including 2 critical". The four alerts were dismissed as `used in tests` with a sentence of why, which also proved the dismiss command, and the branch was deleted.
- *One surprise:* the first version of the planted workflow was **not** flagged. It had an empty token (`permissions: {}`), and CodeQL calls an injection critical only where the job has something worth stealing. Given a write permission it was caught. Kaval's own workflows start with an empty token, which is part of why the real scan is quiet; so "no findings" is read together with "and it can find things".

**Done after the merge (about 22:35).** Roshan merged #333 (`a0374d9`); no release build and no bot pull request started. CI and the scan of `main` were green. Scorecard, run by hand, now reads SAST **7** (it was 0): "3 commits out of 30 are checked", as its rule predicted (7 points for the workflow, about one tenth of a point for each merged pull request that ran a scanner). Three of `KAV-110`'s four boxes are ticked; the fourth ("runs on pull requests and weekly") waits for the first scheduled Monday scan, 2026-11-09 04:41 UTC.
