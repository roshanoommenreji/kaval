# 2026-10-09

## `promote.yml`, the gate between staging and prod (`KAV-63`, Lab 34, ADR-0032)

Picked up the next `ROADMAP.md` Phase 4 line. The question left open at the end of `KAV-62` was how the
gate should treat the backup image, which staging cannot exercise. Looking at the chart answered it:
**prod does not run the backup image either** (the nightly backup job is off until the dump bucket
credentials exist; prod's HelmRelease carries four tags, not five). I had said the opposite in the previous
session. So the gate pins only the four images staging tests, and backup gets its own decision when it is
switched on in prod. ADR-0031 and the roadmap were corrected.

Built `scripts/release/promote.py` (28 tests) and `.github/workflows/promote.yml`. A person dispatches it
with a tag. The `gate` job asks: is the tag on `passed-staging.json`; do the digests ECR holds *now* equal the
recorded ones (a tag deleted and re-pushed would still match by name); is the tag's commit ahead of prod's;
is every `uat` story in the release (the `KAV-n` keys in commit subjects between prod's commit and the tag's)
*Ready for Prod* or *Done* in Jira. If it cannot decide, it refuses. Then `propose` opens a pull request
pinning prod, with the evidence in the description. Merging is the go/no-go.

The second half is `promotion-guard`, a CI job (now the eleventh required check). It fails any pull request
that changes prod's image tags to one that was not on the record *on the base branch*, so a hand edit cannot
skip the workflow and a change cannot add its own proof.

Decisions made with Roshan: Jira is read by CI through repository secrets (chosen over a repo-held sign-off
file and over a laptop-only check), and the token is a new **read-only scoped** one, not the full-access one in
`.env`. Roshan created the token and set the three secrets himself; no value was shown to the assistant.

**Proven live.** `promote.yml` with `sha-2459417`: four PASS and PR #80 opened (left unmerged on purpose:
merging changes what prod pulls next time it is up, including a database migration). With `sha-ffb436b`
(prod's current tag, never on the record): refused. The `uat` question tried against real Jira: `KAV-44`
(`uat`, *In Staging*) refused. `promotion-guard` passed a real promotion and failed a hand edit to
`sha-deadbee`.

**What went wrong.** The admin-console "API keys" page was the wrong place for a Jira token (only `:admin`
scopes); the personal token page under `id.atlassian.com` is the right one. A scoped token needs the
`api.atlassian.com/ex/jira/<cloud id>` address, not the site address copied from `.env`. And a script edit of
mine turned `\n` into real line breaks in the pull-request text, caught by the build, not by a reader.

## An unrelated red CI, and a dated exception (`KAV-64`, ADR-0033)

done under pressure; it can be its own story.

how a known-good earlier tag is allowed back past the guard.

## `rollback.yml`, the way back, and a finding about migrations (`KAV-66`, Lab 35, ADR-0034)

The guard from `KAV-63` blocks any tag that never passed staging, so the version prod ran before
(`sha-ffb436b`) could not be put back. Built `scripts/release/rollback.py` (28 tests) and
`.github/workflows/rollback.yml`: a person dispatches it with a tag and a reason; the gate asks whether prod
has run the tag before or it passed staging, whether it is an ancestor of prod's, whether its four images still
exist in ECR, and whether going back crosses a database migration; then a pull request re-pins prod.
Deliberately **no Jira**: an emergency exit must not wait on Atlassian. `promotion-guard` now also accepts a tag
prod has pinned at an earlier commit on the base branch (`prod_history_tags`).

Live: refused across the migration, passed with `accept_migrations`, opened PR #86 in 30 s, all 11 checks green
(closed unmerged); `sha-deadbee` refused.

**The finding.** Rehearsed on staging, a rollback across migration `a1c4f9b0e3d2` did not run old code on a new
schema; it never got that far. Every upgrade runs `alembic upgrade head` from the gateway image, the older image
does not know the newer revision (`Can't locate revision`), Helm failed four times and Flux put the newer release
back by itself. Services stayed up; the rollback just did not happen. After undoing the migration with the newer
image (`alembic downgrade`), the same rollback worked: **merge to healthy about 80 s** (Flux's once-a-minute check
is 55 s of that). `accept_migrations` therefore means "the migration was undone", and
`docs/runbooks/rollback-prod.md` has the steps. Cost: staging up 1 h 45 min, about $0.08, then destroyed.

**What went wrong.** I had guessed the wrong failure mode for a rollback across a migration; Flux reverted my
`kubectl patch` of its source because Git said otherwise; my stopwatch script was fooled by pods left from the
failed run (read the cluster's own timestamps instead). Two permission checks stopped me (a merge, and editing
staging's database); both were put to Roshan, who approved the database one.

**Open.** Migrations that are not backward-compatible make every rollback a database operation; making them
expand/migrate/contract (ADR-0004) is the real fix. KAV-65 (OPA, 2026-10-23) is still due. Prod is still parked,
pinned on `main` to `sha-2459417`.
