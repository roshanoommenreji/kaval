# 2026-10-11

## Prometheus as a second signal source (KAV-75, ADR-0040, Lab 43)

**What.** Built the second real signal source and closed Phase 3. A small Prometheus in the Helm chart
(`prometheus.enabled`, on only in `local`) scrapes each node's container measurements, and
`kaval_collector.prometheus` is a separate poller Deployment that asks it which containers are above 90% of
their memory limit and writes `container_memory_near_limit` signals, in the shape the agent and the golden evals
already use. Proven live on the dev server's k3d cluster: a container held at 88% wrote nothing, at 94% it wrote a
signal, and the agent opened `memory_pressure:k8s:kaval-demo/memhog` by itself.

**Why these choices.** Poll rather than wait for pushed alerts, because the full alerting bundle (about 1 GB or
more) does not fit a 4 GB node that also runs a model; Alertmanager stays a later, separate source. The ratio is
worked out in Python, not PromQL, so a limit of 0 (no limit) cannot become an infinite ratio and the threshold is a
unit test. Renew a signal every 5 minutes while a container stays high, because a level has no `count` and the
15-minute quiet window would otherwise close the incident under a container still at its limit. Standard-library
HTTP, so the collector image gained no dependency. The poller has no Kubernetes token at all; only Prometheus has
cluster-wide read, on `nodes` and `nodes/metrics`, the first ClusterRole in the chart.

**What went wrong, and what was learned.**
- The first test container landed at 88% of its limit, under the 90% line. Nothing was written, which turned out
  to be the useful proof of the "no signal" half.
- The dev cluster's stored Postgres secret predated the 2026-10-06 database-server change, so the migration
  waited forever on an empty host name. A stale local cluster, not a chart bug; fixed by patching the secret and
  recorded in Lab 43.
- I guessed the kubelet certificate would need `insecure_skip_verify`. Trying verification first showed it was
  unnecessary on k3d, so verified TLS is the default.
- Prometheus was budgeted at ~400 MB. Measured: 33 MiB (poller 45 MiB), on one node with 96 series. Small, but one
  cluster for a short time, so staging gets the real re-measurement before prod turns it on.

**Open.** Staging and prod do not run Prometheus yet. One rule only (memory near limit). Nothing raises "Prometheus
is down" as an incident of its own; the poller logs it every pass. Cost: about $0.10 for the dev-server session.

## Phase 5 starts: service levels, and recording whether a fix held (KAV-77, ADR-0041, Lab 44)

**What.** Agreed the Phase 5 plan with Roshan (own small chaos jobs rather than Chaos Mesh; "handled end to end" means the right outcome per type, which for disk and slowness is an alert with no automated action; measuring first; no chaos on prod) and opened seven Jira stories, KAV-77 to KAV-83. Slice 1: wrote the service levels down, then built the missing end of the measurement. The `outcome` table had existed since the first migration and nothing ever wrote it. `kaval_executor.verify` now judges each fix five minutes after it ran (silence from the detectors means it held), flags a regression if the same fingerprint returns within two hours, and stores wall-clock time to restore. `make mttr` splits that into detect, diagnose, human, queue and execute, and prints median, p90 and worst for machine time and wall-clock separately. The stale `make verify-outcome` target (pointing at a script that never existed) is gone.

**Why.** A chaos run needs a finish line. Without a recorded outcome there is no recovery time to chart, and "Kaval fixes problems" stays a claim.

**Found while doing it.**
- Before building, I read the code against the plan and found four things the roadmap had assumed: nothing wrote `outcome`; the executor knows one fix only (`restart_pod`); no service exposes `/metrics`; disk and latency have no signal source. These shaped the seven slices.
- Live on the dev server: `hoga` (a bare pod) was restarted and stayed fixed, 209 s; `hogb` (a Deployment) was restarted and its replacement filled up again, so it was recorded as not resolved. A restart does not cure a container that is too small, which is the case for the memory-limit fix in `KAV-79`.
- The first live report printed `detect 0s`. `opened_at` is the first signal's time, not when the row was written. Unit tests had passed because their fixtures set both equal; only live data showed it.
- `k3d image import` of a rebuilt `:dev` image printed success and changed nothing. Importing with `ctr` directly worked.

**Open.** Not yet proven on staging, where the executor's database role is separate and the new read grants (`db-roles.sql`) are real. The objectives are provisional until the first game day. Nothing alerts if the verifier stops (`KAV-78`). Cost: about $0.10 for the dev-server session.

## Phase 5 slice 2: watching the watcher (KAV-78, ADR-0042, ADR-0043, Lab 45)

**What.** Every Kaval service now shows a small health page on port 9100 (when its last pass finished, how
often one should, how many failed, its real memory). Prometheus, now switched on in staging's values, reads
them by plain DNS and judges them with three promtool-tested rules: a loop that stopped finishing passes, a
service that is unreachable or has no pod at all, and an always-firing watchdog. The collector's existing
Prometheus poller reads the list of firing alerts and writes signals, and raises "Prometheus is down" and
"Prometheus is not evaluating rules" itself. The gateway posts to Slack straight from those signals (a new
insert-only `notification` table), and a `kaval_*` incident can never get a fix proposed. The dashboard is a
Grafana file in git. Alertmanager is recorded as not adopted (ADR-0043).

**Why.** A chaos test that says "no incident opened" proves nothing if the thing that opens incidents may
have been dead. And the alert path must not run through the parts it reports on.

**Found while doing it.**
- My own plan promised "alert becomes incident becomes Slack message". Reading the code showed Slack posts only
  proposals waiting for approval, never incidents, and that the correlator and agent are exactly what may
  have stopped. So the Slack message is written straight from the signals, which was a bigger piece than planned.
- A rule on `up == 0` is silent when a pod does not exist at all (no series). `absent()` is added, with a test.
- `promtool` found my own wrong expectation in the first run (an `absent()` alert carries the `job` label).
- A table-convention test insisted every table has `created_at`; a privacy test insisted each new text column be
  classified before it can be copied to staging. Both were right.
- Slack is not configured in staging (a second Socket Mode app would split events with prod), so the last hop
  is proven by tests and will be seen live with the production rollout.
- Real memory, read from the services themselves on k3d: 62–98 MiB each, Prometheus 89 MiB resident.

**Staging proof (same day).** Run on staging: a stalled loop (database lock), a missing pod and Prometheus down each raised the alert, signal and incident (4:38, 5:30 and 2:22 after the fault); real memory measured (services 63-105 MiB, Prometheus 80-83 MiB, node 1.92 of 4 GiB); kubelet TLS verified on k3s; KAV-77's verifier and grants proven (resolved, 152 s). The quiet check found a false alarm (watchdog absent right after a Prometheus restart), and the first fix (three misses in a row) was not enough: measured 65 s gap, so the grace is now 150 s of time. My own test also OOM-killed the agent by running a second process inside its 128 MiB container.

**Open (before staging proof).** The fault proofs (database lock, missing pod, Prometheus down) and the staging measurement
(memory, kubelet TLS, 30 quiet minutes, KAV-77's verifier and grants) had not been run. An outside "still
alive" check is deliberately left to the production rollout (`KAV-83`): production is parked most of the time and
a naive ping would alarm on every park. If the gateway is the broken service, nobody is told by Slack.

**Closed (KAV-78 Done).** After the second fix (PR #126, `WATCHDOG_GRACE` = 150 s) the quiet check passed on `sha-12b7179`: 32 minutes, Prometheus restarted twice, no new signal, no pod restarted, six targets up, only the watchdog firing, node at 1.99 GiB of 4 (51%). KAV-77's open item (verifier and grants on staging) is closed by the same session. Left open and recorded: the Slack message is seen live only with the production rollout (`KAV-83`); the outside "still alive" ping is decided there too; `KAV-76` stays In Progress until prod. Next: slice 3 (`KAV-79`), the chaos framework and the OOM experiment with a new "patch memory limit" action.

## KAV-79 — chaos framework and the memory game day (slice 3 of Phase 5)

**Built.** An executor action `increase_memory_limit` (doubles a Deployment's memory limit, never above 512 MiB,
refuses at the ceiling, with no limit set or with two limited containers; always `ask`), with its RBAC (get/patch
deployments, get replicasets, demo namespace only). A chaos runner (`kaval_executor.chaos`) under its own
ServiceAccount, a suspended CronJob, an off-by-default switch, a clock and `make chaos-stop`; absent from prod, proven
by a test that renders prod and a CI grep. `make chaos-run / -propose / -approve / -mttr / -status / -stop`. ADR-0044,
the game-day template, the `pod-oomkilled` runbook, Lab 46. Dropped from the plan: a separate `kaval-chaos` namespace
(the image-pull secret exists only in Kaval's own namespace; containment is by identity, recorded in the ADR).

**Run (staging, `sha-fafc880`).** Noticed in 81 s, an incident for the victim; the by-hand diagnosis filed (staging has
no model; the real policy engine still said `ask`); approved by Roshan; the executor raised the limit 64 to 128 Mi 12 s
after picking it up; the program stayed up; five minutes later the outcome row said `resolved`. Machine time 158 s,
wall-clock 431 s, of which the person's answer was 273 s.

**Found by running it.** (1) A second `chaos.sh run` was refused by the runner, but the script's exit switched the shared
switch off and aborted the first run: the kill switch working, by accident; fixed by refusing before touching the switch.
(2) The helper that files the diagnosis hung on an input stream that never attached. (3) A quoting bug in the busy check.
(4) Twelve minutes was too short for a person; now 20, hard limit 25 (PR #131). (5) Kaval labels an OOM kill `crashloop`:
noted for `KAV-80`. (6) The memory-pressure warning did not fire (the victim dies instantly; it catches slow growth).

**Open.** The model-written diagnosis of the same failure on the dev server (Lab 46 step 5): the 1B model may well propose
a restart, which is the wrong repair for this cause, and that is worth measuring. Peak node memory with the victim running
was not sampled (47 % before, 49 % after). A stale unapproved proposal from the aborted first attempt remains in staging
(approval expiry is `KAV-82`).
