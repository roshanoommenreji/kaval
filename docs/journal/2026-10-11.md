# 2026-10-11

## Prometheus as a second signal source (KAV-75, ADR-0040, Lab 43)

**What.** Built the second real signal source and closed Phase 3. A small Prometheus in the Helm chart
(`prometheus.enabled`, on only in `local`) scrapes each node's container measurements, and
`kaval_collector.prometheus` is a separate poller Deployment that asks it which containers are above 90% of
their memory limit and writes `container_memory_near_limit` signals, in the shape the agent and the golden evals
already use. Proven live on the dev server's k3d cluster: a container held at 88% wrote nothing, at 94% it wrote a
signal, and the agent opened `memory_pressure:k8s:kaval-demo/memhog` by itself.

**Why these choices.** Poll rather than wait for pushed alerts, because the full alerting bundle (about 1 GB or
more) does not fit a 4 GB node that also runs a model; Alertmanager stays a later, separate source. The ratio is
worked out in Python, not PromQL, so a limit of 0 (no limit) cannot become an infinite ratio and the threshold is a
unit test. Renew a signal every 5 minutes while a container stays high, because a level has no `count` and the
15-minute quiet window would otherwise close the incident under a container still at its limit. Standard-library
HTTP, so the collector image gained no dependency. The poller has no Kubernetes token at all; only Prometheus has
cluster-wide read, on `nodes` and `nodes/metrics`, the first ClusterRole in the chart.

**What went wrong, and what was learned.**
- The first test container landed at 88% of its limit, under the 90% line. Nothing was written, which turned out
  to be the useful proof of the "no signal" half.
- The dev cluster's stored Postgres secret predated the 2026-10-06 database-server change, so the migration
  waited forever on an empty host name. A stale local cluster, not a chart bug; fixed by patching the secret and
  recorded in Lab 43.
- I guessed the kubelet certificate would need `insecure_skip_verify`. Trying verification first showed it was
  unnecessary on k3d, so verified TLS is the default.
- Prometheus was budgeted at ~400 MB. Measured: 33 MiB (poller 45 MiB), on one node with 96 series. Small, but one
  cluster for a short time, so staging gets the real re-measurement before prod turns it on.

**Open.** Staging and prod do not run Prometheus yet. One rule only (memory near limit). Nothing raises "Prometheus
is down" as an incident of its own; the poller logs it every pass. Cost: about $0.10 for the dev-server session.

## Phase 5 starts: service levels, and recording whether a fix held (KAV-77, ADR-0041, Lab 44)

**What.** Agreed the Phase 5 plan with Roshan (own small chaos jobs rather than Chaos Mesh; "handled end to end" means the right outcome per type, which for disk and slowness is an alert with no automated action; measuring first; no chaos on prod) and opened seven Jira stories, KAV-77 to KAV-83. Slice 1: wrote the service levels down, then built the missing end of the measurement. The `outcome` table had existed since the first migration and nothing ever wrote it. `kaval_executor.verify` now judges each fix five minutes after it ran (silence from the detectors means it held), flags a regression if the same fingerprint returns within two hours, and stores wall-clock time to restore. `make mttr` splits that into detect, diagnose, human, queue and execute, and prints median, p90 and worst for machine time and wall-clock separately. The stale `make verify-outcome` target (pointing at a script that never existed) is gone.

**Why.** A chaos run needs a finish line. Without a recorded outcome there is no recovery time to chart, and "Kaval fixes problems" stays a claim.

**Found while doing it.**
- Before building, I read the code against the plan and found four things the roadmap had assumed: nothing wrote `outcome`; the executor knows one fix only (`restart_pod`); no service exposes `/metrics`; disk and latency have no signal source. These shaped the seven slices.
- Live on the dev server: `hoga` (a bare pod) was restarted and stayed fixed, 209 s; `hogb` (a Deployment) was restarted and its replacement filled up again, so it was recorded as not resolved. A restart does not cure a container that is too small, which is the case for the memory-limit fix in `KAV-79`.
- The first live report printed `detect 0s`. `opened_at` is the first signal's time, not when the row was written. Unit tests had passed because their fixtures set both equal; only live data showed it.
- `k3d image import` of a rebuilt `:dev` image printed success and changed nothing. Importing with `ctr` directly worked.

**Open.** Not yet proven on staging, where the executor's database role is separate and the new read grants (`db-roles.sql`) are real. The objectives are provisional until the first game day. Nothing alerts if the verifier stops (`KAV-78`). Cost: about $0.10 for the dev-server session.
