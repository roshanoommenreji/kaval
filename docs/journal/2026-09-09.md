## Found and fixed — two real bugs in files nothing had exercised yet

Installing gitleaks meant the pre-commit hook ran for the first time ever. It immediately broke,
twice, in two different ways. Neither had been caught because nothing had run the hook with
gitleaks actually present.

**1. `.gitleaks.toml` — a regex Go's engine can't compile.**
`aws-arn-with-account` used a negative lookahead, `(?!0{12})`, to exclude the placeholder account
ID inline. Gitleaks uses RE2 (via `go-re2`), which has no lookahead support at all — so the config
failed to parse and gitleaks panicked on every invocation. The hook's `if ! gitleaks ...` caught
the crash as a non-zero exit and blocked the commit — accidentally safe, but for the wrong reason:
a crash, not a scan. Fixed by dropping the lookahead and relying on the allowlist regex for
`000000000000` (already present) to clear the placeholder case — RE2-compatible, same effective
behaviour.

**2. `scripts/install-hooks.sh` — the hook called a dead command.**
The hook ran `gitleaks protect --staged`. In gitleaks 8.30.1, `protect` and `detect` are hidden
legacy aliases: they parse every flag correctly, print no error, exit 0 — and never scan anything.
`gitleaks --help` doesn't even list them; the real commands are `dir`, `git`, `stdin`. So after
fixing bug #1, the hook ran clean and reported "no leaks found" **unconditionally**, regardless of
what was staged. Confirmed by forcing specific default rules (`aws-access-token`, `github-pat`)
directly and getting zero matches even against a real staged secret. Fixed by switching to
`gitleaks git --staged`, the documented equivalent.

Both bugs would have shipped invisibly: the hook "worked" (exit 0, no error) either way. The only
way to find this was to actually stage a fake secret and watch what happened — which is exactly
what verification-before-completion means in practice, not just running `--version`.

## An honest note on the testing itself

First attempt at proving bug #2 used `AKIAIOSFODNN7EXAMPLE`, AWS's own canonical example key —
which gitleaks' default ruleset explicitly allowlists as a documented false positive. That looked
like a pass but wasn't a real test. Second attempt used sequential strings
(`1234567890abcdefghijklmnopqrstuvwxyz`), which have low Shannon entropy and get filtered by the
default rules' entropy thresholds for the same reason real scanners reject them: predictable
strings aren't secrets. Only a genuinely random-looking string proved anything. Bad test fixtures
can pass for the same reason a broken tool can pass — both say nothing happened.

**Also:** two of these test attempts used real `git commit` and left commits on `main`
(`e5a1a57`, `32c335e`) before being caught — `git reset HEAD <file>` unstages, it does not undo a
commit that already landed. Both were removed with `git reset --soft HEAD~1` before anything was
pushed. Lesson for next time: run destructive-adjacent test commands with dry-run flags or in a
throwaway branch, not against `main` directly, even for a "it'll definitely get blocked" case.
