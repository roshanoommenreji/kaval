## Fake incidents in, a real API out (`KAV-23`)

Phase 1's exit gate, for signals: a synthetic incident goes from the generator into Postgres and
back out through the gateway's API, all on the dev server.
[Lab 05](../labs/lab-05-gateway-api-and-synthetic-signals.md),
[ADR-0009](../adr/0009-gateway-api-conventions.md).

- **Built:**
  - **`services/collector/kaval_collector/synthetic.py`**: four scenarios (`oom-crashloop`,
    `exec-format`, `cost-spike`, `idle-volume`), each the burst of signals one real failure
    produces, in real payload shapes (Kubernetes `Event`, Prometheus sample, Alertmanager webhook,
    Cost Explorer row). Every row is flagged `synthetic: true` with its scenario and a `run_id`. A
    seed reproduces the content; each run still gets a fresh `run_id`. A run is one transaction.
  - **`services/collector/Dockerfile`**: arm64, non-root, core dependencies only. It runs as the
    `signals` service in `compose.yaml` (the `tools` profile, so `make dev` doesn't start it), via
    `make signals SCENARIO=… [SEED=…]`.
  - **Gateway `/v1`**: `GET /v1/signals` (filters: source, kind, target, `synthetic`, `run_id`),
    `/v1/signals/{id}`, `/v1/incidents` (`status=open|closed`), and `/v1/incidents/{id}` with the
    whole timeline. Newest first, cursor-paged, OpenAPI at `/docs`.
  - **`read_session`**: every request runs in a Postgres `READ ONLY` transaction.
  - **`services/conftest.py`**: one shared `db_session` fixture (moved out of the shared tests).
  - **ADR-0009**: the API's rules, fixed before the first client exists: `/v1`, read-only, cursor
    paging, money as strings, error codes, no auth until Phase 5.
- **Proven on the dev server:** 40 tests pass against the real database, and 28 pass with 12
  skipped without it. Signals written by `make signals` read back through the tunnel: 4 rows for an
  `exec-format` run, newest first. A bad cursor gives 400, `limit=500` gives 422, and an unknown
  incident gives 404. `/docs` lists all five routes. Both images are arm64 and run as `uid=10001`.
- **Bugs the tests caught before they shipped:**
  - `exec-format`'s ±5 s jitter on its last event could put a signal **in the future**. Jitter
    now only moves events earlier.
  - My first read-only test "passed" a write. `next(api.read_session())` let the generator be
    garbage-collected at once, which closed the read-only session, and the insert autobegan a
    normal one. The endpoints weren't affected, because FastAPI keeps the generator alive. The
    test now holds it the same way.
  - A `run_id` derived from the seed would have given two `--seed 42` runs the same id. It's now
    fresh per run.
- **A leak that wasn't in the code: 42 open Session Manager sessions.** Mid-verification, Docker
  started failing with `banner exchange` timeouts and a spurious `client version 1.48 is too new`.
  The laptop was clean. On the server (inspected with `ssm send-command`, no SSH needed) there were
  **35 established SSH connections and 35 session workers.**
  - **Cause:** through SSM, sshd's peer is the local session worker, which stays up after the
    laptop's ssh exits. Each `docker --context` connection therefore lingers for SSM's 20-minute
    idle timeout, and Compose opens ~7 per command.
  - **Cost side effect:** the idle stop counts those dead connections as "someone is working".
  - **Fix:** `ClientAliveInterval 30` / `ClientAliveCountMax 3` in
    `/etc/ssh/sshd_config.d/10-kaval-keepalive.conf`, added to the devbox's `user_data.sh.tftpl`
    and applied to the running server by `send-command`. The module ignores `user_data` changes,
    so Terraform plans no replacement. **Measured after the fix:** 14 connections dropped to 0
    within 2 minutes. The stale sessions were terminated by hand.
- **A second connection bug: `make dev` hung silently after a cold start.** Session Manager's
  `Online` can still be the status from before the stop, so `devbox-up` said ready too soon. The
  server's SSH log showed Docker's connection never arrived. `ssh` timed out, but the SSM plugin
  it left behind held the pipe, so `compose` waited forever with no error. It wasn't the new
  keepalive: nothing had connected for it to drop. `devbox-up` now ends with a real SSH login,
  retried for up to 2 minutes. Verified cold: stopped → `make dev` → healthy in 102 s.
- **Found on the way:**
  - **CPU credits cost money in unlimited mode.** The dev server's credit balance hit 0. In the
    default `unlimited` mode that means billing, not throttling: 7.4 surplus credits yesterday
    (~$0.005), and about the same today. Priced from the Price List API ($0.04 per vCPU-hour for
    T4g) and added to `budget-plan.md`, worst case $0.064/hr. It stays unlimited, because standard
    mode throttles inference to 20% CPU.
  - **`httpx2` is the real successor**, so the open thread is closed. It's on PyPI, written by Tom
    Christie (httpx's author) and maintained by Pydantic, and Starlette's test client imports it.
    The `dev` extra now uses it, and the deprecation warning is gone. The gateway's runtime
    `httpx` is unchanged.
  - Twelve database tests took **2 minutes to skip** with the server stopped: on Windows, a connect
    to a closed `localhost` port takes ~10 s. The probe is now a session-scoped fixture, 12 s total.
  - Two Python edit scripts read files with Windows' default `cp1252` and wrote UTF-8, which
    double-encoded `—` and `·` in two files. Repaired before commit, and every edit script now
    passes `encoding="utf-8"`.
  - `make build` pointed each image at its own folder as the build context, which can't work
    (images need `services/shared` and `pyproject.toml`). It now uses the root context and the
    real Dockerfiles, and lists only services that have code.
  - Another `curl` call was blocked by a local hook, so the live API checks use Python's `urllib`.
- **Cost:** about 1½ hours of dev-server time across four starts (~4 cents) plus ~1 cent of CPU
  credits. No change to the monthly projection.

## Merges go through pull requests from `KAV-24` on: a rule, not yet enforced

Planning `KAV-24` (CI) raised what makes a check a *gate*: `main` should only accept a pull
request whose checks are green. GitHub Free offers neither branch protection nor rulesets on
private repositories (checked in GitHub's docs today), so enforcing it would mean GitHub Pro at
~$4/month. Roshan chose to **keep it a written rule** until v1: push the branch, `gh pr create`,
and merge only on green. Recorded in `docs/contributing.md` and `CLAUDE.md`. Turning on required
status checks is a Phase 9 task, free once the repo is public.

Also settled for `KAV-24`'s scope (to be written into the story when it starts):
- a real Postgres service in CI, so the 12 database tests run there instead of skipping;
- `alembic upgrade head` + `alembic check`;
- a dependency lockfile;
- native `ubuntu-24.04-arm` runners (available to private repos since January 2026);
- least-privilege workflow permissions and SHA-pinned actions;
- Dependabot;
- `terraform fmt` / `validate`.

SBOM, signing and deploys stay in Phase 4's `release.yml`.

## CI on every pull request (`KAV-24`)

`.github/workflows/ci.yml` now runs on every PR and on `main`: lint, pytest against a real
`pgvector/pgvector:pg16` service container, migrations up → check → down → up, gitleaks over the
full history, `terraform fmt`/`validate`, and both images built natively on `ubuntu-24.04-arm`,
checked for arm64 + uid 10001 + importable code, then scanned by Trivy. It builds, never pushes.
Supply-chain rules: `contents: read` token, every action pinned to a commit SHA, gitleaks and Trivy
binaries checked against sha256 sums in the file, base images pinned by digest, and a new
`uv.lock` (46 packages, hashed) that CI, `make sync` and both images install from. Dependabot
proposes weekly grouped updates; vulnerability alerts and Dependabot security updates were switched
on through the API (`enabled: true`), so a security fix arrives as a PR as soon as an advisory
lands. Decisions in [ADR-0010](../adr/0010-ci-pipeline-and-supply-chain.md),
reproduction in [Lab 06](../labs/lab-06-ci-pipeline.md). PR #1 is the first change merged under
the green-PR rule.

**Verified.** Second run all green, 68 s wall-clock, 6 billable minutes. The test job ran
**40 passed, 0 skipped**, the first time every database test has run somewhere other than the
dev server. `uv lock --check` refuses an unlocked `pyproject.toml` edit.

**What went wrong, in order:**

- **SQLAlchemy 2.1.** Creating the lock resolved 2.1.1 (the laptop had 2.0.54), which removed the
  mypy plugin `pyproject.toml` still loaded. Plugin dropped, since the models use `Mapped[]`, and two
  `Select[...]` annotations updated. This is exactly the drift a lock exists to expose.
- **Pre-commit hook refused the commit** over "a 12-digit number": digit runs inside sha256
  hashes in `uv.lock`. It also tried to prompt via `/dev/tty`, which a non-interactive shell
  can't answer, so the commit silently didn't happen and the first push sent an unchanged branch.
  The check now ignores digit runs inside hex strings; real ARN/`account_id` forms still trip it.
- **First CI run, 3 red jobs.** Terraform: the lock files held only Windows provider checksums →
  `terraform providers lock` for windows/linux amd64+arm64/darwin arm64. Both images: Trivy found
  CVE-2026-23949 (`jaraco.context`) and CVE-2026-24049 (`wheel`), both HIGH, in copies vendored by the
  base image's `setuptools` → the runtime stage now uninstalls setuptools, wheel and pip.
- **Trivy's own action was the March 2026 supply-chain incident** (CVE-2026-33634, 76 of 77 tags
  re-pointed). Verified before choosing it, and it's why the binary is fetched directly and
  checksum-checked rather than used through the action.

## Commit convention enforced; Jira linked to GitHub, without smart-commit commands (`KAV-25`)

**What:** `scripts/dev/check_commits.py` holds the commit rules once. Both callers use it:
- the `commit-msg` hook (installed by `install-hooks.sh`) refuses a bad message before the commit exists;
- CI's lint job checks every commit a PR adds.

The rules: a conventional type, a subject of at most 100 characters, a KAV key on story branches,
no smart-commit commands, and no `fixup!` commits in a PR. It has 21 tests. PR #3 went through it:
"2 commit(s) follow the convention", all 6 jobs green, 61 tests passed. The decision is
[ADR-0011](../adr/0011-commit-convention-and-jira-link.md), and the walkthrough is Lab 07.

**The finding that changed the plan:** Jira runs smart-commit commands (`#comment`, `#time`,
`#done`) only when the commit's author email exactly matches a Jira user. Commits here use the
GitHub noreply address, and Jira uses Roshan's personal address. Roshan chose **link only**:
- keep the noreply address, so no personal email enters the history before the repo goes public;
- link by key through the GitHub for Jira app;
- move status with `jira-sync.py`.

The checker refuses `#` commands, because a `#done` that silently does nothing is worse than none.

**Also:**
- Semantic versioning moves to Phase 4 `release.yml`; a version needs a release to tag.
- Every doc that promised smart commits now says what actually links issues. That covered the
  architecture notes, the release-engineering page and the release-record template.
- Only one commit in the whole history fails the check: Phase 0's `style: terraform fmt`. CI
  checks only a PR's own commits, so history isn't re-litigated.
