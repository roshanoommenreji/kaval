# 2026-11-06

## A new scanner finding failed every image check (`KAV-129`)

At about midnight, the image checks of pull request #317 (documentation only) failed on all five images. The cause was outside that change: Trivy reported two HIGH findings in the Debian 12 base image, `apt` and `libapt-pkg6.0` 2.6.1, fixed in 2.6.2 (CVE-2026-109518), published after `main`'s last green run on 2026-11-04. Until it is fixed, every pull request fails its image checks and no release can build.

The repo's own pattern for this is one `--only-upgrade` layer per finding (`libpcre2-8-0`, perl, `libssl3` before it), not an entry in `.github/trivy-ignore.yaml`, which [ADR-0033](../adr/0033-dated-trivy-exception-for-the-bundled-opa-binary.md) keeps for the last resort and which stays empty. The fix is the same layer for `apt` and `libapt-pkg6.0` in the four service Dockerfiles and the backup image's existing line. Checked first, outside CI: on both pinned base digests `apt-get install --only-upgrade apt libapt-pkg6.0` takes both packages from 2.6.1 to 2.6.2.

The images change, so the new build goes through staging before production like any other (the next staging session); production's pin does not move. Jira `KAV-129` (security, 1 point).

## #318 merged at 20:51 IST, and `main` was red anyway: a second finding, in a Python library

Roshan merged #318 (all 11 checks had been green on the pull request about twenty hours earlier). The checks on `main` after the merge failed on the collector and executor images, and so did the release workflow, so no new images were published. The apt finding was gone (the other three images passed). A different one had been published in the meantime: `oauthlib` 4.0.0, a Python library in the collector and executor images, has a new HIGH finding, CVE-2026-49272, fixed in 4.0.1. The dependency bot had already opened the fix as #319 (one file, `uv.lock`, 4.0.0 to 4.0.1). Its checks had failed only because they ran before #318 merged, so the bot was asked to rebase it. `uv.lock` is one of the paths that start the release workflow, so merging #319 should build the new images and open the usual staging-pin pull request. Not a defect, but worth knowing: a scanner that fails on any newly published fixable HIGH finding turns `main` red whenever one appears, with no change of ours; the answer is a quick upgrade, never a silent exception.
