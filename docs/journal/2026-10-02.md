# 2026-10-02

## Real Kubernetes events as signals (`KAV-48`, ADR-0022)

Every signal Kaval has reacted to, through `KAV-47`, was typed in by hand — a fake incident
from `kaval_collector.synthetic`, or a one-off row written directly into Postgres for a demo.
This story gives the collector a second, real source: `kaval_collector.k8s_events` polls
Kubernetes' own Event API (`--every 15`, the same loop shape the agent and executor already
use) and writes the real failures it sees as `signal` rows, in the identical shape
`synthetic.py` already committed to in Phase 1 — `kaval_agent.correlate.cause_of()` needed
zero changes to handle them.

**The part worth getting right, and already named as a trap in `docs/learn/
phase-3-kubernetes-local.md` before this was built:** Kubernetes doesn't emit a new Event
object per occurrence — it bumps the existing object's `count`. Writing a signal on every poll
regardless would flood the table with duplicates; writing exactly one signal per event object,
ever, would let a hour-long crash loop produce one signal and let the correlator close the
incident while the real problem continues. `poll()` does neither: it carries each event's own
`uid` in the signal's `value`, looks up the last signal already written for that `uid`, and
writes a new one only when the real count has grown.

**RBAC follows `KAV-47`'s pattern exactly**, now a repeated rule rather than a one-off: the
collector's ServiceAccount lives in the release's own namespace; its Role (`list`, `watch` on
`events` — not even `get`, since nothing here fetches one named event) is granted in
`kaval-demo` only. Scoped to `Pod`-involved events, one namespace, `Warning` type — a `Node`-
or `Deployment`-involved event doesn't fit the `namespace/workload` target shape
`kaval_agent.correlate.subject()` already expects, so those are an honest, documented gap, not
silently mishandled.

Infra story (ADR-0012: infra doesn't need UAT, same as `KAV-46`) — `make lint`/`make test`
green, 8 new tests against a fake `CoreV1Api` stand-in (the same "fake the client, not the
cluster" shape `kaval_executor`'s tests already use).

## Live verification, once the dev server actually started

`make devbox-up` hit `InsufficientInstanceCapacity` several times before succeeding — the same
known transient AWS issue earlier entries already flag. Once up, the k3d cluster from Lab 16
had survived 11 hours untouched, zero restarts. Full live run: RBAC proven (`yes, no, no`,
same shape as `KAV-47`'s checks); a real `busybox` pod set to crash immediately produced real
`BackOff` events within seconds; the deployed collector picked them up unattended, writing
signals with climbing counts (2 → 6) as the pod kept restarting; the deployed agent opened a
real `crashloop:k8s:kaval-demo/crashy` incident from them, on its own, no prompting; the
gateway's own read API read back the complete chain. Also caught and fixed before merging: the
chart actually renders 17 resources, not the 18 the first draft claimed — an uncounted
arithmetic slip, not a real discrepancy. `KAV-48` ticked and moved to Done. ROADMAP Phase 3:
5/10.
