# 2026-10-02

## Real Kubernetes events as signals (`KAV-48`, ADR-0022)

Every signal Kaval has reacted to, through `KAV-47`, was typed in by hand — a fake incident
from `kaval_collector.synthetic`, or a one-off row written directly into Postgres for a demo.
This story gives the collector a second, real source: `kaval_collector.k8s_events` polls
Kubernetes' own Event API (`--every 15`, the same loop shape the agent and executor already
use) and writes the real failures it sees as `signal` rows, in the identical shape
`synthetic.py` already committed to in Phase 1 — `kaval_agent.correlate.cause_of()` needed
zero changes to handle them.

**The part worth getting right, and already named as a trap in `docs/learn/
phase-3-kubernetes-local.md` before this was built:** Kubernetes doesn't emit a new Event
object per occurrence — it bumps the existing object's `count`. Writing a signal on every poll
regardless would flood the table with duplicates; writing exactly one signal per event object,
ever, would let a hour-long crash loop produce one signal and let the correlator close the
incident while the real problem continues. `poll()` does neither: it carries each event's own
`uid` in the signal's `value`, looks up the last signal already written for that `uid`, and
writes a new one only when the real count has grown.

**RBAC follows `KAV-47`'s pattern exactly**, now a repeated rule rather than a one-off: the
collector's ServiceAccount lives in the release's own namespace; its Role (`list`, `watch` on
`events` — not even `get`, since nothing here fetches one named event) is granted in
`kaval-demo` only. Scoped to `Pod`-involved events, one namespace, `Warning` type — a `Node`-
or `Deployment`-involved event doesn't fit the `namespace/workload` target shape
`kaval_agent.correlate.subject()` already expects, so those are an honest, documented gap, not
silently mishandled.

Infra story (ADR-0012: infra doesn't need UAT, same as `KAV-46`) — `make lint`/`make test`
green, 8 new tests against a fake `CoreV1Api` stand-in (the same "fake the client, not the
cluster" shape `kaval_executor`'s tests already use).

## Live verification, once the dev server actually started

`make devbox-up` hit `InsufficientInstanceCapacity` several times before succeeding — the same
known transient AWS issue earlier entries already flag. Once up, the k3d cluster from Lab 16
had survived 11 hours untouched, zero restarts. Full live run: RBAC proven (`yes, no, no`,
same shape as `KAV-47`'s checks); a real `busybox` pod set to crash immediately produced real
`BackOff` events within seconds; the deployed collector picked them up unattended, writing
signals with climbing counts (2 → 6) as the pod kept restarting; the deployed agent opened a
real `crashloop:k8s:kaval-demo/crashy` incident from them, on its own, no prompting; the
gateway's own read API read back the complete chain. Also caught and fixed before merging: the
chart actually renders 17 resources, not the 18 the first draft claimed — an uncounted
arithmetic slip, not a real discrepancy. `KAV-48` ticked and moved to Done. ROADMAP Phase 3:
5/10.

## Promotion mechanics rehearsed on k3d (`KAV-49`, ADR-0023)

`ADR-0004` already decided what the real staging environment is — a second AWS node, built in
Phase 4. That doesn't exist yet, so this story rehearses the *mechanics* on the one cluster
that does: `kaval-staging` and `kaval-prod`, two more Helm releases, in the same k3d cluster
`kaval-local` already runs in, each in its own namespace, using new, real
`deploy/environments/staging/values.yaml` and `prod/values.yaml` files.

Built each image once, tagged by commit SHA (not the floating `:dev` tag every other lab has
used), deployed to staging, then promoted the identical tag to prod unchanged — confirmed
byte-for-byte via the running pod's `imageID`, not just matching tag text.

**The first break attempt found a better finding than the one it was looking for.** A bad
`gateway` tag never reached a running pod: `migrate-job.yaml`'s pre-upgrade hook also runs from
`gateway.image`, so it failed to pull first and blocked the whole release before touching
anything live. Switched the drill to `executor.image` instead, which has no such hook — that
one actually broke (`ErrImagePull`), though Kubernetes' own rolling-update default kept the old
executor pod running the whole time, so the real "outage" was a stuck release, not downtime.
`helm rollback`, timed: **1.49 seconds** — this project's first measured time-to-restore.

Infra story, no UAT (doesn't change what an operator sees or decides). Both rehearsal releases
torn down after capturing the evidence; `kaval-local` untouched throughout. ROADMAP Phase 3:
8/10 (staging/prod split, promotion rehearsal, and the timed rollback drill all close in one
story — they were one piece of work, not three).

## Phase 4 begins: prod's landing — network, ECR, IAM, a real k3s node (`KAV-50`, ADR-0024)

Checked in again after `KAV-49`: both open Phase 2 items are externally blocked on Roshan's own
actions (`KAV-27` needs a Jev key, gated by `KAV-28`'s waitlist signup; `KAV-44` needs AWS
Marketplace Pay by Invoice), and Phase 3's leftovers wait on Phase 4 hardware. Asked what to do;
Roshan chose to start Phase 4 rather than wait.

Scoped the first story narrowly: the landing itself, not the whole phase. Built real Terraform —
a dedicated VPC (no NAT Gateway), four immutable-tag ECR repos, the node's own IAM role (SSM +
scoped ECR pull — deliberately **not** a per-service agent/executor AWS role; that split is
already live at the Kubernetes RBAC layer since `KAV-47`), and a spot `t4g.medium` in a size-1
ASG running k3s installed from a checksum-verified binary, not the unauthenticated `curl | sh`
installer.

Two real errors on the first `terraform apply`, both AWS rejecting the plan, not a design
mistake: an ASG-managed launch template can't request *persistent* spot (only *one-time* — the
ASG itself owns replacement), and `ap-south-1a` had no `t4g.medium` spot capacity at all (AWS's
own error pointed at `-1b`/`-1c`; moved the default there). Fixed both, reapplied clean.

Live verification, the real way — SSH through an SSM port-forward tunnel, no inbound port open
anywhere: `kubectl get nodes` reports `Ready`, `v1.37.1+k3s1`, `arm64`. The node authenticates to
ECR with its own assumed role, no static key. One genuine debugging finding along the way: a bare
`aws ssm send-command` runs as root with **no `$HOME` set**, so `kubectl` can't resolve
`~/.kube/config` even after copying it there — fixed by pointing `KUBECONFIG` at k3s's own
kubeconfig file directly via `/etc/environment`, which login shells (SSH, `sudo -i`) do read.

Armed the Phase-0-built hard-stop Lambda for real (`hard_stop_dry_run = false`, wired to the live
ASG) in the same change, then proved it rather than trusting the wiring: a manual test invocation
scaled `kaval-prod` from 1 to 0 exactly as designed. It also stopped the dev server in the same
pass — the Lambda is deliberately blunt, stopping every `Project=kaval` instance outside an ASG,
not just the one under test. Expected, not a bug, but a real side effect worth knowing before
running that test again; `make devbox-up` brings it back. That same invocation doubled as the
session's pause, since `make up`/`make down` for prod don't exist yet.

Cost verified live against the real AWS Price List / spot history at apply time, not the ~7-month
estimate: ~$13/month while running (spot ~$8, EBS ~$1.82, public IPv4 ~$3.65) — a touch under
ADR-0004's original ~$14/month Phase 4 estimate.

One PR, infra-only story (no Python changed), `terraform fmt`/`validate` clean, no UAT (not an
operator-facing change). ROADMAP Phase 4: 2/18 — Flux, the Cloudflare Tunnel, the database server
(`KAV-32`), and `make up`/`make down` are each their own next story, deliberately not bundled in.

## Flux GitOps reconciliation, and the ECR bootstrap it needed (`KAV-51`, ADR-0025)

Picked up straight on from `KAV-50`, closing the gap its own header comment named: nothing was
GitOps-managed yet, so a reclamation produced a fresh, empty k3s. Doing that honestly meant
solving two problems first — nothing was in ECR yet, and an ECR registry hostname embeds the
AWS account ID, which can't be committed (CLAUDE.md).

**The registry and the ECR credential never reach Git.** Both are derived from the node's own
instance identity at reconcile time — a `ConfigMap` and a `Secret` the node's cloud-init
creates, merged into the chart via a new `global.imageRegistry`/`global.imagePullSecretName`
and Flux's own `valuesFrom`/`targetPath`. A systemd timer refreshes both every 6h, since this
node has no EKS-style credential provider (that's Phase 7/8 IRSA territory, per ADR-0024's
existing scoping decision) and ECR tokens expire every 12h.

**Flux installs via plain `flux install`, not `flux bootstrap`** — the latter commits a
manifest straight to `main` and would bypass the PR-required branch protection this repo has
had since `KAV-24`. Cloud-init applies the `GitRepository`/`HelmRelease` directly from
`deploy/gitops/prod/`, authored through a normal PR like everything else.

**Three real findings, in order.** (1) A second apply-time spot-capacity failure — this time
in `ap-south-1b`, the AZ Lab 19 had just pinned after `-1a` failed the day before — made clear
one pinned AZ isn't durable for this instance size right now; `infra/modules/network` now
spans all three `ap-south-1` AZs, letting the ASG launch wherever capacity actually exists. The
very next apply then hit a transient CIDR-conflict (the old single subnet's destroy and the new
same-CIDR subnet's create raced); a plain retry cleared it. (2) Pushing the first four images to
ECR (one-time manual bootstrap — `release.yml` automates this later) — three pushed cleanly over
the remote `kaval-devbox` buildx context, the fourth hit a flaky SSM session mid-push; building
it locally under QEMU instead worked first try. (3) The first live verification failed with a
plain 404: `deploy/gitops/prod/` existed only in the local working tree, and Flux's
`GitRepository` pulls from the *published* `main`. The fix was the normal one — branch, PR, CI
green, merge — then re-run the one idempotent bootstrap script by hand, no reboot needed.

**Verified live:** `kubectl get nodes` `Ready` within ~3 minutes of boot; all four Flux
controllers `Running`; after the merge, `GitRepository`/`HelmRelease` both `Ready` and the real
Kaval services running in `kaval-prod` — on the real Graviton node, for the first time.

One PR, no cost change (~$13/month, unchanged). ROADMAP Phase 4: 4/18 — the Cloudflare Tunnel,
the database server, and `make up`/`make down` are each their own next story.
