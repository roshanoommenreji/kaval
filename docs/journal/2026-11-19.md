## A secret rotation rehearsed on staging (`KAV-159`)

On his typed gos (`go staging rotation`, `apply rotation`), staging was built (about 5 minutes) and three secrets were replaced on it: the approver token, the gateway's database password and the database's admin password. A new checker, `make rotation-check` (`scripts/ops/rotation_check.py`, 15 tests), asks the servers whether each new value is stored, whether the cluster holds it, and whether the gateway or the database believes it, printing only words and numbers.

- **Before:** 7 of 7. **After the Terraform apply, before anything caught up:** 10 of 10: the old token still worked, the new one did not, the database still took the old passwords and refused the new ones.
- **The trap:** Postgres reads its admin password only when its disk is first made, so the new admin value had to be set inside the database (`ALTER ROLE`, value never printed) before the app server's start-up script was re-run. The check proved the database refused the new value until then.
- **Then:** start-up script re-run (no reboot), second permissions pass, gateway restarted. **After:** 13 of 13: new accepted, old refused, made-up token refused. Staging smoke test: all seven real checks passed (its "tagged release" line fails on an untagged build; unrelated).
- **A slip, caught on the first run:** the checker glued a status code to the next marker (curl prints no newline). Fixed and tested.
- **Corrected:** ADR-0100 said a password change needs the servers restarted; it does not (amendment). The runbook the Terraform notes pointed to did not exist; [it does now](../runbooks/secret-rotation.md).
- **Teardown and cost:** `go staging down` at 18:28 IST; 93 destroyed, sweep clean. Staging was up about three hours, so about 14 cents (an estimate), most of it waiting between steps.
- **Not rehearsed, said plainly:** agent, executor, collector and monitor passwords; the Slack and Atlassian tokens. Production is unchanged.
