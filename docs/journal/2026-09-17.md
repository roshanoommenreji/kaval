## Three real bugs, all caught by actually running the thing rather than trusting it

1. **PostgreSQL `ENUM` types don't get dropped by `DROP TABLE`.** Alembic's autogenerated
   `downgrade()` drops every table but leaves the six named enum types
   (`severity`/`risk_level`/`blast_radius`/`policy_class`/`verdict`/`execution_status`) behind, so
   a `downgrade → upgrade` round-trip failed with `type "severity" already exists`. Only surfaces
   if the downgrade path is actually exercised — which is exactly why it was. Fixed by explicitly
   dropping each enum type at the end of `downgrade()`.
2. **The integration test fixture was fighting Alembic for schema ownership.** It originally called
   `Base.metadata.create_all`/`drop_all` around every test, which — when run interleaved with the
   migration verification above — dropped tables Alembic was about to downgrade, producing `table
   "execution" does not exist`. Fixed properly: the fixture now binds the test session to a
   connection whose outer transaction is rolled back at teardown
   (`join_transaction_mode="create_savepoint"`), so tests never touch schema and never really
   commit, regardless of how many times the test itself calls `session.commit()`. Verified by
   checking the row count directly in the database after a test run, not by trusting the assertion.
3. **An unreachable Postgres hung the test suite for over four minutes** instead of failing fast —
   found by deliberately pointing the suite at a closed port to confirm the "skip if no DB" path
   actually works. `create_engine(..., connect_args={"connect_timeout": 5})` brought that down to
   about 12 seconds. Matters beyond tests: without it, any service would hang for minutes against a
   genuinely down database instead of failing fast enough for an orchestrator to restart it.
