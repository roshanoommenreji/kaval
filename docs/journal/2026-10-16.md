## KAV-87: starting the production switch-on

Roshan said "go". The route is longer than two lines: production's images (`sha-0904d5c`) predate the diagnosis
worker, so the newer build must first pass staging and be promoted. Order: record the staging pass, promote, switch
the model and worker on, bring production up (plan shown first, 2 in-place changes, 0 created or destroyed), measure.

**First step failed, and why.** `make staging-smoke` on `sha-c8e3dee` failed for two reasons that were not the build:
- Four `chaos-*` pods left over from the 2026-10-15 game days were still in the staging namespace. They count as pods
  (two showed Failed) and ran the older executor image. Deleted with Roshan's agreement (they are test leftovers).
- The node reported the gateway and agent as `sha-b36c4be`: the two builds are byte-identical (the commit changed only
  tests and scripts), and a node names an image by the first tag it pulled. The check now accepts the right bytes under
  an older name; different bytes still fail. Amendment in ADR-0031; two tests (one new, one tightened).

After both, the smoke passed (7 of 7) and the pass is recorded in `deploy/promotion/passed-staging.json`.

Lesson: a long-running staging that has had game days wants its leftovers cleared before a release check, or a rebuilt
staging. Cost so far today: staging only (about $0.045/hr, still up).
