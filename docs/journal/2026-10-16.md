## KAV-88: the confidence number now follows the evidence

Asking the 1B model to be humbler was already measured not to work (ADR-0018: the two thin cases said 0.75 to 0.95, and after
ADR-0054 the mean rose to 0.88), and sampling it several times would cost three to five minutes of the 4 GB node per
incident. So the fix is outside the model: `kaval_agent/evidence.py` limits the number that is **stored**. For an incident
about a Kubernetes workload, one observation caps it at 0.5, several of one kind at 0.7, two or more kinds leave the
model's number alone; it only lowers; cost and unused-disk incidents are not touched. It is applied in `write_proposal`
(the one place every proposal is written), so the laptop, the cluster worker and the evals all get it. The worker counts
each time it bites (`kaval_diagnosis_confidence_limited_total`) and prints "the model said 0.80" in its log line. No
migration, no new permission, no AWS cost.

Measured on the dev server, real model, one run: 20 of 20 pass (18 before). The two sparse cases store 0.50 (model said
0.95); exactly two cases were lowered; mean said 0.89, kept 0.84; right fix 8 of 8, no action 6 of 6, 0 of 14 off the
list. Honest limits written into the ADR: the two sparse cases passing is by construction (the rule is written for
them), the laptop has no `opa` so the policy fell back to `ask` in that run, and the Slack message shows the number but
not the reason (a column and a migration, left for later; KAV-85 is the open migration trouble).

Snags of my own: the first eval run failed (`make` used a Python without the project installed: put `.venv/Scripts` first
on the path), and a waiter I wrote matched the word "Error" in a harmless OPA warning and stopped early; neither touched

## KAV-88 on staging: the first real run showed the rule was too blunt

Build `sha-6603033` on staging, out-of-memory game day. The worker diagnosed by itself and the rule bit: model 0.95, stored
0.70. A read-only job listed the incident's signals: 17 of `pod_oom_killed`, no other kind. A real memory incident holds one
kind, the kill itself, which is the cause, so "one kind means thin" was wrong for it. The golden cases build three kinds, a
shape the real collector does not produce, so the dev-server run could not show it. Fix: `DIRECT_EVIDENCE` (per cause, the one
kind whose own report names it: `oom_killed`/`pod_oom_killed`, `exec_format`/`container_exited`); several of those are not
limited, one alone is still 0.5, a crash loop keeps 0.7. 12 evidence tests. `sha-6603033` is **not** promoted.

My mistake in the same run: I started the game day in the background and did not approve the fix inside staging's 15
minutes, so the runner timed out (clean: victim deleted, switch off). The diagnosis part, which is what this story needed,
had already happened. Next: pull request for the fix, new build to staging, re-run the game day with the approval done in
time, then the smoke check and promotion.
