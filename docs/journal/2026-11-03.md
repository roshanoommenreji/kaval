## `KAV-123` built: the Atlassian login never follows a redirect

Built from 22:15 IST on `fix/KAV-123-no-login-on-redirect`, tests first, after Roshan saw the plan and said "go". [ADR-0075](../adr/0075-a-redirect-is-never-followed-so-the-atlassian-login-stays-home.md), [Lab 75](../labs/lab-75-a-login-that-stays-home.md).

- **The finding, now a failing test.** Python's `urllib` passes the `Authorization` header on if a request is redirected (found on 2026-11-02 while building `KAV-122`). Written as tests first, it failed the way it should: for each of 301, 302, 303, 307 and 308 a second local server received the login, both in the Atlassian transport and in the release workflow's Jira read.
- **What changed.** A redirect is never followed, not to another address and not to the same one. `send()` raises `AtlassianRedirected` and `guard(main)` ends a script with one plain line: method, path and status, never the login and never where the answer pointed (for a write it adds that the request may already have gone through). The ticket said "followed, or returned as a status"; the plan chose a third option, a stop, because `publish-confluence.py` takes any lookup that is not a 200 to mean "that page is not there" and goes on to create it. Before the fix, a followed redirect made it try to create the space and end in a traceback.
- **The scope grew by one piece of code, shown in the ADR.** The plan said the Jira and Confluence scripts. Looking for other senders of the same login found `jira_issue()` in `scripts/release/promote.py`, which `promote.yml` runs with the real token from the repository secrets, through the same default. It follows the same rule, with its own copy of the short handler (the release scripts do not import from `scripts/tracking`). `verify` already turns a failed Jira read into "cannot decide" and exit code 2, and a gate that cannot decide refuses.
- **Found, not changed: `KAV-124`.** `scripts/ops/approve.py` sends the gateway's approver token with the same call. Checked with two local servers: a 302 from the "gateway" made it repeat the request, as a GET, to the second server, which received the token. It is not fixed here because it is a different credential in the approval flow, which is proved live on staging, so it has its own story (one point, filed). The other callers of `urlopen` send no credential.
- **Proof.** 32 new tests: 23 in `test_atlassian_http.py` (57 now) and 9 in `test_promote.py`. 28 were seen failing first, 10 of them because the second server really received the login; the other four pin what must not change (a 304, and a 200, a 404 and a 500 from the Jira read), and the 304 pin was shown able to fail by breaking a copy of the code on purpose. ruff clean, and strict mypy clean on the files `make lint` lists. Full `make test`: 1632 passed, 352 skipped, 8 xfailed (1623 before the release tests). Read-only against the real site, an issue read, the space and page lookups `publish-confluence.py` makes, `jira-sync.py show KAV-14` and the release workflow's Jira read all came back as before, none redirected.
- **At the time of writing:** the pull request was about to be opened. CI, the merge and the first real `make docs-sync` on the merged code (the last box of Lab 75) were still to come, and `KAV-123`'s criteria and its move to Done follow them. **Later the same night:** merged as #311 at 22:46 IST (all 11 checks green); the first real `make docs-sync` on the merged code ran 22:52:53 to 22:57:38 and finished normally (`DONE exit=0`, 107 pages updated, 1 created, no failure, retry or redirect); the three criteria were ticked and `KAV-123` moved to Done.
