## Done

- **Evaluated Jev** (TypeSafe AI, launched 2026-09-15): a typed-decision model that returns a
  choice, score or yes/no answer with calibrated probabilities and no text. It costs $0.042 per
  million input tokens, with output free.
- **Corrected a wrong claim along the way.** The first search turned up "$5 free credit, no
  waitlist". Checking against DataCamp and the launch coverage showed access is **waitlist-only
  with no documented free tier**. The free-credit story came from SEO sites. One of them,
  jev-agent.com, is a third-party proxy handing out keys on its own quota, and ADR-0006 bans
  sending cluster data through it.
- **Decided the role: Jev rates risk, Gemma still writes the diagnosis.** Replacing Gemma was
  rejected because Jev returns no explanation and the approver on the phone needs one.
  [ADR-0006](../adr/0006-jev-as-proposal-risk-rater.md).
- **The safety argument is the interesting part.** The policy engine's `auto` rule turns on
  `confidence > 0.9`, and a 1B model's self-reported confidence is close to meaningless. A model
  built for calibrated probabilities fixes a real weakness. But an opaque hosted model must not
  become the safety gate, so three rules apply:
  - `never` comes from the action type.
  - Jev can only make a class stricter.
  - The executor recomputes blast radius itself.
  
  The worst case of a wrong or manipulated Jev answer is one extra question to the human.
- **No code this session.** `services/agent/` is still empty and this is Phase 2 work. Changes:
  - `.env.example`: `TYPESAFE_API_KEY=` (empty), `JEV_MODEL=jev-1.13.0` (pinned), and
    `JEV_ENABLED=false`.
  - `ROADMAP.md`: a Phase 2 task, and the eval harness now compares Jev with rules-only.
  - `policy/README.md`: an "Inputs" section.
  - `architecture.toml`: a `jev` node and an `agent → jev` edge.
  - `budget-plan.md`: +$0.50/mo.
- **Jira `KAV-27`** "Jev risk rating feeding the policy engine" was created under the Phase 2
  epic `KAV-7`: To Do, 5 points, six acceptance criteria (pinned version, redaction, fallback,
  Rego tighten-only tests, cost recording, evals vs rules-only). The work was committed on
  `docs/KAV-27-jev-risk-rater` after the parallel restructure had merged, then merged `--no-ff`.

## Repository organisation (separate session, same day)

Roshan asked whether the folder was organised well enough, given how many tools the project now
touches (Jira, Confluence, the dashboard, AWS, a database, Git hooks, Claude Code). He wanted
every tool to have an obvious home, and nothing to break. The audit found the skeleton was
sound, with six specific problems, and fixed them on a branch rather than rebuilding:

- **`scripts/` split by what each script touches:** `scripts/ops/` (AWS + database),
  `scripts/tracking/` (Jira, Confluence, dashboard), `scripts/dev/` (hooks, lab scaffolding).
  All moves used `git mv`, and `git log --follow` still reaches each file's first commit.
- **Jira automation is now in the repo.** The code that created `KAV-21`–`KAV-26` had only ever
  lived in a temp folder. `scripts/tracking/jira-sync.py` (`show` / `transition` / `create`)
  replaces it, sharing auth with Confluence through a new `atlassian.py` instead of a second copy.
- **`alembic/` → `migrations/`**, and **`infra/envs/lab` → `lab-eks`**, which clears the
  long-standing naming blocker against `deploy/environments/lab-eks`.
- **README gained a "which tool lives where" table**; `.env.example` gained the Jira/Confluence
  placeholders it had always been missing; new `make migrate`, `make docs-sync`, `make jira`.
- **Branching written down** in [docs/contributing.md](../contributing.md): short-lived
  `type/KAV-<n>-slug` branches merged `--no-ff` into an always-verified `main`. There are
  deliberately **no environment branches**, because ADR-0004's build-once-promote rule means
  environments differ only by values file and digest.
- The 2026-09-17 data-model work, which had sat uncommitted on `main`, went in first on
  `feat/KAV-21-data-model`.

**Worked alongside another live session.** Midway through, the Jev edits above appeared in
three files this restructure also touched. They were kept out of the restructure commits by
staging only the path changes in those files. The edits were parked in a stash for the merge
and restored unchanged afterwards (same diff before and after). Nothing of that work was
committed or reverted.

**Found while verifying:** renaming the folder changed how ruff sorts `from alembic import`, since
the library was no longer shadowed by a local folder of the same name. Also, `make` loads `.env`
over exported shell variables, so testing `make migrate` against a throwaway database needs the
settings on the `make` command line. That's expected behaviour, not a bug. The two older
generator scripts carry 63 pre-existing ruff style warnings. They stay outside `make lint` for
now, so lint stays green.

Verified: 7/7 tests against a real throwaway Postgres, `alembic check` with no drift and a clean
downgrade/upgrade from `migrations/`, `make lint` green, `bash -n` on every shell script,
`make -n` resolving every moved path, the reinstalled pre-commit hook still refusing a fake
secret, and zero references to old paths outside dated journals.

**Then a full repository guide**, because Roshan asked for one:
[docs/repo-guide.md](../repo-guide.md). It covers every folder and file, what it does today, and
whether it's working, written but not yet run, or an empty placeholder (with the phase that fills
it). It's linked from the README, `00-start-here.md` and `CLAUDE.md`, and it's published as a new
Confluence page, *Repository Guide*. That page went out through `publish-confluence.py` like
everything else: it rendered 12 tables with no raw Markdown leaking through. Every path the
guide names was checked against the real tree. `CLAUDE.md` now says to update the guide in the
same change whenever a folder is added, moved or starts being used.
