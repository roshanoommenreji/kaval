# 2026-10-01

## KAV-44's real root cause, confirmed — and a deliberate decision not to route around it

Follow-up to yesterday's Bedrock escalation story (`KAV-44`, ADR-0019). Roshan checked the AWS
console and AWS Support directly, and the "Marketplace payment-instrument" 403 from the live test
has a real, specific cause, not a generic billing hiccup:

- **Payment Preferences** showed "Payment currency: No currency selected," locked from editing by
  an active **e-mandate** (an RBI-regulated recurring-payment authorization on the card).
- **AWS Marketplace → Manage subscriptions → Inactive subscriptions** showed exactly what
  yesterday's live calls had done: both "Claude 3 Haiku" and "Claude Haiku 4.5 (Amazon Bedrock
  Edition)" subscriptions, auto-created, then **Terminated** within the same minute — timestamped
  to the live test run.
- **AWS Support's diagnosis** (consistent with both of the above, and with what's independently
  known about Indian payment regulation): this account is billed through **AISPL** (AWS's India
  entity). Since March 2022, RBI rules block AWS Marketplace from accepting stored-card payments
  for **contract-pricing subscriptions** on AISPL accounts — and that's exactly how Anthropic's
  Bedrock models are sold. UPI AutoPay (what's actually active here) covers ordinary AWS invoices
  fine; it doesn't satisfy a Marketplace contract subscription's payment requirement. That single
  mismatch explains the missing currency, the e-mandate lock, and the subscription being born and
  killed in the same minute — not three separate problems, one.

**The fix exists and isn't done yet, on purpose.** AWS Support's own recommended path: switch the
account's default payment method to **Pay by Invoice** (root user, Billing contact details, up to
7 days to activate for new Marketplace purchases; a subscription attempt then has one hour to
complete payment before voiding). A same-day workaround also exists — Amazon's own Nova models
aren't sold through Marketplace, so they sidestep this restriction entirely and could escalate to
instead of Claude, today.

**Declined the Nova workaround, deliberately.** ADR-0019 and `escalate.py` were built and priced
specifically around Claude Haiku 4.5 — swapping the escalation path's model family is a real
design decision (different pricing to re-verify, different prompt behavior, a different vendor
story), not something to slide into silently just because it unblocks faster. Roshan's call,
asked directly: **leave `KAV-44` blocked, fully documented, exactly as it is.** He has an
interview to show this project at, and a correctly root-caused, honestly-reported real-world
billing/regulatory constraint — found live, diagnosed with evidence (not guessed), with the fix
identified but not yet actioned under no particular time pressure — is itself solid material for
that conversation. Pay by Invoice is something he'll set up when it's convenient, not a blocker to
rush before any deadline.

## Phase 3 starts — a real Helm chart, deployed to a real k3d cluster (`KAV-46`, ADR-0020)

Jev stays explicitly skipped (Roshan's call). With `KAV-44` blocked on an external billing
process with no deadline, moved to Phase 3: `deploy/charts/kaval` — empty since the project
began — now deploys Postgres, the gateway and `kaval_agent.correlate` (as a real, continuously
running Deployment, not a one-shot) to a real Kubernetes cluster. `k3d`, `kubectl` and `helm`
installed on the dev server, checksum-verified like `opa`/`gitleaks`/Trivy; images built via
the existing `docker compose build` against the dev server's Docker daemon and imported into
k3d directly — no registry needed for local.

**Three real bugs, found live, two now guarded against automatically:**

1. A `{{- -}}` trim pair in `agent.yaml` ate the newline between a comment block and
   `apiVersion: apps/v1`, silently turning the whole key into part of the comment.
   `helm lint` didn't catch it — only reading the rendered output did. Fixed, and CI gained a
   new `helm` job (`helm template` through **kubeconform**, checksum-verified like every other
   CI tool) — confirmed to actually catch this exact bug by deliberately reintroducing it.
2. The migrate Job's hook was `pre-install`, which runs *before Postgres exists at all* — the
   first real `helm install` left it stuck at `Init:0/1` forever with no postgres pod anywhere
   to wait for. Fixed: `post-install,pre-upgrade`.
3. The agent crashed once on its first tick, racing Postgres's own startup —
   `correlate.py`'s `--every` loop doesn't catch a connection failure and retry. Kubernetes'
   restart quietly recovered it, which made the race easy to miss as "just a restart." Gave it
   the same `wait-for-postgres` initContainer the migrate Job needed; zero restarts since.

**Live proof the loop actually works in real Kubernetes, not simulated:** wrote one real
incident's signals via a one-off `kubectl run` against the in-cluster Postgres; the deployed
agent's own log on its next tick: `opened    oom_killed:k8s:kaval-demo/checkout  high  6
signals`. `kubectl port-forward` to the gateway confirmed `/healthz` (`postgres.ok: true,
migrated to head`) and `/v1/incidents` showing that same incident — the gateway reading the
same database the Kubernetes-deployed agent writes to, for the first time.

**Deliberately out of scope for this story**, left for the next ones: the executor
(`services/executor/` is still a placeholder — no RBAC to design until there's a component to
bind it to), real K8s events as signals, the staging/prod values split, the timed rollback
drill. `/healthz`'s Ollama sub-check reads `ok: false` in this deployment — correct and
expected, not a bug: no chart deploys Ollama yet, and `diagnose.py`/`escalate.py` stay
laptop-run tools until ADR-0016's deployed-agent trigger design resolves.

This is infra work (ADR-0012: "Infra, CI, docs and refactors don't need UAT"), so `KAV-46`
ships in one PR, ticked and Done directly — no separate UAT sign-off story, unlike the
proposal-facing Phase 2 stories.
