## Slack ChatOps via Socket Mode; mobile app deferred to Phase 9 (`KAV-55`, ADR-0026)

Started from a question about Phase 4's still-open Cloudflare Tunnel task, which exists only to
let the mobile app (Phase 5) reach the gateway. That led somewhere else: a custom mobile client
is unusual in real ops tooling — most companies approve incidents through PagerDuty, Opsgenie,
or ChatOps, not a bespoke app — and even a tunnel still answers "how does the public internet
reach in," which real companies are reluctant to accept for an internal system at all.

Slack's **Socket Mode** removes the question entirely: the gateway opens an *outbound*
WebSocket to Slack and receives button clicks over it, the same direction every other
integration in this project already uses (the node's security group has zero inbound rules;
access is SSM, never SSH). No tunnel, no domain, no public hostname, no inbound port — ever.

**Decision, recorded in ADR-0026:** Slack ChatOps (`KAV-55`) becomes the real approval surface,
landing in Phase 4 rather than waiting on mobile. Mobile moves to **Phase 9**, last, deferred —
not cancelled, just no longer a prerequisite for anything. Chaos+proof, FinOps, EKS, and
Harden+publish each shift up one number (6→5, 7→6, 8→7, 9→8) to fill the gap.

## Slack ChatOps built and unit-tested (`KAV-55`, Lab 21) — live verification still open

Picked up straight on, same session. Built the actual feature ADR-0026 only decided:

- **One shared write path.** Pulled the three checks out of `api.decide()` into
  `kaval_gateway/decisions.py`'s `record_decision()` (`never` refused, no double-decision,
  `not_found`), so `decide()` and the new Slack button handler go through the identical
  function instead of two copies that could drift. `decide()`'s own tests, unchanged, still
  pass — the refactor didn't change its behaviour, only where the checks live.
- **`kaval_gateway/slack_chatops.py`**: `start()` opens an outbound Socket Mode connection
  (`slack_sdk`) at FastAPI startup via the lifespan handler — a genuine no-op unless
  `SLACK_BOT_TOKEN`/`SLACK_APP_TOKEN`/`SLACK_CHANNEL_ID` are all set, true in every environment
  so far including CI. A background thread (`notify_pass`, polled every 30s) finds undecided
  `ask`-class actions nobody's been told about (`pending_actions`, using `~Action.decision.has()`
  — the one-to-one relationship's EXISTS-filter form) and posts each once with Approve/Deny
  buttons. A click's payload is routed to `record_decision()`.
- **Migration**: `action.slack_notified_at`, nullable timestamp — verified both with
  `alembic check` (no drift against the models) and the full test suite rerun against a real
  Postgres (192 passed).
- **Helm**: `gateway.slackSecretName` — empty by default, only ever a Secret *name*, same
  posture as `ecr-cred`; the gateway Deployment adds an extra `envFrom.secretRef` when set.
- **Tests** (`services/gateway/tests/test_slack_chatops.py`, 6 new): real `WebClient`/
  `BaseSocketModeClient` subclasses with their network methods overridden to record arguments,
  never a mock of the whole module — the actual query and decision logic runs for real. Caught
  one real mypy issue along the way: the listener callback's parameter needed typing as
  `BaseSocketModeClient`, not the concrete `SocketModeClient`, for Liskov substitutability.
- A stale mypy cache (left over from an earlier `git stash`/`pop` mid-session) produced one
  flaky, unrelated-looking error (`kaval_collector` missing an attribute it plainly has);
  `rm -rf .mypy_cache` resolved it outright — not a real code problem, worth remembering before
  chasing a mypy error that contradicts a clean `pytest` run.

**Honest gap, not hidden, same posture as `KAV-44`'s AWS Marketplace blocker:** nothing here can
create a Slack App — that's Roshan's own action (Lab 21, Part 2). Until it's done, this story
stays **In Progress**, not Done, and the ROADMAP checkbox stays unticked. The code is complete
and tested; the live click-to-execution proof is not.
