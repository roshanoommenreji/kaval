- **Release round:** #377 (KAV-111) merged 23:09, #379 (Kaval 0.4.1) 23:21, the bot's staging pin #380 at 23:27; v0.4.1 tagged on `85a97f0`, images built and published.
- **The failure:** staging built (93 resources, plan exactly as reviewed) but did not become ready in 15 minutes. The gateway's migrate job failed with `No 'script_location' key found in configuration`. Cause: the first version of the change also removed `/app/pyproject.toml` from the images, and alembic reads `[tool.alembic]` from that file. My before-and-after file list showed the removal; I called it unused after searching only the source folders, which was wrong.
- **What it did not touch:** production (pins `sha-14311a9`, parked). Nothing was promoted. The smoke test passed nothing and recorded nothing.
- **The KAV-116 check on that copy was inconclusive, not a pass:** the gateway login answered `false` for UPDATE, DELETE and TRUNCATE, but also `false` for SELECT and INSERT, which should be `true`. The permissions are applied after the release is ready, and it never was. The positive controls are what made that visible.
- **Teardown:** `make staging-down` destroyed 92 resources and the data disk (00:09); sweep clean (nothing of staging in any service), production's backup copies 23 before and 23 after. Staging ran about 35 minutes: roughly 3 cents.
- **The fix (`fix/KAV-111-gateway-image-keeps-alembic-config`):** the gateway image copies `pyproject.toml` back (with `migrations/`); four new tests (the gateway image holds what the migration job reads; alembic's `script_location`; the chart still runs alembic from the gateway image; and the rule that finds what a stage copies); `alembic heads` on the real arm64 image answers `d4f7a2c9e815 (head)`, and prints the `script_location` error on the broken v0.4.1 image, so the check would have caught it on the laptop. Comparing the fixed gateway with the old one: only the source copy is removed (51 files), plus the renamed version folder.
- **Lessons recorded:** (1) a file list proves what is inside an image, not that it works: run the thing it is for (now Part 5b of the lab); (2) when a file is dropped, search the whole repository, not only the code, for its reader; (3) positive controls on a check (read and insert must be true) are what stopped a wrong "false" being read as a pass.
- **Next:** this fix needs its own release round (v0.4.2) and a fresh staging session that proves KAV-111 and KAV-116 together (about 5 cents), then promotion on his own phrase. Jira KAV-111 stays In Progress, KAV-116 stays open.
