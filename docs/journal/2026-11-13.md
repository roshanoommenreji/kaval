## Supply chain, story 1: a parts list and a signed build record (KAV-137)

His `go` after the compact started the supply-chain line of Phase 8. It is four stories, filed in Jira under KAV-14: `KAV-137` (this one: a parts list and a signed build record for every image, CI only, $0), `KAV-138`
(cosign signatures in ECR, needs a reviewed read permission for the build robot), `KAV-139` (`promote.yml` refuses an unsigned image) and `KAV-140` (the cluster refuses unsigned images, watch-only on staging
first, memory measured on the 4 GB node).

- **Built:** `release.yml` makes a CycloneDX parts list with the same pinned Trivy right after the scan and before any AWS access (checked to be CycloneDX and not suspiciously short; kept 90 days as `sbom-<service>`),
  signs a build record for the digest ECR reported (`actions/attest-build-provenance`, pinned by commit) and fails the release if GitHub's store has no record for that digest. `publish` gains
  `attestations: write`; `propose` gains nothing. [ADR-0089](../adr/0089-every-image-gets-a-parts-list-and-a-signed-build-record.md), [Lab 91](../labs/lab-91-a-parts-list-and-a-signed-build-record-for-every-image.md),
  [runbook](../runbooks/verify-an-image.md), 11 tests in `scripts/dev/test_release_supply_chain.py`.
- **A design turn worth keeping:** my first version had the release verify the record's signature with `gh attestation verify oci://…`. That reads the image from ECR, and the build robot's role is deliberately push-only, so
  it would have failed on its first real run. The release now only proves the record **exists**; the signature check lives where a read is allowed (by hand, then the promotion gate in `KAV-139`). A test also pins
  that the role gained no read permission.
- **A leak avoided:** the record's name is `kaval/<service>` with no registry host, because the record on a public repository is public and the host holds the AWS account number.
- **Tried locally:** the pinned Trivy produced a valid CycloneDX list for a real image (15 parts, no findings); `--scanners none` is not accepted by this version.
- **Proven live, same night (his merge of #394, then my manual release run 43291746398):** all five jobs green, parts lists of 143-151 packages, one stored record per digest, `gh attestation verify` passed for `release.yml` on `main` and was refused for `ci.yml`. Side effect I had not planned: a run for a new commit opens a staging-pin PR (#395), which I closed unmerged; five extra images sit in ECR (cents). Lab 91 and ADR-0089 now say so.

## Supply chain, story 2: signing every image in the registry (KAV-138)

- **Plan (his "go" after the compact):** keyless cosign signing of each pushed digest, stored in ECR; the build robot's role gains a read on its own five repositories (the only AWS change); the parts list is bound to the digest too. Cost $0.
- **Checked in the docs rather than recalled:** ECR supports the OCI 1.1 referrers API, so a signature is stored as an *untagged* item that points at its image. That avoids the clash with immutable tags that the older `sha256-<digest>.sig` tag scheme would cause, and ECR's lifecycle policy removes referrers within 24 hours of their image being removed. What the docs do not say is whether our "untagged images expire after 7 days" rule spares them, so the live proof runs ECR's lifecycle preview and reads the answer.
- **Built:** `release.yml` fetches cosign 3.1.4 with a pinned checksum (like Trivy), signs the digest ECR reported (skipping a digest that already has a valid signature, then checking the new one straight away so an unreadable signature stops the release), binds the parts list to the digest with `actions/attest` (kept in GitHub's store, not ECR, so a public log never carries the registry host), and the store check now needs both records. Who may have signed is spelled out in full (`release.yml@refs/heads/main`), never a pattern. [ADR-0090](../adr/0090-images-are-signed-keyless-and-the-signature-lives-in-the-registry.md), [Lab 92](../labs/lab-92-signing-every-image-in-the-registry.md).
- **Terraform plan (shown, not applied):** `0 to add, 1 to change, 0 to destroy`: one in-place edit of the publish role's policy, adding `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer` on the five repositories.
- **Tests:** 19 in `scripts/dev/test_release_supply_chain.py`. The old test that forbade any read permission was replaced on purpose by tests that pin exactly the two new actions on the five repositories and still no delete. Three tests run the real signing step against a stand-in for cosign (already signed: nothing signed; unsigned: check, sign, check; unverifiable: the step fails). Removing the post-sign check from the workflow makes two of them fail, so they do bite.
- **Order matters:** the permission must be applied before the first release on `main` that carries the sign step, or that release stops at it. Nothing unsigned would be promoted, but it wastes a round.
