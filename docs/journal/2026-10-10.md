## Component versions, tags and generated change records (KAV-67, ADR-0035, Lab 36)

**What.** Built the two remaining pieces of `release.yml`'s promise. `scripts/release/versions.py` works out each
component's next version from the conventional commits since its last tag; `release-prepare.yml` opens the
`chore(release): Kaval X.Y.Z` pull request that writes them (`__version__`, `pyproject.toml`, `uv.lock`);
`release.yml` tags `<svc>-vX.Y.Z` and `vX.Y.Z` once images are pushed. `scripts/release/change_record.py`
writes `docs/releases/<date>-vX.Y.Z.md` and `promote.yml` puts it in the promotion pull request. Backfilled the
first record, `v0.1.0`, for the version prod is pinned to.

**Why these choices.** A stdlib script, not release-please: it has to know which files ship in which image, and
a test now checks that against the Dockerfiles. The bump is a pull request of its own because the image label is
stamped from the code, so the number must exist before the build. A breaking change moves the minor while a
version is 0.x (amends ADR-0013). The record rides in the promotion pull request so approving the pin approves
the record, and it is written by the job that has no AWS or Jira access, from Git, the passed-staging record
and the gate's own output. It says "unreleased changes in this build" when the images carry more than the tagged
versions, and "verification: not recorded yet" because nothing has run when it is written.

**What went wrong.** `bump` first forgot `uv.lock` (it records the project's version and CI uses `--locked`);
my Dockerfile parser read one source of a two-file `COPY`; the previous release did not have the backup
component yet. Most useful: the generator needed "what did prod run before", and `promote.py body` gave the
wrong answer, because it read prod's files *after* `pin` had rewritten them. Pull request #83's text says
"Prod runs sha-2459417 now". Fixed with `committed_prod_tag` and a regression test.

**Proof.** 145 release-script tests; the generator run on the real history (39 commits, nine Jira keys, risk
high because of the migration and the executor); the dashboard's own parser reads the output; a bump rehearsed
in a clone passes `uv lock --check`. **Not proven live:** the new steps in `release.yml` and `promote.yml` run
at the next real release and promotion.

**Open.** `rollback.yml` does not mark the record it undoes; no Jira Release is created yet (needs write access
CI deliberately lacks); ECR retention is next; KAV-65 (OPA) is due 2026-10-23; prod is still parked on
`sha-2459417`.

**After the merge (pull request #88).** With Roshan's approval the baseline tags `gateway-v0.1.0`, `collector-v0.1.0`,
`agent-v0.1.0`, `executor-v0.1.0`, `backup-v0.1.0` and `v0.1.0` were pushed at `sha-2459417`. `release-prepare.yml`
was dispatched on `main` once: it fetched the history and tags and reported nothing to bump, the first live
proof of that workflow.

## KAV-68 — ECR keeps the newest fifteen images (ADR-0036, Lab 37)

**What.** `infra/modules/ecr` gets a second lifecycle rule: per repository, keep the newest 15 `sha-*` images
and let ECR expire the rest (variable `keep_tagged_images`, minimum 5). ADR-0024's "kept forever" is amended;
the audit trail is Git (tags, `passed-staging.json`, `docs/releases/`). `promote.py preflight`, the first line
of `make up`, asks ECR whether the four images prod pins still exist and stops before anything bills if not.

**Why 15.** ECR cannot be told "except what prod runs", so the only exposure is a prod parked through more than
N newer builds, as it is now. Fifteen is five to seven weeks of builds at the current pace and costs at most
about $0.71 a month (7 GB). The cost doc budgets the cap (ECR row 0.70, total worst case ~$40.75).

**Proof.** An ECR lifecycle *preview* of the same rule with a limit of one, on the real gateway repository,
listed `sha-ffb436b` as the image it would expire and left `sha-2459417` alone. `preflight` passed against the
real registry. The prod plan is five policy replacements and nothing else. 147 release tests pass.

**Nearly wrong.** A second `keep-*` tag to protect prod's image cannot work: ECR has no exclusion, so the
image still matches the `sha-` rule.

**Applied** after PR #90 merged (with Roshan's go): 5 added, 5 destroyed (policies only); all five repositories read
back with both rules; a second plan showed no changes; `preflight` still passes.

**Not proven live.** No repository has more than 15 images, so no expiry has happened yet.

## KAV-71: a rollback marks the release record it undoes

dashboard's change-failure figure could never move. `rollback.py pin` now finds the newest `docs/releases/` file whose

## KAV-74: the nightly database dump is taken by the app node, not by a pod

Needed before staging can be seeded (KAV-73): the S3 backup bucket is empty. Reading the chart `CronJob` found four things
wrong with it before it had ever run (ADR-0038). (1) It needed an `aws-creds` Secret holding a live key, because a pod cannot
reach the node's identity (the hop limit); the safety classifier had refused to draft it. (2) It was scheduled 00:00 UTC, and
the nightly auto-stop runs at 20:30 UTC (02:00 IST) and scales the node to zero and stops the database, so nothing would have
been running. (3) The node installs `postgresql15` but the database is Postgres 16, and `pg_dump` refuses a newer server.
(4) `backup.sh` checked `pg_dump`'s exit code but not that the file could be read, and it moves the `LATEST` pointer
`restore.sh` trusts.

Decision (Roshan chose, from three options): the node dumps itself, from a systemd timer at 19:30 UTC (01:00 IST), using its
own instance role, which can already write to the bucket. No key is created or stored anywhere. `user_data.sh.tftpl` writes
`kaval-db-backup` (looks up the database server by tag, reads the admin password from SSM exactly as the `db-roles.sql` step
already does, fetches and runs `backup.sh`). The Postgres 16 client is installed with a fallback to 15 so a missing package
cannot stop a node booting. `backup.sh` now lists the archive with `pg_restore --list` before uploading, and passes the TLS
mode through. New `backup_bucket_name` input on the node module; prod and staging both pass their own bucket.

Proof, local and free (Lab 40): the real boot script rendered by Terraform with and without a bucket (valid shell both ways);
the node's own command plus the real `backup.sh` against a real Postgres 16 with the real migrations: dump uploaded and
readable with the row in it, `LATEST` moved, a 40-day-old dump expired, a 3-day-old one kept. Four failures (unreadable dump,
version-mismatch message, no database server, refused login) upload nothing and exit 1. Mutation: with the readable-file
check removed, a junk file IS uploaded and `LATEST` points at it. Prod `terraform plan`: 0 add, 2 change, 0 destroy (launch
template and ASG version), nothing applied. `make lint` clean, 193 tests pass. One slip caught on the way: I exported the
region after the first call that needed it; reading the rendered script back found it.

Not proven, and not claimed: `dnf install postgresql16` on this Amazon Linux image (search results conflicted), the real TLS
dump, the real S3 write, the timer firing. All three are checked by the first real run. "Nightly" also only means nightly
while production is running; parked days rely on the EBS snapshots. Cost: no new resource, S3 stays within its $0.05 line.
Lab 40.

### First live run, same day: failed before the node started, and why

Roshan ran `make up` on prod for the first real dump. The database server started, then Terraform failed on the launch
template: `InvalidUserData.Malformed: User data is limited to 16384 bytes`. The rendered boot script was 17,643 bytes (14,653
before KAV-74); the plan cannot see that limit and my local proof never rendered it against the limit. Nothing else changed:
no node, no migration, no pods. The database server was left running (the 20:30 UTC auto-stop is the backstop, about $0.02/hr),
and `node.auto.tfvars` (the "stay parked" guard that `make up` deletes) was put back. Fix on `fix/KAV-74-zip-node-user-data`:
`base64gzip` in the node module, zipped size ~6,550 bytes. Staging shares the module and would have failed the same way. Lab 40
step 1b and ADR-0038 record the check. Lesson: a plan proves the shape of a change, not the limits of the service that receives it.

### First live run, second attempt: it works

After PR #108 (zipped boot script) `make up` applied (0 added, 2 changed). The node came up: boot finished, `pg_dump 16.15`
(the `postgresql16` package exists on this image, no fallback needed), timer scheduled for 19:30 UTC. `systemctl start
kaval-db-backup` exited 0 and a 22 KB dump landed at `postgres/kaval-20261010T134919Z.dump`, `LATEST` pointing at it, file
starting `PGDMP`. So the real TLS connection, the SSM read and the S3 write under the node's own role all work, with no new
credential. Unproven: the timer firing by itself (node parked before 19:30), and a full restore (KAV-73). One Windows
quirk: the log's arrow character crashed the AWS CLI's output decoding (`charmap`); the command had already run, so the log was
read again with `PYTHONUTF8=1` rather than running the dump twice. Cost of the whole session: the app node and database for
about an hour, roughly $0.10. ADR-0038, Lab 40 step 6.
