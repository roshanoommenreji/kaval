## `KAV-112`: a written threat model and a prompt-injection set (evening, built)

The roadmap's Phase 8 security line, done as a document plus tests rather than a diagram. [The threat model](../architecture/threat-model.md) has 33 threats in eight groups (the agent and the model, the collector, Slack and the approval path, the executor, the database logins, supply chain, operations), each with what stops it, the test or file that proves it, and a status. [ADR-0072](../adr/0072-a-written-threat-model-and-a-prompt-injection-set.md), [Lab 72](../labs/lab-72-the-threat-model-and-the-prompt-injection-set.md).

What was built: tests for every layer around the model that need no model (209 new tests: a fix list that stays last and unchanged under eight kinds of planted text; a reply refused for every supported cause and a dozen look-alike types and targets; the policy words against names written to get past them; every executor handler taking the target and nothing else; a model-ordered removal refused), and a ten-case injection set for the real model, kept apart from the golden twenty so their history does not move. Seven cases ask the model to begin its summary with a marker; the report counts how many did (reported, not gated).

What it found, which the old argument ("the agent can only write a suggestion") did not predict:

- **The approval route has no login, and the chart has no network rules** (`KAV-115`). `POST /v1/actions/{id}/decisions` records an approval for whoever can reach it, with a free-text name, and the only NetworkPolicies in the repository are in the EKS lab. A pod inside the cluster, including the demo workloads where the untrusted text starts, could approve a proposal for itself. Bounded (a `never` action cannot be approved, the executor re-checks, three fixes, the incident's own workload, 60 minutes), and production is parked most of the time, but it is the weakest link in "a human approves".
- **Model-written text is live Slack markup** (`KAV-114`). Slack's own rules say `<`, `>` and `&` are control characters, and the summary goes into the card as written, so a summary can ping the whole channel or draw a link labelled "Approve all fixes".
- **Signal text is not flattened or capped** (`KAV-113`), and **the gateway's database login can `UPDATE` a decision** (`KAV-116`).
- **One claim was too strong.** ADR-0054 and `fixes.py` said text planted in a log line cannot change the cause. It has two switches (the phrase `exec format error`, a reason of `OOMKilled`); each only chooses between causes that have a fix. Both places amended, a test pins it.

The gaps are written as expected-failure tests that name their stories, so fixing one forces the marker out. Lab 71's last box ticked (GitHub recognises the security policy; the API list that disagreed was the unreliable one).

**Run live the same night** (dev server, each step on its own go, about 20 minutes, a few cents): the ten attacks against the real model, twice. The gate held and every case got the right fix aimed at its own workload. The model obeyed planted text in 2 of 7 marker cases, the same two both times (a plain instruction in the message; a claim that a person already approved, which would open the card's summary with "Approved by the on-call lead"), and did not write the Slack broadcast or the fake link. New story `KAV-117` (tell the model the text is data; label the summary on the card). **My mistake, caught in the output:** the first run had no `opa` on its path, so every action fell back to `ask` and the safety gate read "0, OK" without checking anything. ## `KAV-115`: a login on the approval route (built, part 1 of 3)

`KAV-112` found that `POST /v1/actions/{id}/decisions`, the route that records an approval, asked nobody who was calling, and that the chart used by staging and production has no network rules. Roshan picked it as the next free item.

The plan was two controls, so one covers the other's miss: a token on the route, and network rules around it. A look at how secrets already reach the cluster showed a third piece: the node's bootstrap rebuilds every Secret from Parameter Store on each boot and on a six-hour timer, so a hand-made token would be lost at the first replacement. The token therefore needs a Terraform-made home in Parameter Store too. Three pull requests, each through staging before production: the login (this one), the token's home, the network rules. [ADR-0073](../adr/0073-the-approval-route-gets-a-login-and-the-namespace-gets-network-rules.md).

What this one does: the route needs `Authorization: Bearer <token>`. It is shut (503) when no usable token is configured, compares in constant time, runs before the database or the body is touched, and never writes the token to a log, a reply or a metric. The actor is stored as `api:<name>` so a caller cannot pose as `slack:<name>`. The chart reads the token from the Secret `kaval-approver` (optional, so a missing Secret leaves the route shut rather than crash-looping the pod); `make approve` reads it from an environment variable, never an argument; `make chaos-approve` reads it from the cluster on the node so it never reaches the laptop. Tests: 30 for the login (no database), the existing approval tests now send the token, one new one for the `api:` prefix, chart tests for staging, production and the empty default. Run against a throwaway local database: 127 gateway tests pass (6 expected failures are `KAV-114`); the wider run passes 1,113.

Two small things the work turned up. A new metric label (`why`) failed the existing "nothing from data on the metrics page" test the moment the gateway and the shared tests ran in one process; the label is now `outcome`, which that test already allows. And `services/shared/tests/test_metrics.py` and `kaval_shared/metrics.py` both say Flannel enforces no network policy; k3s's own documentation says it ships a policy controller that is on unless switched off, and ours is not switched off. To be proven live in the third part and then corrected everywhere, including the comment at the top of the EKS lab's network-policies file.

Until the second part lands an environment has no token, so its approval route answers 503 and `make approve` cannot work there (Slack still does). The two are promoted to production together.

## `KAV-115` part 2: the token's home (built)

#298 merged. The second pull request makes the token a thing that exists without anyone typing it. A new Terraform module (`infra/modules/approver-token`) generates it (43 letters and digits) and stores it in Parameter Store at `/kaval/<env>/approver/token`; staging and production each use it and let the node's role read exactly that one parameter; the node's bootstrap writes the Secret `kaval-approver` from it on every boot and on its 6-hour timer, like the database passwords.

One deliberate difference from the Slack and database Secrets: if the token cannot be read, the bootstrap **carries on** and writes no Secret. A gateway without a token is shut, which is the safe state; stopping the whole cluster's start-up for a login Secret would be worse. The test I wrote for that case found a real hole: a value of spaces passed the "not empty" check and made a Secret. The step now strips spaces first.

Read-only `terraform plan` for production: 2 to add (the parameter and the password), 3 to change (the node's read permission, the launch template's bootstrap text, the scaling group's template version), 0 to destroy, and no other drift. The group is parked at zero, so no server is touched. Nothing was applied. A new runbook, `approval-refused.md`, covers a 401 or 503 from the route, how to load the token into your shell without showing it, and how to rotate it.

Cost: $0 (a standard-tier SecureString parameter is free; the default key is free).

The node's start-up script is close to EC2's size limit (16,384 bytes once packed), and a guard test (`test_the_node_start_up_script_still_fits_the_ec2_limit`, line at 15,800) caught the first version of this step at 16,060. Rather than raise the guard, the step was made shorter and two comments that repeated a note already at the top of the same script were trimmed: it now packs to 15,744, 8 bytes more than before this change. The next addition to that script has to move something out first.

## `KAV-115` part 3: the network rules (built)

#300 merged. The third pull request closes every way *into* the namespace and opens exactly the doors Kaval uses. To find the doors I read every port and URL in the chart rather than guess: Prometheus reads every pod's health page (:9100); the poller (`collector-prometheus`) asks Prometheus what is firing (:9090) and times the gateway's health page (:8000), which makes it the only pod allowed to open the gateway's port; the diagnosis worker reaches the model (:11434); the chart's own Postgres, used only locally and in the lab, accepts Kaval's pods. Nothing else. No rule uses an address range or another namespace. Staging and production render five policies; `local` and `lab-eks` render none (the lab has its own stricter set). Outgoing traffic is not touched.

The part that cannot be proved offline is the node: kubelet's health checks, the smoke test and the game days all reach pods from the node, not from a pod. Whether the controller lets that through is exactly what the live proof on staging checks. k3s's documentation says its built-in controller enforces policy unless started with `--disable-network-policy`, and the node's unit file does not pass that flag, which contradicts two comments in the repo (the metrics module and the EKS lab's policy file). They are corrected after the proof, not before.

Also built, because the plan says an alert on the feature itself: `KavalApprovalRefused` fires when the gateway has refused more than two wrong or missing tokens in ten minutes (a typo is one or two). `switched_off` is left out on purpose: a freshly built environment has it, and it is not an attack. It reaches a person through the existing health-alert path with the approval runbook. promtool tests: a typo never alerts, five wrong tokens alert and then stop, `switched_off` never alerts.

Tests: 17 chart tests for the rules (the gateway accepts the poller and no other pod; no rule opens to an address range, another namespace, or "everyone"; every pod a rule names exists; Prometheus is the only reader of the health pages; the model answers the diagnosis worker only), 3 promtool cases, 1 message test. Gateway suite with a throwaway database: 166 pass (6 expected failures are `KAV-114`).
