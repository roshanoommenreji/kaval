## `KAV-113`: a signal's text is flattened and capped before the model reads it

Roshan said "start KAV-113", I gave the plan (options, the whole path, safety, failure, cost, tests), and he answered "go with your recommendations" (evening, 10 November IST).

- **What was wrong.** Before the model diagnoses an incident it reads the incident's cause, then up to four signal messages. Two gaps, written by `KAV-112` as expected-failure tests: a line break in a message could start a line that looks like one of the message's own headings (T-AGENT-4), and nothing capped a message's length (T-AGENT-5). Both were low risk, because the real fix list is always last and the reply is checked afterwards.
- **The fix** ([ADR-0083](../adr/0083-a-signals-text-is-flattened-and-capped-before-the-model-reads-it.md), [Lab 85](../labs/lab-85-flattening-and-capping-a-signals-text.md)). `kaval_agent.context.flatten_signal_text` turns every line break, tab, control character and Unicode line separator into a space, collapses blanks, and cuts to 300 characters ending in "…". `query_text_for` uses it for each message and counts messages that differ only in blanks once. It is applied only where the model's text is built: the stored signal and the correlator that picks the cause still see the whole message (a test pins that a clue 5,000 characters in still decides the cause).
- **Why 300.** Measured: the longest message among the twenty golden incidents is 203 characters, and none has a line break, so their scores cannot move. Kubernetes cuts an event near 1,000.
- **A mistake caught before commit.** My first version treated every non-printable character as a blank, which would also have turned a zero-width space into a space and changed one of the injection set's cases. Now only control characters and the two Unicode separators count; invisible format characters stay, because they cannot start a line.
- **Checked.** Test-first: the new tests failed for the right reason (the helper did not exist) before the code. The two former expected failures pass as ordinary tests, so the project now has none. `ruff` is clean and `mypy` shows only the error that was already there.
- **Merged** as #358 (13 checks green after one fix: a docstring line over the 100-character lint limit, which I had rewrapped and not re-linted).
- **The before-and-after run** (Roshan's `go eval run`, then `go with recomended` for the rerun; dev server about 40 minutes in two sessions, an estimated 2 to 3 cents). The first attempt stopped at once: `make evals` refuses to run without `opa`, which this laptop did not have. I downloaded the release CI uses (1.21.4) into a scratch folder, checked the checksum, and confirmed 29/29 policy tests. Old code: 20/20. New code, straight after: **18/20**, both sparse cases over the confidence limit. The text the model sees in them is identical, and the stored values (0.7, 0.95) matched leftover signals from the first pass joining the same open incidents (the evidence rule then sees two observations, not one). A rerun more than 15 minutes later gave 20/20 with both at 0.5. I did not inspect the leftover rows directly. Injection set: 10/10, obeyed 2/7 (unchanged), the 6,000-character case reached the model as about 300 characters. Details in [Lab 85](../labs/lab-85-flattening-and-capping-a-signals-text.md) Part 5.
- **A wrong figure of mine found on the way.** The `KAV-114` write-ups say live-Slack-markup cards are counted "n/10"; the run prints `0/7`, because only the seven cases that plant a marker get a card verdict. Corrected in ADR-0082, Lab 84 and the evals README (the 9 November journal entry is left as the record of its day).
- **Not yet done.** A release round together with `KAV-114`, staging smoke, promotion. Jira `KAV-113` stays In Progress, boxes unticked, until then.
