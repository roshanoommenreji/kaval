# 2026-10-08

## `infra/envs/staging`, built and proven live (`KAV-57`, Lab 29)

Picked up the next `ROADMAP.md` Phase 4 line. ADR-0004 had already decided the shape (a second
cluster, created per release, destroyed after), so the work was making it real. Planned first
(approved), then built.

**The first surprise was in the existing code, not the new environment.** `network`, `node` and
`iam` had `"kaval-prod"` hard-coded, unlike `database` and `backups`, which already took a
`name_prefix`. Added a required one to all three; prod's names are byte-identical, and a prod
plan shows only three intended in-place updates (nothing applied).

**Then a bug that cannot exist with one database.** Every lookup of "the database" used
`Role=database` and took the first match: `make down`/`up`, the health check, the restore script
(whose default snapshot was newest account-wide), the node bootstrap, and the daily snapshot
policy. With a second server, any of them could act on the wrong environment, including pointing
staging's services at prod's database. All now match the exact `Name` tag.

**Live:** 48 resources applied in 71 seconds. Spot `t4g.medium` had no capacity in any AZ (as on
2026-10-06); On-Demand launched at once, so staging now defaults to On-Demand. The services
then crash-looped against a fresh database: the bootstrap applied the per-service roles before
Flux had run the migration that creates the tables, so the grants always failed and the services
waited for a 6-hour timer. The script's own comment called it a race it could lose; it could not
win it. Fixed (roles last, after waiting for the schema) and **re-proven by destroying staging and
building it again from nothing**. A second latent bug surfaced the same way: the gateway role
could not read `alembic_version`, `signal` or `incident_signal`, so `/healthz` reported a
permissions error. Invisible on prod because `/healthz` also 503s there for want of a served
model.

**Teardown was a first too:** the database's data volume is `prevent_destroy` (and wired by
address into the restore script), so staging is destroyed by stopping the database, releasing the
volume from state, destroying 47 resources, then deleting the volume by hand. Verified nothing
staging-tagged remained and prod's database, volume and ASG were untouched.

ADR-0004, ADR-0008 and ADR-0027 amended; full writeup in [Lab 29](../labs/lab-29-staging-environment.md).

## Prod On-Demand and the $50 ceiling (`KAV-58`, ADR-0028)

Roshan chose On-Demand for prod's app node too, with the budget raised to match (the nightly
auto-stop and `make down` limit the hours it bills). Doing the arithmetic for the ADR found a
mistake in the existing budget table: its "app node subtotal ~$13" and "total ~$27" counted only
compute, disk and IPv4, leaving out about $3.75 of rows it listed (ECR, S3, logs, Bedrock, Jev,
transfer). Always-on was already ~$31.70 on Spot and is ~$40.25 worst case On-Demand (~$38–39
expected). I had quoted ~$35.50 earlier from that table. So the thresholds are **$42 / $46 /
$48 on a $50 ceiling**, not the $40/$45/$48 the old spacing would have given: the first alert must
sit above normal spend. Effect on the credit: projection ~$110 to ~$126, headroom ~$30 to ~$14.
Every living statement of the old figures updated (CLAUDE.md, budget-plan, README, docs, learn
pages, architecture, dashboard, Terraform defaults); dated ADRs, labs and journals left alone.
The prod plan is four in-place updates (budget, snapshot policy, launch template, ASG), shown and
awaiting approval before any apply.
