## UAT, component versions and Jira dashboards (`KAV-34`, `KAV-35`, `KAV-36`)

Roshan asked three questions from how releases work at their job. Is there one Jira dashboard with
everything? Where is **UAT**? And components have their own versions, which release notes name.
All three are now built. The decisions:
- UAT **reuses In Staging** (being accepted) and Ready for Prod (signed off), with no new status;
- a release is **named by the product with its component versions listed** (Kaval 0.3.0: gateway
  1.2.0 · collector 0.4.1);
- **three dashboards**.

**KAV-34, UAT ([ADR-0012](../adr/0012-user-acceptance-testing.md)).**
- A story that changes what an operator sees or decides is labelled `uat` and carries **UAT
  scenarios**, written first and kept separate from the Acceptance Criteria.
- `jira-sync.py uat KAV-n pass|fail --env … --note …` records the verdict:
  - `pass` ticks only the scenarios and moves the story to Ready for Prod;
  - `fail` raises a linked `uat-defect` Bug (Service copied, current sprint) and moves the story
    back to In Progress.
- **Refused:** a story that isn't In Staging, one without the `uat` label, and a `pass` while its
  defect is open. Two of those refusals were added after the live trial showed `pass` would
  otherwise accept anything.
- The ADF layout moved to `jira_adf.py`, which is unit-tested in CI.
- The delivery diagram gained a "UAT signed off?" gate.

**KAV-35, component versions ([ADR-0013](../adr/0013-component-versions-and-release-naming.md)).**
- gateway and collector carry `__version__ = "0.1.0"`, reported by `/healthz`, OpenAPI,
  `--version` and the OCI image label.
- CI reads the version from the code, stamps it on the image, and checks inside the image that
  the two agree (`label=0.1.0 code=0.1.0 want=0.1.0`).
- Bumps and tags (`gateway-v1.2.0`, `v0.3.0`) come from path-scoped conventional commits,
  automated with `release.yml` in Phase 4.
- Roshan added a **Service** Checkbox field (Jira's team-managed projects have no Components) and
  a **Bug** work type. `backfill-service` set Service on 9 past stories from the folders their
  commits touched.

**KAV-36, dashboards as code.**
- `scripts/tracking/jira-dashboards.toml` declares 10 filters and 3 dashboards, Delivery (10001),
  UAT (10002) and Releases (10003), and `make jira-dashboards` builds them.
- A second run changed nothing.
- It's a `uat` story itself: signed off only after Roshan looks at each dashboard, because gadget
  settings go through a thinly documented part of Jira's API.

**What went wrong:**

  so GitHub rejected the whole workflow and PR #12 showed *no* checks, which isn't the same as

  Placeholders are now skipped.

## KAV-36 UAT, first pass: the dashboards were empty

Roshan opened the three dashboards: they existed, but every gadget was blank. The script had
stored each setting as its own dashboard item property. Jira reads one property, `config`, whose
value is an object; the Default dashboard's own gadgets showed that. The API took every write and
the idempotency check passed. Only looking at the page showed the fault, which is the reason
KAV-36 was a `uat` story. Fixed: one `config` per gadget, a bare filter id for Filter Results,
`filter-<id>` for the charts (checked against the `/rest/gadget/1.0/...` endpoints), and stale
per-setting properties removed. A second run changes nothing. The UAT verdict comes once Roshan
looks again.

**Second look:** Delivery rendered, including both columns and the Filter Results list, but every
UAT and Releases gadget still said "hasn't been configured yet". All three dashboards stored the
same `config`, so Jira had kept the state those gadgets were first opened in.
`jira-dashboards.py --rebuild --only …` replaced them with fresh gadgets, and after a hard reload
both dashboards showed the expected data: KAV-36 awaiting acceptance, and 21 issues "Unscheduled"
on Releases.

The trial story KAV-37 and its Bug KAV-38 were deleted, with Roshan's OK.

## Phase 2 starts: signal correlation (`KAV-39`, ADR-0014)

The first code in `services/agent`. `kaval_agent.correlate` turns the signals not yet in an
incident into `incident` rows. The six signals of one OOM become one incident, named
`oom_killed:k8s:kaval-demo/checkout`. All the rules are code; none of it is the model's job
([ADR-0014](../adr/0014-signal-correlation-and-incident-fingerprints.md)):
- **Subject:** the workload, with the pod's generated suffix removed, so a restarted pod keeps
  its fingerprint. For AWS, the resource.
- **Cause:** the most specific cause in the group names the incident, e.g. the kill rather than
  the restarts it caused.
- **Time:**
  - a new group waits 60 s before opening, because the fingerprint can't change afterwards;
  - an incident closes after 15 quiet minutes (48 h for AWS, whose data is daily);
  - a recurrence is a new incident with the same fingerprint.
- **Cost:** a day counts as a problem only above 3× the week's median, so six normal days stay
  unlinked.
- **Two at once:** a Postgres advisory lock makes a second correlator skip its pass.

The agent became a real component:
- its own image, in the CI matrix and Dependabot;
- `make correlate` runs one pass;
- a migration adds `ix_incident_signal_signal_id`. The table's primary key starts with
  `incident_id`, so "is this signal linked yet?" would otherwise scan the whole table.

The 20 pure unit tests ran locally. The two database tests run in CI.

**Signed off.** The dev server's idle-stop (ADR-0007) had paused it mid-session; `make devbox-up`
brought it back, and the pause turned into an unplanned but useful check: a `make correlate` right
after restart closed the exec-format incident that had gone quiet while the server was down,
proving the quiet-window rule works on wall-clock time, not on how often a pass happens to run.
`oom-crashloop`, `exec-format` and `cost-spike` each opened the right incident (`oom_killed` and
`exec_format` high, `cost_spike` medium with exactly one signal), a second pass reported nothing
new, and a repeat of `exec-format` a day later opened a **second** incident with the **same**
fingerprint — the recurrence rule, seen live. `jira-sync.py uat KAV-39 pass --env dev` recorded it;
KAV-39 went to Ready for Prod, then Done.

## The context builder (`KAV-40`, ADR-0015)

Before the agent can ask a model to diagnose anything, it assembles what a person on call
would read first. Three sources, three different mechanisms, because they're three different
questions:
- **Runbooks** need real similarity search — `container_memory_near_limit` and "the pod keeps
  OOMing" are the same problem in different words. `kaval_agent.runbooks` chunks each
  `docs/runbooks/*.md` by its `## ` heading; `kaval_agent.embeddings` calls Ollama's
  **all-minilm** (384-dim, ~45 MB); `kaval_agent.index_runbooks` syncs the result into a new
  pgvector table, `runbook_chunk`, re-embedding only what changed.
- **Past incidents don't** need similarity search: the fingerprint from correlation already
  says precisely what kind of failure this is. `similar_incidents` matches on cause and domain
  (`func.split_part`, Postgres-specific), exact fingerprint first, joined with the outcome if
  one was ever measured.
- **Recent changes** turned out to be the hard one to source honestly. There's no real
  deployment history yet — that's Phase 3 — so `kaval_agent.recent_changes` reads this repo's
  own `git log` for the service a workload maps to, and it runs from the **laptop only**: the
  agent's Docker image never receives `.git`, a Phase-0 security boundary not worth punching a
  hole in for this. It degrades honestly (`unmapped workload`, or `unavailable here`) rather
  than pretending to have checked.

`kaval_agent.context.build_context()` assembles all three into one prompt-ready text block.
`make context INCIDENT=<uuid>` prints it for inspection — the step that actually calls the
model for a diagnosis is a later Phase 2 task.

**The relevance cutoff was measured, not guessed.** A first guess of 0.35 turned out to sit
*inside* the noise floor: two genuinely unrelated queries (an OOM, an idle volume) against the
only runbook that exists scored 0.38–0.40 on the dev server. A real match — a
database-connection query against "database lost or corrupted" — scored 0.69. The gap between
0.40 and 0.69 is where 0.5 sits. Run live on real incidents: an OOM correctly finds no runbook
match and reports `unmapped workload` for `checkout` (the synthetic scenario's fictional
workload); an `exec-format` incident on `gateway` (a real service) correctly lists this week's
actual commits to `services/gateway/`, and a recurrence correctly finds the earlier incident
under similar past incidents.

The runbook-sync and retrieval tests first failed against the shared dev database — not a code
bug: `sync_runbooks` correctly saw the real, already-indexed rows from the live calibration run
as stale, since the test's own file set didn't include them. Each database test now clears
`runbook_chunk` inside its own rolled-back transaction first.

`runbook_chunk` is the first table that isn't part of the append-only spine, and
`test_all_spine_tables_present` moved from exact equality to a subset check to allow it, while
still catching a dropped spine table.
