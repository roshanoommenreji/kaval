## `KAV-122`: a documentation sync can hang, and one failed quietly (found late on 2026-11-01, recorded here)

Found at 23:30 IST on 2026-11-01 while refreshing the dashboard and Confluence after #307. A sync started at 20:19 had been running for over three hours: one Atlassian connection had stalled and the script waits for it forever (`urllib.request.urlopen` is called with no time limit). It was stopped, all of its processes were confirmed gone, and Confluence's newest change was confirmed to be the last good run (23:19), so nothing was half written.

- **Two mistakes of mine, recorded because they are the useful part.** Straight after the context was compacted I said nothing was running without checking; the session's own notice and the process list both showed that job. Later I called the next refresh clean because the background notice said "exit code 0", when the log said `DONE exit=2` (a dropped connection, `WinError 10060`): the notice reported my wrapper's last `echo`, not the sync. Both were corrected the same hour; the rerun finished (`DONE exit=0`, 23:55 IST) and Confluence, the dashboard (version 143) and the new page were checked against `main`.
- **Found, not fixed:** `call()` in `scripts/tracking/atlassian.py` has no time limit and catches only HTTP errors, so a stalled or dropped connection either hangs or ends the whole run. Every Jira and Confluence script goes through it. Filed as `KAV-122` (Phase 8, one point, under `KAV-14`): a time limit on every request, a clear failure naming the method and path (never the token), reads retried a few times and writes never retried automatically (a write that timed out may have landed, and a repeat could make a second Jira issue), and `make docs-sync` exiting non-zero on failure, each proven by a test against a local server that never answers.
- **Not known:** which end caused the failures. A name-lookup failure at 00:53 on 2026-11-02 (the laptop could not find Atlassian's address) was gone by 00:56, which points at the laptop's connection rather than Atlassian, but neither is proven.
- **Until it is fixed:** syncs run under a 15-minute limit, a sync past about 10 minutes is checked and stopped, and the log is read before anything is reported.
- Cost: $0.

## `KAV-122` built: the Atlassian scripts give up instead of waiting for ever

Built from 22:00 to 22:46 IST (pull request #309 opened) on `fix/KAV-122-atlassian-time-limit`, tests first, after Roshan saw the plan and said "go". Roshan merged it at 22:56. [ADR-0074](../adr/0074-the-atlassian-scripts-get-a-time-limit-and-only-reads-are-retried.md), [Lab 74](../labs/lab-74-a-sync-that-cannot-hang.md).

- **Reproduced before it was fixed.** A local server that accepts a connection and never answers; the old `call()` was still waiting after 8 seconds.
- **What changed.** `call()` hands every request to the new `scripts/tracking/atlassian_http.py`. Every wait has a 30-second limit. A read is tried three times (pauses of 1 and 3 seconds); a write never, because one that timed out may have landed. No answer is one `AtlassianUnreachable` failure whose message names the method and path and never the login, and the three scripts end with that one line and exit code 1 (`guard(main)`). Any answer, whatever its status, comes back as before.
- **One thing past the five written criteria, shown in the plan.** `publish-confluence.py` printed `UPDATE FAILED` for a page Confluence refused and still ended "done" with exit code 0. It now tries every page, then ends non-zero with the titles and no done line.
- **Proof.** 34 new tests against a real socket on `127.0.0.1` that stays silent, hangs up, resets, sends half an answer or answers: a GET gets three connections and a POST exactly one; the login and token appear in no message, traceback or screen output; and the real `publish-confluence.py`, `jira-sync.py`, `jira-dashboards.py` and `make docs-sync` itself, run in a throwaway copy of the repo, exit non-zero with no "done" line and no "Now republish" line, while the same harness ends "done" when the server answers (so it is not simply failing for every reason). Seen red first (9 tests failed for the right reasons, 4 of them "still waiting after 5 seconds"), then green. `scripts/dev` and `scripts/tracking`: 382 passed. A real read from Jira and a real story creation (`KAV-123`) went through the new code and came back as before.
- **Found on the way, now `KAV-123`.** Python's `urllib` passes the `Authorization` header on if a request is redirected to a different address (checked with two local servers; the second received it). Atlassian does not redirect these calls off-site, so the risk is small. Filed, not fixed: the five criteria here are about time limits.
- **Merged and proven.** #309 merged at 22:56 IST (main at `b25b09b`), all 11 CI checks green first. The first real `make docs-sync` on the merged code ran 22:57 to 23:01 and ended `DONE exit=0`: 106 Confluence pages updated and 1 created (Lab 74), no failed page, no "no answer" line, no retry, no traceback. Confluence was read back (Session Notes, Decisions Log, Lab 74 and Repository Guide carry the new content), the dashboard was published as version 145 and spot-checked, and Jira has KAV-122's five criteria ticked and the story in Done, with comments on KAV-122 and KAV-123.
- **Still unknown.** Whether the stalls came from the laptop's connection or from Atlassian.
- **A laptop note.** `make lint` on this laptop stops at four type errors in `services/agent/tests/test_fixes.py`, a file this work did not touch. GitHub's lint, on a clean machine, passed, so the four look specific to this laptop; their cause was not looked into.
