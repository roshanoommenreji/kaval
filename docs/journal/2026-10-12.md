# 2026-10-12

## Phase 5, slice 4: a bad release and a lost server (KAV-80, ADR-0045, ADR-0046, Lab 47)

(Started 2026-10-11 evening; the bad-release run was that night, the lost-server and memory re-run the
next morning.)

**What.** Two more failures handled end to end on staging, and one thing fixed that slice 3 found.
- **A bad release.** New executor action `rollback_deployment`: put a Deployment back to the version it
  ran before. New chaos experiment `badrelease`: a healthy program, then a new version that exits at
  once. Kaval noticed in 66 s, a stand-in diagnosis proposed the rollback, a person approved, 12 s later it
  was done and it held. A restart would not have helped (the same broken version comes back).
- **A lost server.** `scripts/ops/chaos_node.py` (`make chaos-node`) ends staging's app machine through its
  auto-scaling group and times the replacement. About 2 min 10 s later every pod was ready on a new
  machine and the incident written before the loss was still there. Nobody acted.
- **An OOM kill is its own cause.** The collector now reads a pod's last exit reason on a `BackOff` event
  (Kubernetes never emits an `OOMKilled` event), so a real memory kill is `oom_killed`, not `crashloop`.
  Seen live on the memory re-run.

**Why these choices.**
- Rollback with approval, refusing when there is nothing safe to go back to, and refusing a second
  rollback inside an hour (it would go forward to the broken release). The chaos runner may patch exactly
  one named Deployment and nothing else.
- Lost server = the app machine, not the database: it is Kaval's real single point of failure and the one
  that can happen to it for free. The cluster cannot test its own death, so the script runs on the
  laptop with its guard in the script: the group `kaval-staging`, exactly one machine, healthy to begin
  with, and the machine id typed back.
- Flux versus direct fixes (ADR-0045): direct fixes only where Flux does not own the object; today nothing
  the executor can touch is Flux-owned. An action that writes to git is deliberately not built.

**What went wrong, and what it taught.**
- The node script refused twice before ending anything, both for its own mistakes: it expected an `Env` tag
  the auto-scaling group never passes to its machines, then used `/healthz` as its "healthy" test, which
  is 503 on staging for ever (no language model there). Failed shut, then fixed. Neither shows in tests with a
  fake cloud.
- Its step times were stamped before the checks that saw them; cross-checked against the cluster's and
  AWS's own clocks (within about 20 s), then changed to stamp after.
- A bad release with no readiness check took the whole service down (the crashing pod counts as Ready for
  a second, so the good one is removed). The agent, collector and executor have no readiness probe: noted
  for `KAV-83`.
- A live probe to see whether Flux undoes by-hand changes was blocked by the session's guard rails; not
  retried, not worked around. The ADR rests on slice 3's observation and the permissions proof.

**Tests.** 615 passed against real Postgres (the whole suite, including 14 new for the rollback, 14 for the bad-release
runner, 5 for the collector and 3 chart tests), then 17 for the node script and 5 shell-helper tests added; opa 17/17; ruff and mypy clean.

**Next.** Slice 5 (`KAV-81`): full disk and slowness, which end in an alert to a person and no automated
action. Still open from this slice, for later slices: readiness probes on the loop workers and an outside
"still alive" check (`KAV-83`); whether an approval waiting for a person survives a lost server (not
tested); approval expiry (`KAV-82`); the model proposing these fixes (`KAV-84`).


## Slice 5 (`KAV-81`): a full disk and a slow service, where the right answer is "tell a person"

**Why.** Kaval can fix a memory kill and a bad release. Two other everyday failures have no fix a program
should apply: a restart frees no disk and speeds nothing up. The right outcome is a person told and
nothing proposed, and it has to be proven by breaking things.

**What was built.** The "people only" rule (`disk_pressure`, `latency_high`, `kaval_*`) enforced in the agent,
in the policy (the incident's cause is now policy input; any attached action is `never`), in the executor's
re-check, with the gateway's existing 409 as the fourth layer; a Python and Rego list kept equal by a test.
A measuring session on staging first (`make staging-measure-disk`, read-only): cAdvisor already sees the root
disk (28.5 % against `df` 29 %), so no new agent. A disk check (the used fraction, line 0.85, staging 0.38 so
a bounded fill can cross it) and a slowness check (`kaval_collector.probe`, a timed request inside the existing
poller: over 1 s or no answer in 5 s, three in a row, settings-only targets, no redirects). Slack alerts for
both through the existing straight-from-the-signals path. Two game days (`slow`, `disk`) in the runner and
`make chaos-check`, which reads the database afterwards and dry-runs the real alert code because staging has
no Slack. Two runbooks (`disk-pressure`, `latency-spike`), ADR-0047, Lab 48, two post-mortems.

**What went wrong, and what it taught.** The first slow-service run found nothing: the staging setting
was in `deploy/environments/staging/values.yaml` but Flux deploys the copy inside the HelmRelease, which
lacked it (a test now compares the two). My fix commit then failed silently (subject six characters over the
limit, output filtered) and a pull request merged without it; the cluster showed it and it was redone. The
second run wrote the signals but they joined an older incident named `unhealthy`, opened a few seconds earlier
by a harmless "readiness probe failed" event, so the incident kept a name that allows a restart proposal. That
was a safety hole; people-only causes now have their own lane in the correlator, with tests that fail on the
old code. The third run passed, and the disk game day passed on its first run on that build. A chart/image
timing gap crashed the poller for about five minutes after the first deploy; Kaval's own alert fired for it.

**Numbers.** Slow service: incident about 80 s after the program turned slow. Disk: 30 % to 45 % from a bounded
3 GiB write, incident about 35 s after, back to 30 % after cleanup; node memory 1511 to 1608 MiB (39 to 42 %)
while it was held. Both: a hand-filed restart classed `never`, approval refused 409, nothing executed.

**Tests.** 720 passed against real Postgres, OPA 23/23, helm chart tests, ruff and mypy clean. New: the
people-only rule at four layers, 24 for the probe, 7 for the disk check, correlator lane (5), alert text (4), the
runner experiments (13), the check's verdict (7), the settings-equality test (3).

**Not seen live.** A real Slack post (staging has none; prod is `KAV-83`), the production disk line 0.85,
a slow fill over hours (no trend is built), the database server's own disk (`KAV-82`).
