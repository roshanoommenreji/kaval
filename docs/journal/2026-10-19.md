## Live proof, first run: a real gap found

Planted a 1 GiB disk labelled `Project=kaval Env=staging ManagedBy=manual`; ran the scan twice (one finding, the disk,
nothing else); ran the server's cost pull by hand to copy the finding in. The incident `idle_volume:...` opened.

- **Found live:** the removal planner failed every pass, 30 seconds apart, with only `ProgrammingError` in the pod's
  log. The database server's log gave the real message: `permission denied for table decision`. The planner runs in
  the diagnosis worker, so as the agent's database login, and it reads `decision` and `execution` to avoid asking a
  step twice. That login had no right to read either. The end-to-end test ran as an all-powerful database user, so it
  could not see this. Same family as the `outcome` grant found live on 2026-10-15 (KAV-87).
- **Nothing unsafe happened:** no proposal was filed and nothing in AWS changed.
- **Fix** (PR `fix/KAV-95-agent-reads-approvals`): `GRANT SELECT ON decision, execution TO kaval_agent` in
  `scripts/ops/db-roles.sql`, read-only; the agent still cannot write either. A role test runs the planner's own
  lookup as that login and proves writes are refused (it fails without the grant, passes with it). ADR-0063 notes it.
- **Lesson, worth a line:** a role-level test is the one that sees a missing grant. The pod log hides the message
  (only the error's type is printed); the planner's catch-all could also print the message. Left as is for now:
  the message can carry a SQL fragment, and the database server's log has it.
