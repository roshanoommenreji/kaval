# 2026-10-06

## The start-up health check, the last of ADR-0008's three stopping-table safeguards (`KAV-32`, Lab 26)

Picked up the next `ROADMAP.md` Phase 4 line: `pg_isready` plus a sanity query on start,
restoring the latest pre-stop snapshot only on failure. The other two safeguards (graceful
shutdown, snapshot-before-every-stop) were built in earlier sessions; this was the one still
unchecked.

**Design question surfaced before writing any code:** the original table's wording — "only on
failure is the latest pre-stop snapshot restored" — reads as fully automatic. Asked directly,
Roshan chose to have a failed check stop and ask instead of restoring on its own. `make up` is
already an attended command with its own billing-confirmation prompt; a destructive-ish volume
swap (detach, tag damaged, attach a new one from a snapshot) fits that same attended pattern
rather than running unattended off a single SSM round-trip that could itself be the flaky part.

**Built:**

- `scripts/ops/health-check-database.sh` — `pg_isready` + `SELECT 1`, run over SSM (no network
  path to 5432 exists from the operator's machine). Wired into `resume-database.sh` so every
  `make up` gets one; also standalone as `make db-health-check`. Never restores anything itself
  — on failure it prints the exact restore command and exits non-zero, which stops `make up`
  before `terraform apply` runs.
- `scripts/ops/restore-snapshot.sh` (`make db-restore-snapshot SNAPSHOT=<id>`, or the newest
  snapshot if omitted) — the actual restore, matching the manual procedure
  `docs/runbooks/restore-from-backup.md` already documented: stop Postgres, detach the current
  volume (tag `Reason=damaged`, keep it), create a new volume from the snapshot in the same AZ,
  attach, mount, restart Postgres, re-verify. New compared to the manual version: reconciles
  Terraform state (`state rm` + `import` on the volume and its attachment) so the next
  `terraform plan` doesn't try to undo the restore by reattaching the damaged volume. The
  `aws_volume_attachment` import ID format (`DEVICE_NAME:VOLUME_ID:INSTANCE_ID`) was checked
  against the AWS provider's own docs rather than recalled.
- A second trigger point, for the case nobody ran `make up` for: a systemd oneshot unit,
  `kaval-db-healthcheck.service`, added to `user_data.sh.tftpl`, ordered after Postgres. No
  operator is attending an unexpected reboot, so there's nobody to ask — resolves the same
  "don't auto-restore" decision the other way: logs a loud warning to the journal instead of
  restoring, for whoever looks next.

**Verified live, not just reviewed:** `make db-health-check` run against the actual running
production database — read-only, so it didn't need a separate go-ahead beyond this story's own.
Passed. `terraform validate` passed on the `database` module; `terraform plan` against prod
showed no changes anywhere, confirming the boot-unit edit is correctly inert
(`lifecycle.ignore_changes = [ami, user_data]` on the instance means it only takes effect on the
next genuine replacement) and that nothing else drifted.

**Deliberately not run live:** `make db-restore-snapshot`. It stops Postgres and swaps the data
volume on the actual production server — real enough to need its own explicit go-ahead, same
reasoning as the pause/resume scripts' still-pending real stop-test from the 2026-10-05 session.
Syntax-checked and reviewed line by line against the runbook instead.

Full writeup in [Lab 26](../labs/lab-26-startup-health-check.md); ADR-0008 amended with the
same-day reasoning. `ROADMAP.md`'s "Start-up health check" line ticked — the last of Phase 4's
three named stop/start safeguards is now built.

## The restore drill, run for real (`KAV-32`, Lab 27)

Picked up the next open Phase 4 line right after the health check above: "Restore drill —
measured RTO recorded, and `restore-from-backup` runbook verified." Asked directly, Roshan chose
to run it live against prod rather than defer it again.

Resumed just the database (not the full `make up` — the drill didn't need the app node), then
ran `make db-restore-snapshot` for real against that morning's DLM snapshot, with an explicit
go-ahead for the actual destructive step (stop Postgres, swap the volume).

**It found two real bugs, immediately**, both latent since Lab 26 because the script had only
ever been syntax-checked and reviewed, never run: Git Bash on Windows rewriting `/dev/sdf` into
a Windows path before the AWS CLI saw it, and the AWS CLI's `--parameters` shorthand parser
choking on a nested double quote in the mount command. Recovered the in-flight state by hand
(the old volume was already safely detached and tagged by that point, the new one created but
not attached) and fixed both in `restore-snapshot.sh` for next time.

**RTO: ~3m51s**, confirmation to verified-healthy. `signal`/`incident` tables were empty before
and after — not a failure, just no real incident data in prod yet to lose, so this drill proved
the restore mechanism works, not that data survives it. Worth re-running once prod has real
history.

Cleaned up afterward: deleted the old pre-restore volume by hand (confirmed with Roshan first —
it's an irreversible delete), applied a small tag-only Terraform fix the import had left on the
new volume (`-target`ed at just the database module, confirmed 0 destroy first), and paused the
database again to return to Phase 4's standing posture.

Full writeup in [Lab 27](../labs/lab-27-restore-drill.md); ADR-0008 amended; `ROADMAP.md`'s
"Restore drill" line ticked — the restore path documented since Lab 22 and built in Lab 26 is
now a verified fact.

## The `make up`/`down` drill, part 1 — two more bugs, then an AWS wall (`KAV-32`, Lab 28)

Picked up `ROADMAP.md`'s last open Phase 4 line right after Lab 27: `make up` / `make down`,
never run for real end to end. Read-only verification *before* touching anything — a plain
`terraform plan` against prod, the same habit that's paid off all session — caught a real one
immediately: `associate_public_ip_address` on the database instance only reads back `true` while
running, so with the database paused (stopped), the plan wanted to destroy and recreate the live
server. Fixed with a one-line addition to the instance's `ignore_changes`, confirmed inert with a
plan showing zero changes, before running anything live.

Running `make up` for real then hit a second bug: the resumed database's health check failed —
Postgres couldn't find its TLS cert. Root cause was worse than the symptom: `/etc/fstab` still
pointed at the volume Lab 27's restore detached and later deleted, so the real 20 GB data volume
never mounted at all, and Postgres quietly auto-initialised a brand-new empty cluster on the root
disk instead. The actual restored production data was never touched — nothing had written to it,
since nothing had mounted it. Recovered live (approved step by step): stopped Postgres, fixed the
stale `fstab` line, discarded the bogus empty cluster, remounted the real volume, confirmed the
original TLS cert was still there untouched, restarted, health check passed against the real
data. Fixed `restore-snapshot.sh` to rewrite the `fstab` line on every restore going forward, and
hardened the systemd unit (`RequiresMountsFor=/data`) so a future instance can't repeat this
failure mode even if `fstab` goes stale again — though that only takes effect on the next genuine
instance replacement.

`terraform apply`'s remaining step — scaling the app node's ASG to 1 — then failed for a reason
with nothing to fix in code: no Spot capacity for `t4g.medium` anywhere in `ap-south-1` right now.
Confirmed the ASG already spans all three AZs; AWS's own activity log said as much. Polled for
about 5 minutes, still nothing. Left `desired_capacity=1` — the ASG keeps retrying on AWS's side
at no cost — and left the database running rather than pausing it, since the drill is paused, not
done. `ROADMAP.md`'s `make up` / `make down` line stays unchecked: two real bugs fixed is
progress, but the round trip itself hasn't happened yet. Full writeup in
[Lab 28](../labs/lab-28-make-up-down-drill.md); ADR-0008 amended with both findings.

## The `make up`/`down` drill, part 2 — On-Demand to get unstuck, then a far bigger bug (`KAV-32`, Lab 28)

Spot stayed unavailable for `t4g.medium` for over three hours, then also for `t4g.large` across
multiple AZs — a region-wide Spot squeeze for the whole `t4g` family that day, not one unlucky
AZ. Switched the node to On-Demand temporarily (new `var.spot` toggle in `infra/modules/node`,
default `true`) just to get the round trip done. It launched immediately: k3s `Ready`, Flux
reconciled, all four services running in `kaval-prod`.

Then read `make down`'s actual command for the first time, closely, before running it — and a
plan (never applied blind) showed it would destroy far more than the node: the entire budget
guardrail module, *and the live production database* — its instance, security group, and volume
attachment. Two stacked causes: `module.budget`'s `asg_name` was a live Terraform reference to
`module.node.asg_name` even though that value is a hardcoded literal that never varies, creating
an unnecessary dependency; and the database's security group correctly scopes 5432 to the app
node's security group by ID, which means destroying the node's security group forces destroying
anything that references it — including, transitively, the database itself. **`make down` had
been unsafe since the database module shipped, and nobody had caught it because nobody had ever
run it for real and read the plan.**

Fixed the actual design, not just the symptom: an idle ASG/launch-template/security-group costs
nothing, only a *running* instance bills, so `make down` now scales `desired_capacity` to `0`
(new variables in both `infra/modules/node` and `infra/envs/prod`) instead of destroying
anything. Confirmed with a plan — `0 add, 1 change, 0 destroy` — before applying for real: node
terminated cleanly, database snapshotted and stopped.

Then, reverting the temporary On-Demand override right after, made the same mistake the fix was
meant to prevent in miniature: ran `terraform apply` without re-passing the capacity override, so
Terraform used the variable's default (`1`) and started scaling back up. Spot capacity happened
to have freed up by then, so it actually launched rather than failing — caught immediately,
scaled back to `0`. Fixed properly: the override now lives in a gitignored
`infra/envs/prod/node.auto.tfvars` file that Terraform auto-loads on every plan/apply, which
`make down` writes and `make up` deletes, instead of a one-off CLI flag nothing forces anyone
(including the person who just wrote the fix) to remember to repeat.

Both halves of the round trip are now proven live end to end. `ROADMAP.md`'s `make up` /
`make down` line is ticked. Ended with the node at zero and the database paused — the standing
posture — and the temporary On-Demand/`t4g.large` overrides fully reverted to Spot `t4g.medium`.
Full writeup in [Lab 28](../labs/lab-28-make-up-down-drill.md); ADR-0008 amended a fourth time.
