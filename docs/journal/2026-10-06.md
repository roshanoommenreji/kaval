# 2026-10-06

## The start-up health check, the last of ADR-0008's three stopping-table safeguards (`KAV-32`, Lab 26)

Picked up the next `ROADMAP.md` Phase 4 line: `pg_isready` plus a sanity query on start,
restoring the latest pre-stop snapshot only on failure. The other two safeguards (graceful
shutdown, snapshot-before-every-stop) were built in earlier sessions; this was the one still
unchecked.

**Design question surfaced before writing any code:** the original table's wording — "only on
failure is the latest pre-stop snapshot restored" — reads as fully automatic. Asked directly,
Roshan chose to have a failed check stop and ask instead of restoring on its own. `make up` is
already an attended command with its own billing-confirmation prompt; a destructive-ish volume
swap (detach, tag damaged, attach a new one from a snapshot) fits that same attended pattern
rather than running unattended off a single SSM round-trip that could itself be the flaky part.

**Built:**

- `scripts/ops/health-check-database.sh` — `pg_isready` + `SELECT 1`, run over SSM (no network
  path to 5432 exists from the operator's machine). Wired into `resume-database.sh` so every
  `make up` gets one; also standalone as `make db-health-check`. Never restores anything itself
  — on failure it prints the exact restore command and exits non-zero, which stops `make up`
  before `terraform apply` runs.
- `scripts/ops/restore-snapshot.sh` (`make db-restore-snapshot SNAPSHOT=<id>`, or the newest
  snapshot if omitted) — the actual restore, matching the manual procedure
  `docs/runbooks/restore-from-backup.md` already documented: stop Postgres, detach the current
  volume (tag `Reason=damaged`, keep it), create a new volume from the snapshot in the same AZ,
  attach, mount, restart Postgres, re-verify. New compared to the manual version: reconciles
  Terraform state (`state rm` + `import` on the volume and its attachment) so the next
  `terraform plan` doesn't try to undo the restore by reattaching the damaged volume. The
  `aws_volume_attachment` import ID format (`DEVICE_NAME:VOLUME_ID:INSTANCE_ID`) was checked
  against the AWS provider's own docs rather than recalled.
- A second trigger point, for the case nobody ran `make up` for: a systemd oneshot unit,
  `kaval-db-healthcheck.service`, added to `user_data.sh.tftpl`, ordered after Postgres. No
  operator is attending an unexpected reboot, so there's nobody to ask — resolves the same
  "don't auto-restore" decision the other way: logs a loud warning to the journal instead of
  restoring, for whoever looks next.

**Verified live, not just reviewed:** `make db-health-check` run against the actual running
production database — read-only, so it didn't need a separate go-ahead beyond this story's own.
Passed. `terraform validate` passed on the `database` module; `terraform plan` against prod
showed no changes anywhere, confirming the boot-unit edit is correctly inert
(`lifecycle.ignore_changes = [ami, user_data]` on the instance means it only takes effect on the
next genuine replacement) and that nothing else drifted.

**Deliberately not run live:** `make db-restore-snapshot`. It stops Postgres and swaps the data
volume on the actual production server — real enough to need its own explicit go-ahead, same
reasoning as the pause/resume scripts' still-pending real stop-test from the 2026-10-05 session.
Syntax-checked and reviewed line by line against the runbook instead.

Full writeup in [Lab 26](../labs/lab-26-startup-health-check.md); ADR-0008 amended with the
same-day reasoning. `ROADMAP.md`'s "Start-up health check" line ticked — the last of Phase 4's
three named stop/start safeguards is now built.

## The restore drill, run for real (`KAV-32`, Lab 27)

Picked up the next open Phase 4 line right after the health check above: "Restore drill —
measured RTO recorded, and `restore-from-backup` runbook verified." Asked directly, Roshan chose
to run it live against prod rather than defer it again.

Resumed just the database (not the full `make up` — the drill didn't need the app node), then
ran `make db-restore-snapshot` for real against that morning's DLM snapshot, with an explicit
go-ahead for the actual destructive step (stop Postgres, swap the volume).

**It found two real bugs, immediately**, both latent since Lab 26 because the script had only
ever been syntax-checked and reviewed, never run: Git Bash on Windows rewriting `/dev/sdf` into
a Windows path before the AWS CLI saw it, and the AWS CLI's `--parameters` shorthand parser
choking on a nested double quote in the mount command. Recovered the in-flight state by hand
(the old volume was already safely detached and tagged by that point, the new one created but
not attached) and fixed both in `restore-snapshot.sh` for next time.

**RTO: ~3m51s**, confirmation to verified-healthy. `signal`/`incident` tables were empty before
and after — not a failure, just no real incident data in prod yet to lose, so this drill proved
the restore mechanism works, not that data survives it. Worth re-running once prod has real
history.

Cleaned up afterward: deleted the old pre-restore volume by hand (confirmed with Roshan first —
it's an irreversible delete), applied a small tag-only Terraform fix the import had left on the
new volume (`-target`ed at just the database module, confirmed 0 destroy first), and paused the
database again to return to Phase 4's standing posture.

Full writeup in [Lab 27](../labs/lab-27-restore-drill.md); ADR-0008 amended; `ROADMAP.md`'s
"Restore drill" line ticked — the restore path documented since Lab 22 and built in Lab 26 is
now a verified fact.
