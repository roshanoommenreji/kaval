# 2026-10-13

## Phase 5, slice 6, part A: approvals nobody answers (KAV-82, ADR-0048, Lab 49)

**What.** A request waiting for a person now has a life cycle instead of waiting for ever.
- A reminder after 15 minutes (in the original message's thread), a louder `@here` message after 30
  (to a second channel when one is set), and an **expiry after 4 hours**: the buttons come off and an
  "expired, nothing was done" message goes out. Staging uses 3 / 7 / 15 minutes so the whole sequence
  can be watched.
- The refusal is where the decision is written (`decisions.record_decision`), computed from the
  request's own age, so it holds when the notifier is down or Slack is not configured. Approve and
  deny are both refused after the expiry; the HTTP API answers 409.
- The executor also refuses a human approval older than 60 minutes (production is parked at night, so
  an approval can outlive the moment it was given for).
- Full disk and slow service (no buttons, so nothing to answer) get one louder message after 2 hours
  of still being reported.

**What went wrong, and what it taught.** Reading the code to design this showed that the gateway's
database role could not write to `action`, although the Slack notifier updates `action.slack_notified_at`
after every post. In production the post would have succeeded and the update been refused, so the same
approval would have been posted again every 30 seconds. It was never seen because Slack has not yet run
against the real roles. Fixed with a two-column grant, and a new test (`test_db_roles.py`) runs the real
`db-roles.sql` and checks what each role may and may not do (it fails without the grant).

**Tests.** 21 for the notifier and the refusal (every step, the one-message-per-step memory, a Slack
outage retried, gateway-down catch-up, nothing sent for decided or non-`ask` actions, unusable settings
falling back), 4 for the escalation of people-only faults, 4 for the executor's age rule, 3 for the
database roles, 3 for the rendered chart settings per environment.

**Not yet seen.** The live staging proof (a real request left to expire on the deployed gateway) and a real
Slack post (prod, `KAV-83`).

## Phase 5, slice 6, part B: backups that are watched and restores that are drilled (KAV-82, ADR-0049, Lab 49)

**What.**
- A **daily backup check** that runs from GitHub (so it works when AWS is parked or broken). Its rule is the
  interesting part: a dump is owed only for a 19:30 UTC at which the app server was running (read from the
  auto-scaling group's history), so a parked production raises no false alarm. It also catches a truncated or
  shrunken dump and a restore drill older than 35 days, and reports when it cannot run at all.
- A **read-only role** for it (`infra/modules/backup-watch`): it can list the dump folder and read the server's
  launch history, nothing else. Written and validated; applying it to production waits for an explicit go.
- **`make restore-drill`**: restores production's newest dump strictly into a throwaway Postgres on the laptop,
  counts rows, and writes a dated record. Run for real: it passed, in 1 second, with the dump 63 hours old and
  production holding no signals or incidents (two honest notes on the record).
- **`docs/architecture/disaster-recovery.md`**: RPO 24 h and RTO 30 min for the database, with where each number
  comes from, and two gaps found while writing it down.

**What went wrong, and what it taught.** The first drill failed twice, for the right reasons. It first failed
because the dump predated the `notification` table (an older dump legitimately lacks later tables; the rule now
asks only for the tables the dump's own schema version includes). It then failed because production held no
data, which is true; an empty dump now passes with a visible note instead of making the monthly drill
impossible to pass. Separately, the "dump too small" guess was wrong: an empty schema alone is 20 KB and
production's whole dump is 24 KB, so the size rule became a floor plus "under half the usual".

**Gaps found.** Terraform's state lives only on the laptop (not backed up). The nightly dump skips nights
production is parked, so the "24 hours" in older documents is the disk snapshots' promise, not the dump's.

**Tests.** 20 for the daily check's rules, 15 for the drill record, plus the Terraform module validated.

**Not yet.** The role applied and its two repository variables set; the daily check's first live run; the timer
firing on its own is still unseen.

## Phase 5, slice 6, part C: the database server is watched and patched (KAV-82, ADR-0050, Lab 49)

**What.**
- Two small exporters on the database server (machine and Postgres, 64 MiB each, readable only from the app node),
  a read-only monitoring role, and Prometheus on the app node reading them through targets its init container
  writes from the database address every service already has.
- The database server's own disk goes through the path built last slice (85 %, an incident for a person, no
  automatic proposal, the same runbook, now with a section for this server). Two new rules for the database
  being unreachable and the monitor being silent, neither of which pages while the server is parked.
- Weekly no-reboot patching, connection and failed-login logging, and a cap on Docker's log size so that logging
  cannot fill the disk that is being watched.

**The design turn.** The database server ignores edits to its boot script after creation (a deliberate guard
against replacing a running database), so boot-time setup would never have reached production. Everything is
applied by SSM State Manager instead: on creation, daily, and whenever a stopped server comes back online. One
mechanism for staging (rebuilt each time) and production (never rebuilt).

**Found on the way.** A production plan shows unrelated, existing drift: the app node's launch template (newer
image and boot script, including the nightly dump timer) was never applied to production. It only matters the next
time the node is created, but it should be applied on purpose. Also: a security group's description cannot be
edited in place, so it still says "5432 only" although it now admits the two exporter ports.

**Tests.** 5 for the database disk and its wording, 4 promtool cases for the two rules (healthy, parked, down,
exporter silent), the rendered Prometheus config checked by promtool, Terraform validated for staging and
production, and a read-only production plan: 8 resources to add, none to destroy.

**Proven live on staging (later the same day).** See the next section. **Not yet:** production (with Prometheus, `KAV-83`).

## Phase 5, slice 6: the staging proof (KAV-82, Lab 49)

**What ran.** Staging came up with the database server and its monitoring (6 added, 3 changed, nothing destroyed;
the association ran by itself: Success; the patching association too).

**Part C, proven.** Prometheus showed the two database targets up and the database as reachable; the database's
disk read 33 % (system) and 6 % (data). Forcing the poller's line to 1 % opened `disk_pressure` on
`database-disk`; the real alert code prepared "the database server's disk is nearly full", no fix proposed, nothing
run. Each exporter used about 7 MiB of its 64; 1.4 GB stayed free on the 2 GB database server; Prometheus used
86 MiB and 2.2 GB of 3.8 GB stayed free on the app node.

**Part A, proven.** A request left alone: at 13 minutes the louder `@here` message (the only step still due, by
design); an approval at 16 min 40 s was refused with HTTP 409 "expired with no answer", and the report showed
the expiry message.

**Three things found.** (1) My report script mis-quoted its request, so it printed production's timings instead
of staging's and said "nothing to send": plausible and wrong, now fixed. (2) My first "late" approval went in
16 seconds before the expiry and was correctly accepted; the drill action failed harmlessly (its target does not
exist). (3) The database disk query also listed the exporter container's `/etc/hosts` and `/etc/hostname`;
now excluded.

**Part B, proven live.** After the staging proof I applied the backup-watch role to production on request (a saved
plan: 2 added, 0 changed, 0 destroyed; IAM, $0), set the two repository variables, and ran the daily check once. It
logged in through the role and passed: one dump seen (2026-10-10), "no dump owed is missing, the newest is a
plausible size, a drill is recent". The second job (opens an issue) correctly stayed skipped.

**Still not seen.** A real Slack post (production, `KAV-83`), the 19:30 UTC dump timer firing on its own, and the
check raising for real (only the unit tests have made it raise).
