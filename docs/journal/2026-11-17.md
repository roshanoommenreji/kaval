## A ceiling over the two roles that act (`KAV-161`)

Built on branch `infra/KAV-161-boundary-and-brake-limit`; **nothing is applied to AWS**, $0. Plan first, as always: ADR-0101 was already accepted, so this is the build of its decisions 2 to 4 ([Lab 103](../labs/lab-103-a-ceiling-over-the-two-roles-that-act.md)).

- **The brake's group limit (A-2).** `ScaleAsgToZero` (all three verbs, every group) became two statements: looking at groups stays on `*` (AWS cannot narrow a list call); update and set-size only on a group carrying `Project=kaval`. Checked against AWS's own service reference that both actions support the label condition; both server groups carry the label on the group itself.
- **Two ceilings (A-3).** `infra/modules/budget/boundary.json` (fixed text, deliberately not following the module's variables) and `infra/modules/waste-removal/boundary.json.tftpl`; each attached to its role with `permissions_boundary`. `terraform validate` passes on both modules.
- **A change from the story's wording (A-5).** "Require `Env` to match" would have broken the remover's rule for old copies with no `Env` label at all, which the code deliberately deletes. So it is a Deny for a copy labelled with another environment's name, in the role and the boundary. Recorded as an amendment to ADR-0101. A test keeps Terraform's list of environment names equal to the code's.
- **Proof.** `scripts/dev/test_iam_boundaries.py`: about 100 allow and refuse cases against each boundary, with the role policy widened to everything. Two ways of checking: a small checker in the file (runs in CI) and IAM's own simulator on request, which must agree on every case. Run 2026-11-17 07:30: 116 passed, simulator agreed on all of them. The first simulator run caught a mistake in the test (a made-up log ARN AWS rejects), not in the boundary. Loosening a boundary on purpose makes five tests fail, and they pass again when it is put back.
- **A thing worth knowing.** The brake lives in production's Terraform record but covers staging's group too, so "staging first" cannot mean applying to staging first. The plan: one apply to production's record (brake only, plan shown, his typed go), then at once a staging session that fires it for real. The risk of this change is the brake itself (the nightly 02:00 stop uses the same function and role), which is why the proof follows at once.
- **Left for the owner's go.** The plan and apply of the brake on production's record; the staging session (fire the brake, rerun the remover's refusals); production's remover at its next start-up; then `make iam-review` should show "boundary: yes" on both roles.
