## `KAV-106` and `KAV-105`: two health pages, locked-down pods

Built test first as one package ([ADR-0068](../adr/0068-two-health-pages-and-pods-that-pass-restricted.md), [Lab 67](../labs/lab-67-two-health-pages-and-pods-that-pass-restricted.md)). The gateway gets `/livez` (nothing behind it) and `/readyz` (the migrated database only); `/healthz` is unchanged. Every pod in the chart now runs as a non-root user with the system-call filter, no privilege escalation and no extra powers.

Two things worth remembering. First, the in-cluster Postgres cannot start as a non-root user on a disk it does not own: Docker reproduced the exact error (`initdb: could not change permissions`) with the old layout, and the fix is to keep the data in a subfolder. My first attempt at that test proved nothing, because a Docker volume copies the image's own folder ownership and hides the problem; a memory-backed folder owned by root with group 999 imitates Kubernetes properly. Second, Kubernetes' own checker (a server-side dry run into a namespace that warns at `restricted`) flagged the old chart 9 times and the new one 0 times, for local, staging and prod values. A minikube profile would not start here; Docker Desktop's built-in cluster did the check.

Not yet done: the staging run (about $1), promotion, and production's next bring-up with `make prod-smoke`. `KAV-105` and `KAV-106` stay open until then.

## Staging run, first attempt: a start-up wait that never ended

`ASSUME_YES=1 make staging-up` created all 91 resources, then the pods never came up (15-minute wait expired). One pod, the database migration, sat in its first step; its log said `no attempt`. Cause: the seven start-up waits run `pg_isready` from the Postgres image, and as user 10001 (new in `KAV-105`) the tool has no account to take a default user from and refuses to connect. Reproduced in Docker, fixed by naming the user (`-U "$POSTGRES_USER"`) in all seven, new chart test with a negative case, [ADR-0068](../adr/0068-two-health-pages-and-pods-that-pass-restricted.md) amended, [Lab 67](../labs/lab-67-two-health-pages-and-pods-that-pass-restricted.md) Part 5. The tests and the cluster's dry run had passed because neither runs the pod; staging did its job. Staging was left running while the fix goes through (about $0.045 an hour; it parks itself after four idle hours).

## Correction (written the same evening): the retries were already there

The entry above, and [Lab 67](../labs/lab-67-two-health-pages-and-pods-that-pass-restricted.md) Part 6, said Flux was stuck because staging's release had no retries set. That was wrong: staging and prod both retry an install and an upgrade three times (and so does the lab). The three attempts had run out on the broken chart, and a release whose retries have run out is not tried again by itself; prod did the same on 2026-10-02 ([Lab 20](../labs/lab-20-flux-gitops.md)), and deleting the `HelmRelease` for a clean install was the cure then. Staging could have been unstuck that way instead of rebuilt (about $1 and an hour spent). Found when planning the follow-up (`KAV-108`): the file already had the lines. Lab 67 is corrected, the runbook gains the step, and a test now guards the retries. Whether `remediateLastFailure: true` would let a release heal itself is unproven and not done.
