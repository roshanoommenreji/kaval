## `KAV-108`: what Flux does when its retries run out, measured on staging

After Roshan saw the plan on 2026-11-03 and said "go" (and again at each live step), staging was built from nothing (23:25 to 23:31 IST, 93 resources, 9 of 9 pods) and two experiments were run on throwaway test releases in their own namespaces. [ADR-0076](../adr/0076-a-stalled-flux-release-is-reset-not-rebuilt.md) has the decision and the tables, [Lab 76](../labs/lab-76-what-flux-does-when-its-retries-run-out.md) the recipe.

- **The prediction was wrong.** Written down first: after a failed first install, with today's settings, the simple repair (changing the release's own values) would leave the release stuck. It healed within about 17 seconds, by an upgrade of the leftover failed record. With `remediateLastFailure: true` it installed fresh within about 12 seconds. The setting only changes what is left behind when Flux gives up (nothing, or a failed record).
- **Experiment 2 reproduced the stuck state.** With the cause outside the release (a quota allowing no pods, deleted by hand), neither release tried again in five minutes, and a plain nudge changed nothing. `flux reconcile helmrelease --reset` repaired both in about 30 seconds, nothing deleted.
- **Decision.** The setting is not adopted. The first remedy for a stalled release is the reset; deleting the release is the fallback; rebuilding staging is never needed. [Runbook step 4b](../runbooks/prod-rollout.md) and [Lab 67](../labs/lab-67-two-health-pages-and-pods-that-pass-restricted.md) Part 6 are corrected. **Not proven:** the exact `MissingRollbackTarget` state of 2026-10-31, and a new chart revision from Git (only a values change was tested).
- **A mistake caught on the way.** My first watcher looked for Helm's records in the target namespace and printed "release: not found" for both releases. Flux keeps them in `flux-system`. Nothing was concluded from that column before it was re-read.
- Cost: about $0.20 (staging for about 3.7 hours at $0.045 an hour).

Staging was left up at the end of the first session. I had told Roshan staging "parks itself after four idle hours" and forgot this second rule. The staging docs now say so ([ADR-0029](../adr/0029-staging-parks-itself-when-idle.md) amended; `staging.sh`, the Makefile help, `CLAUDE.md`, the budget plan, Lab 30, the repo guide, the roadmap).

## `KAV-125` built: the database-roles script no longer prints the passwords

Built on `fix/KAV-125-no-passwords-in-logs`, tests first, after Roshan said "go" to the list. [ADR-0077](../adr/0077-the-database-roles-script-keeps-passwords-out-of-psqls-output.md), [Lab 77](../labs/lab-77-passwords-that-stay-out-of-the-logs.md).

- **The finding, now a failing test.** The existing role test goes through the Python driver, which prints nothing, so it could never see this. A new test runs the real `psql` with four fake passwords against the same Postgres image CI uses. Against today's file the control passed, the leak test said `psql printed the password of: gateway, agent, executor, collector`, and the no-database guard named lines 22 to 25.
- **The fix.** The four `SELECT set_config(...)` statements end in `\gset`, which keeps the result in a `psql` variable instead of printing it. A third test proves each role's stored password fingerprint still matches the password it was given (and was seen failing when one password was changed on purpose). A rewrite with `\getenv` and `\gexec`, as `db-monitoring.sh` does, was left as a later cleanup.
- **A slip the tests caught.** Right after the fix the five older role tests said "5 skipped": they apply the file through the Python driver, `\gset` is a `psql` command, and a catch-all `except` turned the error into a skip. In CI, with the database required, those five would still have skipped silently, because the skip is inside the test, not in the database check. The older test now translates the line and skips only for "this database user may not create roles" (SQLSTATE 42501); anything else fails.
- **Missing `psql` cannot hide.** Without `psql` the new tests skip on a laptop and fail in CI (`KAVAL_REQUIRE_DB=1`). This laptop has no `psql`, so the tests ran through a one-line stand-in that runs it inside the database container.
- **Noticed, not changed.** The node's bootstrap passes the passwords as `psql` command-line arguments (visible in the process list for a moment); `db-monitoring.sh` already uses the environment for that reason. The database server's own statement log is off by its configuration (no `log_statement`); the live value is read in the staging proof.
- **A recommendation for Roshan:** do not rotate production's four passwords (root-and-`adm`-only logs on a server that no longer exists, no log shipping, the database reachable only from the app node); rotating is cheap if he prefers it at the next bring-up.
- Not proven yet, and ticked only when it is: zero occurrences of each password in the boot log and the journal on a staging booted after the merge.

## `KAV-124` built: the approval command never follows a redirect

Built on `fix/KAV-124-approve-no-redirect`, tests first. [ADR-0075](../adr/0075-a-redirect-is-never-followed-so-the-atlassian-login-stays-home.md) amended, [Lab 75](../labs/lab-75-a-login-that-stays-home.md) Part 6.

- **The finding, now failing tests.** Twelve tests against two real local servers (one plays the gateway and redirects, the other records what it is sent). Five failed first: for a 301, 302 and 303 the second server received the request, because Python re-sends a `POST` as a `GET` with its headers; a 307 and a 308 were already refused for a `POST`, and the tests pin that; the plain-message and same-address tests failed too.
- **The fix.** `approve.py` has its own copy of the handler (as `promote.py` does). Any redirect stops the command with one plain line that names neither the token nor where the answer pointed, and says the decision may already be recorded. A 401, an unreachable gateway and a missing token are reported exactly as before (pinned).
- **A wrong guess of mine, corrected.** I had planned a staging session to prove `make approve` "through the tunnel". But `approve.py` is not how approvals reach staging: `make chaos-approve` runs `curl` on the node with the token read from the cluster's own Secret, and `approve.py` only talks to a gateway through the laptop's tunnel to the dev server. ADR-0075's sentence that the flow "is proved live on staging" is corrected, and the story's acceptance criteria are rewritten.
- **Proved instead on the laptop, for $0:** the real gateway (`uvicorn kaval_gateway.main:app`) against a local Postgres, a real pending action, and the real `approve.py`: a wrong token got `401 Unauthorized` and exit 1 as before; the right token printed the decision, exit 0, and exactly one `approved` row was in the database.
- So the shared staging session is now for `KAV-125` and `KAV-126` only.
