## `KAV-108`: what Flux does when its retries run out, measured on staging

After Roshan saw the plan on 2026-11-03 and said "go" (and again at each live step), staging was built from nothing (23:25 to 23:31 IST, 93 resources, 9 of 9 pods) and two experiments were run on throwaway test releases in their own namespaces. [ADR-0076](../adr/0076-a-stalled-flux-release-is-reset-not-rebuilt.md) has the decision and the tables, [Lab 76](../labs/lab-76-what-flux-does-when-its-retries-run-out.md) the recipe.

- **The prediction was wrong.** Written down first: after a failed first install, with today's settings, the simple repair (changing the release's own values) would leave the release stuck. It healed within about 17 seconds, by an upgrade of the leftover failed record. With `remediateLastFailure: true` it installed fresh within about 12 seconds. The setting only changes what is left behind when Flux gives up (nothing, or a failed record).
- **Experiment 2 reproduced the stuck state.** With the cause outside the release (a quota allowing no pods, deleted by hand), neither release tried again in five minutes, and a plain nudge changed nothing. `flux reconcile helmrelease --reset` repaired both in about 30 seconds, nothing deleted.
- **Decision.** The setting is not adopted. The first remedy for a stalled release is the reset; deleting the release is the fallback; rebuilding staging is never needed. [Runbook step 4b](../runbooks/prod-rollout.md) and [Lab 67](../labs/lab-67-two-health-pages-and-pods-that-pass-restricted.md) Part 6 are corrected. **Not proven:** the exact `MissingRollbackTarget` state of 2026-10-31, and a new chart revision from Git (only a values change was tested).
- **A mistake caught on the way.** My first watcher looked for Helm's records in the target namespace and printed "release: not found" for both releases. Flux keeps them in `flux-system`. Nothing was concluded from that column before it was re-read.
- Cost: about $0.20 (staging for about 3.7 hours at $0.045 an hour).

## The nightly auto-stop stopped staging, and it was not the idle timer

Staging was left up at the end of the first session. At 02:00:06 IST the account's nightly auto-stop ([ADR-0008](../adr/0008-production-database-on-its-own-server.md)) scaled its node group to zero and stopped its database (CloudTrail: the `kaval-budget-hard-stop` role). The idle-stop Lambda had logged `idle=False` (5,357 seconds of 14,400) just before, and no budget was near its limit (`kaval-monthly`: $1.34 of $50, forecast $13.50, every alert in state OK). I had told Roshan staging "parks itself after four idle hours" and forgot this second rule. The hard-stop Lambda logs "Budget hard stop triggered" for the nightly run too, which reads as a money alarm and was not. A resumed staging gets a **new cluster**, so the test releases were gone and the second experiment waited for a 7½-minute resume. The staging docs now say so ([ADR-0029](../adr/0029-staging-parks-itself-when-idle.md) amended; `staging.sh`, the Makefile help, `CLAUDE.md`, the budget plan, Lab 30, the repo guide, the roadmap).

## Found while reading the logs: three stories filed

- **`KAV-125` (security, 2 points): the four service-login passwords were printed into the node's logs.** `scripts/ops/db-roles.sql` passes each password to the database with a `SELECT`, and `psql` prints the result. Counted without printing anything: each of the gateway, agent, executor and collector passwords is in the boot log once and the journal three times; the admin password nowhere. The same script runs in production, whose app server is not running now (its logs went with it). One staging password appeared in my own tool output; it was copied nowhere and died with staging.
- **`KAV-126` (1 point): a good seed was reported as "skipped".** The permissions pass re-runs the whole bootstrap about 20 seconds after boot and its seed step overwrote the status file. The restore had run (its log lines are there); only the report was wrong.
- **`KAV-127` (1 point): `make staging-down` misses the nightly stop's snapshots.** It deletes snapshots by a name pattern those do not carry. A sweep after the teardown found three (10 GB each, from 22 Oct, 27 Oct and 4 Nov). Not deleted yet: deleting AWS resources needs a go. (The tag search lags and still listed volumes, snapshots and servers that were gone; each was checked directly.)
